Prototype of Konjir's engine and its delivery rails:

- **Kolab:** versioned specs with stable element IDs, the invalidation cascade, child-spec overrides with the three-way rule, the review gate, and role enforcement. It implements the three decisions in *Konjir — Open Design Decisions*.
- **An MCP server:** stateless Streamable HTTP, MCP spec 2026-07-28, with the SDK's fallback for 2025-era clients. It's a NestJS app; each verb is an `@McpTool` method, the inboxes are `@McpResource` methods, and the operating instructions and the reviewer's instructions are `@McpPrompt` methods, served too as the `konjir_instructions` tool and the `konjir://instructions` resources (`apps/server/src/instructions.ts`: one text for all three).
- **An OAuth 2.1 authorization server** for the MCP endpoint and the web interface, with GitHub as the identity: a person signs up and in with GitHub, and their client gets short-lived access tokens that refresh (D55). See *Signing up and in*.
- **A `konjir` CLI:** the same verbs for a shell or any harness without MCP. It is an MCP client of Kolab, so there is one backend.
- **A web interface:** a React and Vite single-page app that Kolab serves at its root, kept live with server-sent events, for a person who never opens a terminal (W3.1, API8). See *The web interface*.

TypeScript on Postgres, through [Kysely](https://kysely.dev). Give `konjir serve` a `--database-url` (or `KONJIR_DATABASE_URL`) for a Postgres server. Without one, Kolab runs on embedded Postgres ([PGlite](https://pglite.dev), Postgres in WASM), so local development needs no server.

## Changing the schema

The schema is the SQL files in `libs/db/src/migrations`, applied in order (DAT2). `0001_schema.sql` is the core schema; each later file changes it. When Kolab opens a database, it applies the files it hasn't recorded yet, in one transaction under an advisory lock. It records each one in the `kj_migration` table, with the sha256 of the file's text. A second Kolab process opening the same database waits for the first, then finds nothing left to do. A migration that fails rolls the whole open back, and the error names its file. Kolab refuses to open a database in two cases:

- it's recorded at a migration this release doesn't have
- a recorded file's text has changed since it was applied

The error names the file.

A database made before migrations began has Kolab's tables but no `kj_migration` table. Those are PGlite data directories from release 0.5 on, and the test server's first RDS database. Kolab runs `baseline.sql` on it once, which brings it to 0001 with idempotent statements. It then records 0001 as baselined, with 0001's checksum.

To change the schema:

1. Add `libs/db/src/migrations/NNNN_what_it_does.sql`, numbered one past the last file. The name must be four digits, an underscore, then lowercase letters, digits and underscores. Any other `.sql` file in the folder stops Kolab loading, so a misnamed migration can't be skipped.
2. Never edit a file that has shipped, not even a comment, and never edit `baseline.sql`. An edited file would never reach databases that already ran it, so Kolab refuses them instead. `libs/db/src/migrations/checksums.json` pins the sha256 of every `.sql` file in the folder. Kolab refuses to load if any file differs from its pin, has no pin, or is pinned but missing. The release ships only a commit's tracked files (`deploy/release/pack.sh`), and Kolab's own checkouts and tests load whatever is in the folder, so this check is what keeps a draft migration from loading or shipping unpinned. Add the new file's checksum there (`shasum -a 256 <file>`) when it's ready to ship, and never change an existing one.
3. Write plain SQL that runs once. It doesn't need to be idempotent. Every file runs inside the runner's one transaction, so a file may not contain `begin`, `commit`, `rollback`, `end`, `abort`, `start transaction`, `savepoint`, `release` or `prepare transaction`. Kolab rejects such a file when it loads. The same words are fine inside comments, string literals (including `E'…'` strings), quoted identifiers, and dollar-quoted bodies: `do $$ … $$` blocks and `as $$ … $$` functions. Write a function's body dollar-quoted, not as a SQL-standard `begin atomic … end` body, whose `end` the check can't tell apart. Avoid statements that can't run in a transaction, such as `create index concurrently`. Statements that create roles must guard against another database on the same cluster creating them first, as `0001_schema.sql` does.
4. **A new table** gets no rights by itself. The engine writes as `kj_agent` or `kj_system` through `set local role`, so grant each what it needs explicitly. If the table holds kolab data, give it a `kolab_id` that references `kolab`, not null, set from its parent by the `kolab_of_parent` trigger (`kj_kolab_of_parent`, from 0006) or by Kolab, and enable row-level security with policies like 0006's: `kolab_read` for `kj_agent` (`kolab_id = kj_session_kolab()`), `system_all` for `kj_system`, and for anything an agent inserts, an `agent_layer` policy plus a restrictive `kolab_write`. Grants on all tables are fine: Kolab revokes everything on `kj_migration` from `kj_agent`, `kj_system` and `public` after every migration.
5. **Value lists.** `MARK_REASONS`, `QUERY_KINDS`, `QUERY_STATES`, `ACTOR_KINDS`, `ACCOUNT_KINDS`, `ORG_ROLES`, `ACCESS_LEVELS`, `VISIBILITIES`, `VERSION_STATES`, `REVIEW_REQUEST_STATES`, `OUTBOX_KINDS`, `OUTBOX_STATES`, `CASE_FILE_STATES`, `POSITION_VERDICTS`, `RULING_EFFECTS`, `ARCHIVABLE`, `AUDIT_ACTIONS`, `KINDS`, `WORK_STATES`, `WORK_EVENT_KINDS` and `EVIDENCE_KINDS` in `@konjir/types` are also written out in the database's `invalidation_reason_check`, `query_kind_check`, `query_state_check`, `actor_kind_check`, `account_kind_check`, `org_member_role_check`, `kolab_grant_level_check` and `kolab_base_permission_check` (both `ACCESS_LEVELS`), `kolab_visibility_check`, `version_state_check`, `review_request_state_check`, `outbox_kind_check`, `outbox_state_check`, `case_file_state_check`, `position_verdict_check` and `ruling_verdict_check` (both `POSITION_VERDICTS`), `ruling_effect_check` and `position_seeks_check` (both `RULING_EFFECTS`), `archive_event_kind_check`, `audit_event_action_check`, `node_kind_check` (with `LAYER_OF_KIND` in `node_layer_of_kind`), `work_package_state_check`, `work_event_kind_check` and `evidence_kind_check`. A change to any of them needs a migration that drops the check and adds it again with the whole new list. The test "the database's value lists are @konjir/types' …" fails until there is one. Before removing a value, the migration must deal with the rows that use it.
6. Run `npm test` and `npm run test:postgres`.

The files ship as they are: the release runs `libs/db/src`, and `npm run build` copies them to `libs/db/dist/migrations`, so they are found from either.

## Running it with agents

```
# 1. Start Kolab. It persists to ./.konjir and prints an admin token: the break-glass token (see *Konjir's admins*).
bin/konjir serve --port 7420

# 2. Register a person, a kolab they own, and the agents they own, each granted access to it.
export KONJIR_URL=http://127.0.0.1:7420/mcp KONJIR_TOKEN=<admin token>
bin/konjir admin_add_actor id=lee
bin/konjir admin_add_kolab name=checkout owner=lee              # Lee owns it: Admin
bin/konjir admin_add_actor id=lee-pm owner=lee
bin/konjir admin_add_actor id=lee-eng owner=lee
bin/konjir admin_grant kolab=checkout to=lee-pm level=write layers='["functional"]'
bin/konjir admin_grant kolab=checkout to=lee-eng level=write layers='["technical"]'

# 3. Give each agent a session in the kolab (one actor, one kolab, one active role).
bin/konjir admin_open_session actor=lee-pm role=product kolab=checkout   # prints the agent's token
bin/konjir admin_open_session actor=lee-eng role=engineer                # kolab defaults to the one it can reach
bin/konjir admin_list_actors owner=lee                                   # an account's agents
```

Then point each harness at Kolab with its own token. The token decides who the agent is, which kolab it works in and which layer it may write. Tool arguments never carry identity.

Where Kolab has an identity provider (GitHub, D55), none of this needs an admin: a harness that speaks MCP's authorization, such as Claude Code, connects with the URL alone, and the person signs in with GitHub and chooses, on Kolab's consent page, who the harness works as (an agent of theirs, by default), in which kolab and role. See *Signing up and in*. Hand-issued tokens keep working beside it during the transition.

**A token is shown once (P1, D50).** `admin_open_session` prints it, beside the session's key, and nothing prints it again: `whoami` names the session by its key. Kolab stores no token. A session's id is its key, the sha256 of its token, base64url (`sessionKey`), and Kolab hashes the bearer token on every request to find its session; a key presented as a token finds nothing. Row-level security's `kj.session` carries the key too, so the token never reaches the database at all, and a check (`session_id_is_key`) refuses any id that isn't a key. To revoke a session, `admin_end_session` takes exactly one of its `token` (`kjs_…`), its `session` key (43 base64url characters) or the `actor` whose open session it is, and returns the key it ended. A token passed as `session=`, or a key as `token=`, is refused, naming the right argument, and so is a call that matches no open session, so a mistyped revoke never reads as a successful one. The MCP client a token connects as is named by its key too, never the token, and the admin token is compared in constant time. Migration 0011 hashed every existing session's id in place, so each token handed out before it, agents' included, kept working. It can't be undone (see *Deploying to AWS*).

An actor is a person, or an agent owned by an account: a person or an organization. Each agent is an actor of its own: it holds its own session, so one person's agents can each hold one at the same time, and it is the author of what it writes. `whoami` names the agent and its `owner`, its kolab and its access there, and `read_node` gives each version's `author`, with the agent, its owner and its role. An actor's kind and owner never change once it's added, so past authorship stays as it was written. An id is letters, digits, `.`, `_`, `-` and `@`, and `kolab` is reserved for Kolab's own work. Two actors with Write on one layer of a kolab review each other's versions there (see *Review*): two product agents of Lee's with Write on the functional layer each wait for the other's approval.

`deploy/demo/run-local.sh` runs all of this end to end against a throwaway Kolab: two companies, a spec and its binding, reviews, questions, a spec change, a ruling and a restart. `deploy/demo/m1-walkthrough.mjs` runs the same walkthrough against any Kolab, given its URL and admin token. [`deploy/demo/DEMO.md`](deploy/demo/DEMO.md) says what each step shows.

### Accounts, kolabs and access

Kolab follows GitHub's model (D3). An **account** is a user or an organization, in one namespace: each person is a user, by the same id. An organization has **members**, some of them **owners**, and **teams**, which can nest and hold no konstructs. A **kolab** belongs to one account. Its name is unique across the whole database (`kolab.id`, its primary key, lowercase letters, digits and `-`), so a name another account has taken is refused (D7, D12). It is `private` by default, or `public` (anyone may read it) or `internal` (the owning organization's members may), and an organization's kolab may have a **base permission** that every member holds.

Access to a kolab is one of five levels, `read`, `triage`, `write`, `maintain` and `admin`. A `write` grant names the layers it covers, `functional`, `technical` or both; `maintain` and `admin` cover both, and `read` and `triage` write neither. A person's access is the most that any of these gives them: owning the kolab or being an owner of the organization that owns it (Admin), the base permission, a grant to them (a member or an outside collaborator), or a grant to a team they are in or to a parent of one. Teams are granted access only to their own organization's kolabs, and `kj_access` counts a team's grant only on a kolab its organization owns. Kolab alone refuses a base permission on a person's kolab, where it would give nothing anyway: it counts only for members of the owning organization. A session may write its role's layer only while its access covers that layer; with less, it can still read and ask.

**An agent never holds more access than its owner (TEN11, D30).** Its access is its own grant on the kolab, cut down to what its owner holds there: the lower level, and only the layers both may write. An organization holds all of its own kolabs and nothing in anyone else's, so its agents work only in its kolabs. Kolab enforces this in several ways:

- `admin_grant` refuses an agent a grant its owner lacks: a higher level, or a layer its owner can't write.
- A session's access is computed when it opens and on every use, from the grants as they stand. So an agent's session opens with no more than its owner holds, and it narrows the moment its owner's access does. An agent whose owner holds nothing in the kolab can't open a session there at all.
- Every change to grants, memberships or teams ends, in the same transaction, each open session that can no longer reach its kolab, and tells its listen streams so they close (D41). A narrowed session stays open. Those changes and sessions opening take one advisory lock, so a session can't open on access a concurrent change is removing. A session found with no access when it is used (after a change made outside Kolab's verbs) is ended then, and its streams are told.
- A draft commits only while its author may still write its layer: one whose author lost Write since drafting is rejected, whoever submits it. And submitting needs Write on the draft's layer: Read can't decide when someone's draft becomes truth.

Every row of Konjir data carries its kolab: nodes, sessions, versions, elements, deltas, edges, marks and their causes, questions, case files, positions, rulings, precedent, and work packages and their events. A child row takes its parent's kolab when it is inserted, whatever its writer gave. A session works in one kolab, and everything an agent writes or works on (a node it drafts, a mark, a question, a link's source) must be in it; a link's target and a variant's parent may be another kolab's committed version it reads (see *Links and forks across kolabs*). Reading is wider: a full address, `kj:<kolab>/<node>…`, resolves in any kolab the session's actor holds Read on (see *Addresses* below). Anything else in another kolab is refused as if it didn't exist. Row-level security repeats this in the database. As `kj_agent`, a session reads the rows of its own kolab only while its actor can still reach it (`kj_session_kolab()`). In another kolab it reads only the nodes, the committed versions and their elements and questions, and only where its actor holds Read now (`kj_session_readable_kolabs()`, 0008). It writes only its own kolab (a link or fork it makes may name a committed version it reads elsewhere, 0017), and only its layer while its access covers it (`kj_session_layer()`). The reads Kolab does for a session's addresses run as `kj_agent`, so this binds them too; see *Addresses* for the one read across kolabs that doesn't. How access is computed lives in one place, the database's `kj_access(actor, kolab)`, which the engine calls too.

The database also keeps tenants apart for every role, not only `kj_agent`:

- **No row references another kolab's row**, except a link's target, a fork's parent, an override's base and a mark's trigger, which may name another kolab's committed version (see *Links and forks across kolabs*). Each other reference is a foreign key on the pair of the referenced id and the row's own kolab: a version's node and base, an element's or delta's version, an edge's source, a mark's version, edge and delta, a mark cause's two marks, a question's version, asker's version and mark, a case file's version, and a position's or ruling's case file or version.
- **A row's kolab never changes** once written (`kolab_fixed`), and those keys stop a row being re-parented into another kolab.
- **`kj_agent` reads no sessions**, whose ids are their tokens' hashes (0011), **and no actors**. Only Kolab can run `kj_access` (and `kj_system`, which re-checks an author as a draft commits).
- **No shadowing.** Every security definer function searches `pg_catalog, public, pg_temp`, with temporary tables last. Only the database's owner may create temporary tables (0006 revokes `TEMPORARY` from `public`), so `kj_agent` can't plant a table that a helper would read in place of `session`.
- **Precedent is per kolab**, keyed by the kolab and the fingerprint triple, and a rebase matches only its own kolab's.
- **The served instructions** (the `konjir_operating_instructions` prompt, the `konjir_instructions` tool and the `konjir://instructions` resource) carry only the session's kolab's precedent and answered questions; the admin token gets the rules alone.

Row-level security's session helpers sit in subqueries, so Postgres evaluates them once per statement, and the tables they filter are indexed by kolab. A 400-element draft takes about 320 ms on PGlite, down from about 450 ms before that change.

**Archiving (D52).** Nothing is ever deleted: an admin archives a kolab, an organization or an actor instead, with `admin_archive`, naming exactly one. An archived one is left out of `admin_list_kolabs` and `admin_list_actors` (unless `archived=true`), and can't be used. Its data is kept for audit, and its name stays reserved: a new kolab, account or actor of that name is refused. People, agents and organizations share one namespace, and names in it must differ in more than case, so archiving `lee` also keeps anyone from becoming `Lee`. The refusal reads exactly as for a live holder ("taken"), so nobody learns an archived one exists; only the admin token's verbs add which archived one holds the name and how to unarchive it. `admin_unarchive` restores it as it was, grants and memberships included. Every archive and unarchive is logged, with who asked (`admin` for the admin token) and when, in `archive_event`, which is only ever added to.

- **A kolab:** every session in it ends, in the same transaction, and its listen streams are told so they close (D41). No session opens in it, nothing in it can change, and nobody holds any access there, so nothing reads it but the admin token. A grant on it is refused; revoking one isn't. Its outbox jobs wait, unclaimed, until it is unarchived; a job already running when it was archived is released without counting as an attempt.
- **An organization:** its kolabs and its agents are archived with it, so every member's, team's and grant's access to those kolabs stops counting. It takes no members, teams, kolabs or agents.
- **An actor:** its session ends and none opens. A person's agents go with them (an agent never holds more than its owner, D30). The kolabs a person owns directly stay live for the others who work in them; the archived person holds nothing there, and can't own a new kolab. An agent can be archived alone. Its authorship stays as written.

What goes with an account is computed, not copied: a kolab is archived if it is or the organization that owns it is, and an agent if it is or its owner is. So unarchiving the account brings back exactly what wasn't archived on its own, and unarchiving a kolab or agent whose owner is still archived is refused, naming the owner. Archiving checks, changes and logs under the access lock, in one transaction, so two admins at once can't both archive one thing. Migration 0014 stores it: `kolab.archived_at`, `account.archived_at` (an organization, or a person, whose user account has their id), `actor.archived_at` (an agent only, `actor_archived_is_agent`) and `archive_event`, with unique indexes on `lower(id)` for accounts and actors. The database enforces it as well as Kolab: `kj_access` gives an archived actor, and anyone in an archived kolab, nothing (through `kj_kolab_archived` and `kj_actor_archived`), so row-level security gives `kj_agent` nothing there either. And for every role, Kolab's own login included, statement-level triggers refuse any insert, update or delete of an archived kolab's rows, one check per statement over the kolabs it touched (`kolab_writable_insert`, `_update` and `_delete` on every table with a `kolab_id` but `session`, `outbox` and `audit_event`; new grants on it too), and a trigger refuses any session opening, or reopening, in an archived kolab or for an archived actor (`session_openable`). The one exception is the migration runner: its transaction sets `kj.migrating`, which the triggers honour only on Kolab's own login, never under `kj_agent` or `kj_system` (`kj_migrating`), so a later migration's backfill still reaches archived rows. Each helper is a security definer function with its search path pinned.

**Who made each write (W2.20, D70).** Every write records who made it: an actor, through its session or its own sign-in, a Konjir admin's included (W2.22); `admin`, for the break-glass admin token (`ADMIN_DOER`); or `kolab`, for Kolab's own work. A change with a row of its own says so in that row, from migration 0024 on: `node.created_by` and `created_at`, `account`, `actor`, `kolab` and `team.created_by`, `identity.linked_by`, `session.opened_by` and `ended_by`, `kolab_invite.revoked_by`, `oauth_grant.revoked_by` and `version.submitted_by` (who put a draft to review: its author, the admin applying a ruling, or Kolab for its rebases and folds), beside what already did (`version.actor_id`, `review_request.reviewer_id`, `query.raised_by` and `answered_by`, `invalidation.cleared_by`, the case files', rulings' and precedent's actors, `kolab_invite.created_by` and `accepted_by`, `archive_event.done_by`). A change that leaves no row of its own goes in `audit_event`, which is only ever added to: a grant made, changed or removed (`grant.set`, `grant.removed`), a person added to or removed from an organization or a team (`member.set`, `member.removed`, `team_member.added`, `team_member.removed`) an outbox retry (`outbox.retried`), and, since W2.22, a person made or no longer a Konjir admin (`admin.granted`, `admin.revoked`), an admin raising or lowering their session (`admin.elevated`, `admin.lowered`) and each admin verb the break-glass token ran (`break_glass.used`, its subject the verb), each with its kolab when it has one. Only Kolab's own login reads or writes it, so no session reads it (D49, D58); `admin_audit` lists it. It has no `kolab_writable` triggers, since removing an archived kolab's grant is still allowed and still recorded. Rows made before 0024 keep null: nothing is guessed. After it, the database refuses a row that names no one, or names someone blank, in a constraint trigger checked at commit (`kj_doer_given`); it refuses a change to `kolab_grant`, `org_member` or `team_member` whose transaction adds no `audit_event` row for that grantee or person (`kj_access_audited`); and no actor or account may be called `admin` or `kolab`, in any case (`actor_not_doer`, `account_not_doer`; 0024 stops, naming it, if one already is). Kolab itself has no default doer: each write that a caller asks for takes `by`, and refuses to run without one, so a caller that forgets is never recorded as the admin or as Kolab. Each admin verb passes its doer through one helper in `apps/server/src/admin-tools.ts`, `admin()`, which names the Konjir admin whose raised session called it, or `admin` for the break-glass token, and never falls back to either (W2.22, D69); `@konjir/engine/testing`'s `TestKolab` acts as the admin token when a test names no one. `konjir_read_node` names who made the node (`node_created_by`) to a reader in the node's own kolab only: `kj_agent` can't read `node.created_by`, and reads it through `kj_node_creator`, which answers only for its own kolab's nodes (D49, D58). The web interface's activity names who made each node once one of its versions is submitted. `WRITE_ACTORS` in `libs/engine/src/write-actors.ts` says where each public method of `Kolab` that writes records its actor, or which of a closed list of reasons it records no one for; `libs/engine/test/write-actors.test.ts` reads `kolab.ts` and fails when a method that writes is missing from it, when the SQL a method reaches doesn't write the place it names, when a method records no one that isn't on the test's own list, or when SQL is written anywhere else.

Migration 0006 keeps what the database holds. If it has any actor or node, its data becomes the kolab `kolab`, owned by the organization `konjir`; each person becomes a user and a member of `konjir`, and each person and agent gets Write on both layers of `kolab`, which is what any actor could do before. Open sessions work in `kolab`. A fresh database gets none of this. An existing actor named `konjir`, person or agent, stops the migration, since the organization needs that id: rename the actor first.

**Take a database snapshot before deploying any release with a new migration**, such as 0006, 0007 (the review flow), 0008 (node names per kolab), 0009 (which drops `version.findings`, W1.7), 0010 (the outbox), 0011 (hashed session tokens), 0012 (link removals and the cascade's indexes), 0013 (rulings' dates and the case-file verbs) 0014 (archiving), 0015 (rebase jobs), 0016 (outside readers see no question a mark raised), 0017 (links and forks across kolabs), 0018 (identities and OAuth), 0019 (invites), 0020 (the consent token's index), 0022 (a session that holds only Read sees no mark and no question a mark raised), 0023 (questions about a version in review, and the `withdrawn` state), 0024 (who made each write, and the audit log) 0025 (the paged lists' indexes and the rates' events), 0026 (Konjir's admins, a session's raise, and hand-issued tokens' expiry) 0027 (typed konstruct kinds: `wbs` nodes become `plan`, and each binding and plan names its parent) 0028 (a sign-in's "agent N of M": display only, but once applied an earlier release refuses the database all the same) 0029 (work-package fields on a plan's elements: two nullable columns and their checks, nothing rewritten, and again an earlier release refuses the database once it is applied) 0030 (work state: `work_package`, `work_event` and each kolab's lease length, with a To do package and an `added` event for each element of every plan's latest committed version; nothing else is rewritten, and after it, events and leases written since are lost on going back) or 0031 (work review and evidence: `evidence`, a review request's work-package subject, and a package's `returned` and `touched_at`; nothing is rewritten but `touched_at` on each package In progress, and after it, evidence, work reviews and the returns of requests for changes written since are lost on going back). Once one is applied, an earlier release refuses the database ("recorded at a migration this release doesn't have"), so going back means restoring from that snapshot, which loses whatever was written since: after 0007, for example, versions in review and their review requests, after 0010 the outbox's jobs, the work commits and approvals still owed, and after 0012 the links drafts remove. A release before 0015 also can't run the `rebase` jobs a later one queued.

### Konjir's admins

Admins are people, not a token (W2.22, D69). Specific people, signed in with GitHub (D55), are Konjir admins, and run the admin verbs from their own sign-in, each recorded as theirs. The static admin token stays only as a break-glass. There is no Cognito.

- **Who is one.** `konjir_admin` holds each admin with who made them one and when (migration 0026). Only a person, never an agent (D30, D56): the engine refuses one, and so does the database (`kj_admin_is_person`). Only an admin, or the break-glass token, makes or removes one: `admin_make_admin actor=<person>`, `admin_remove_admin actor=<person>`, `admin_list_admins`. Each change is in the audit log (`admin.granted`, `admin.revoked`), and the database refuses one whose transaction doesn't record it (`kj_admin_audited`).
- **Running admin verbs as yourself: a raise you confirm in your browser, 15 minutes long.** An admin's own session, which they opened by signing in with GitHub (as Yourself, never as an agent, and never a hand-issued one), shows one admin verb, `konjir_admin_elevate`, and that only asks (Lee's ruling of 2026-10-23). It raises nothing: it answers with a link, `<origin>/oauth/raise?request=kje_…`, which lasts 20 minutes and works once. The person opens it in their browser, signs in with GitHub, and confirms on Kolab's page, which says what raising gives. GitHub's OAuth has no forced re-authentication (no `prompt=login`, no `max_age`), so Kolab asks for GitHub's account picker, `prompt=select_account`: the person picks their account by hand, but a browser already signed in to GitHub asks for no password or 2FA. What the step proves is a browser holding the person's GitHub sign-in and a click on Kolab's page, not a fresh credential. The page names the session by what Kolab itself knows: that the request was made over MCP by a session of the person's, its key (`whoami`'s `session`), when it signed in, and the client it signed in through, as Kolab's own web page or as the registered client's id and the origins it receives codes at. A registered client's name is its own choice, so the page shows it only as such, marked unverified. The link is used up whatever happens in the browser: raised, *Don't raise*, cancelled at GitHub, or reached by someone else's sign-in, so a link someone was talked out of using never raises later. Only then does the session carry the `admin` scope, for 15 minutes (`ADMIN_ELEVATION_S`; `session.admin_until`), and see every admin verb. The browser step is a sign-in of Kolab's own (`konjir-raise`) with every protection the consent page has (D55, D57): its own binding cookie (`__Host-konjir_oauth_<id>`), its state at GitHub, the page's form token and Kolab's own `Origin`, and the same limits. It completes only as the session's own person: anyone else who signs in at GitHub, an admin or not, is stopped there and nobody is signed up, and the database step checks it again (`completeRaise`, under the access lock). Asking again and confirming again renews it; `lower=true` ends it now, with no browser, since lowering only takes power away. Each raise and lower is in the audit log (`admin.elevated`, `admin.lowered`); a request is logged (`admin_raise_requested`) but recorded nowhere else, since it changes nothing. Every admin write made meanwhile records the person, through `admin()`: a ruling applied (D47) as `version.submitted_by` and in its review note (`through <person>'s own admin session`), a grant as `audit_event.done_by`, and so on. `whoami` says `konjir_admin: { raised }`, and nothing about how to raise, and the web page says *Konjir admin* under the person's name. Kolab reads the raise, and whether the person is still an admin, from the database on every request, so a raise that lapsed, or an admin removed, stops at once; removing an admin lowers their sessions, and making one never finds a session already raised. Why the browser: an MCP or CLI session may be driven by an agent, which can call any verb the session sees, so no MCP-callable path completes a raise. An agent with the link alone gets nowhere without a browser signed in to the person's GitHub account and their click on Kolab's page, which the `admin-session-raised` alarm then reports. Someone at the person's own unlocked browser, already signed in to GitHub, could complete it with a pick and a click; the alarm reports that too.
- **Never an agent.** An agent's sign-in token never carries `konjir-admin` or `admin`: an agent is never made an admin, its session is never raised (asking for a raise refuses it, so does completing one, and KonjirAuth checks the actor is a person on every request, whatever `admin_until` says), and it sees no admin verb.
- **The break-glass token.** `KONJIR_ADMIN_TOKEN` (or `--admin-token`) still runs every admin verb, as `admin`. Each request with it logs a warn line, `event: break_glass_used`, which the `break-glass-used` alarm emails (see *Logs and alarms*), and each admin verb it runs is in the audit log as `break_glass.used`, its subject the verb, whether it succeeds or not. `KONJIR_ADMIN_TOKEN=off` (or `--admin-token off`, in any case and with any surrounding whitespace, so a hand-written `Off` never becomes a guessable token) disables it. `konjir serve` refuses a token holding whitespace, and, with a public host, one shorter than 32 characters (`rotate-admin-token` writes 44). Disabled, no token is the break-glass, and the last live admin can be neither removed nor archived (`admin_remove_admin` and `admin_archive` refuse, under the access lock, so two admins removing each other at once leave one). Only an admin who can sign in counts as one left: a live admin with a linked GitHub identity, since one without could never raise a session (`admin_list_admins` says `signs_in`). On the test server it lives in SSM outside Terraform: `deploy/konjir-ops.sh rotate-admin-token` writes a new one and restarts Kolab, and `rotate-admin-token --off` disables it, but only after asking Kolab, with the token still in place, that such an admin exists; `--off-without-an-admin-who-signs-in` disables it anyway (see *Deploying to AWS for testing*).
- **Bootstrap, once.** Lee makes himself the first admin with the break-glass token, then works as himself:

  ```
  export KONJIR_URL=https://kolab.konjir.com/mcp
  KONJIR_TOKEN=$(deploy/konjir-ops.sh admin-token) bin/konjir admin_make_admin actor=icedlee337
  bin/konjir login                     # sign in with GitHub, and choose Yourself
  bin/konjir admin_elevate             # prints raise_url: open it, sign in with GitHub, confirm on Kolab's page
                                       # then 15 minutes of admin verbs, as icedlee337
  bin/konjir admin_apply_ruling ruling=D69 actor=… node=… elements=…
  deploy/konjir-ops.sh rotate-admin-token   # retire the token that bootstrapped
  ```

### Signing up and in

A person signs up and signs in with GitHub, so their first session needs no admin (D55). Kolab is an OAuth 2.1 authorization server for its MCP endpoint and the web interface, following the MCP authorization spec for remote servers, with GitHub as the upstream identity. Other identity providers can be added behind the same interface, `IdentityProvider` (`apps/server/src/oauth/identity.ts`); tests use `StubIdentity` in GitHub's place.

- **Discovery.** `/mcp` answers a request without a valid token with 401 and `WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource/mcp"` (RFC 9728), which @onivoro/server-mcp sends. That names Kolab itself as the authorization server, whose metadata, `/.well-known/oauth-authorization-server` (RFC 8414), lists `/oauth/authorize`, `/oauth/token`, `/oauth/register` and `/oauth/revoke`. The issuer is Kolab's origin: `https://<public host>` behind the TLS proxy, or the loopback address a request names. Without an identity provider none of it is served. The protected-resource metadata lists no `scopes_supported` (D59): an MCP client asks with the scope its own configuration gives only when the resource names none (the MCP SDK's scope selection, which OpenCode follows), and a harness's configured scope is how `konjir connect` preselects the agent, kolab and role at consent. Kolab requires no scope of a client.
- **Clients** register themselves (RFC 7591), as public clients with no secret: `none` is the only token endpoint authentication, and PKCE stands in for a secret. A redirect URI is https, or http on a loopback address, on a host that is a DNS hostname, an IPv4 address or an IPv6 literal (never `a_b` or `a;b`, which a URL may hold but a CSP source can't); never an app's own scheme, and never one with a fragment or credentials. One given at authorization must be such a URI and match a registered one exactly, but for a loopback URI's port (RFC 8252 §7.3). Kolab redirects nowhere before the person has seen the consent page: an unknown client, an unregistered redirect URI, a missing or plain PKCE challenge, another response type or another resource each gets a page saying so, since anyone may register a client with any https redirect URI (RFC 9700 §4.11.2). A client never used is deleted a day after it registered, and one unused for 30 days with no live grant then too. The web interface is Kolab's own client, `konjir-web`, never registered, whose only redirect is its own callback. Client ID Metadata Documents, which spec 2026-07-28 prefers to registration, aren't accepted yet.
- **Authorization code with PKCE**, S256 only. A `resource` other than Kolab's own `/mcp` is refused (`invalid_target`). Kolab signs the person in at GitHub as an OAuth client of its own, with a state and a PKCE verifier of its own, both bound to the browser by an `HttpOnly`, `SameSite=Lax` cookie (`__Host-konjir_oauth_<id>`, `Secure`, `Path=/`, behind the TLS proxy, so no other host under the domain can toss one in; `konjir_oauth_<id>`, scoped to `/oauth`, on loopback), so GitHub's answer counts only in the browser that asked, with the state it was given; both are checked before GitHub's code is redeemed. Each sign-in has a cookie of its own, named by its id, a random value that isn't secret (the cookie's value, the binding, is): the id rides in the state sent to GitHub, `<id>.<state>`, and in the consent form, so two sign-ins in one browser, an MCP client's beside the web page's say, never overwrite each other's, and allowing or denying one clears its cookie alone. A sign-in, and its cookie, last 20 minutes. At most 10 are open in one browser at once: a new one always goes ahead, and at the cap the oldest are let go to make room, so no other site, sending the browser to `/oauth/authorize` again and again, can lock its person out. A sign-in that is over lets its cookie go: cancelled at GitHub, allowed, denied, or found expired or used. A sign-in that can't go on says why: it expired (and how long one lasts), it was already used, or it didn't start in this browser, or the browser let it go for newer ones. An expired one is kept 2 hours as a tombstone, its keys and times only, so a late form can be told so; the form's token is found by an index of its own (migration 0020). GitHub's answers and consent forms are limited like authorizations, 30 a minute from one address each, counted before anything is looked up. GitHub is asked for no scope, so the token it gives reads public data only, as long as the OAuth app only ever requests no scope: GitHub gives a request without a scope the scopes the person already granted the app, so the app must stay dedicated to this sign-in. Kolab reads only the user's id, login and name, then drops the token: it is never stored, logged or passed on (DEL4), and not revoked, since revoking a person's only token of the app removes their authorization, and GitHub would ask them to authorize Kolab at every sign-in. An OAuth app's tokens don't expire on a timer; GitHub keeps at most 10 per user and app, revoking the oldest past that. Then the person consents on Kolab's page, which runs no script, loads nothing from elsewhere and can't be framed, with a form token of its own, from Kolab's own origin only. Its forms post only to Kolab, and their `form-action` names the client's redirect URI too (its origin, port and all; for an IPv6 literal such as `[::1]`, which a CSP source can't name, the scheme alone, which is broader, but the page's one form posts only to Kolab, whose 303 goes only to the sign-in's own redirect URI), since a browser holds the 303 that follows a form to it: under `form-action 'self'` alone, Chromium blocked the redirect to an app's loopback listener, OpenCode's say, after the consent had gone through. The client's `state` comes back to it, with the issuer in `iss` (RFC 9207).
- **Sign-up.** A person is their GitHub identity, by GitHub's numeric user id, never their login, which can change hands. The first sign-in makes a person and their user account, named after the login, lowercased. If a live or archived account or actor holds that name in any case (D52), the name tried next is `<login>_2`, then `_3` and so on: a GitHub login never holds `_`, so no variant is someone else's login. `kolab`, `admin`, `root`, `system`, `support` and the like, and anything starting `konjir`, are reserved, and sign up as `gh_<login>`; so does a login that reads as an existing person's agent, `<person>-<label>` (`lee-claude` while `lee` exists), so no one passes for someone's agent or takes the name their agent would have; the same goes for an organization's (`acme-bot` while the organization `acme` exists). Whoever takes a name first keeps it: a person `lee-claude` who signed up before `lee` stays a person, shown as one with no owner, and `lee` choosing the label `claude` is refused, saying so, to choose another. Nobody is matched by name: an admin links an existing person to their GitHub identity with `admin_link_identity actor=lee provider=github subject=<GitHub user id>` (`gh api users/<login> --jq .id`), so their first sign-in reaches them. An archived person doesn't sign in.
- **Consent.** The person chooses who the client works as, in which kolab and role. An MCP client works as an agent of theirs by default (D30): one they have, or a new one, `<person>-<label>`, at most 10 of them, and 3 in 10 minutes. If it has no grant in the kolab, it gets what its owner holds there, at most Write, on the layers its owner writes, in any kolab the person reaches by owning it, a grant, a team or their organization, an organization's included (D56). That grant stands, but never above its owner: an agent's access is cut down to its owner's on every use (D30), so it follows the person's access down, and ends with it. A kolab the person reads only because it is public gives their agents nothing, and no grant is stored there. The database holds to that on every use too: `kj_access` cuts an agent down to `kj_agent_cap` (0018), its owner's access without what visibility alone gives, so an agent whose owner's team or grant goes, leaving only a public kolab's Read, holds nothing there, and its session ends. A grant someone else gave the agent stands as it is. The agent cap, and the rate of 3 agents in 10 minutes (counted in the database, by `actor.created_at`, so every process counts the same), are checked and the agent made under the access lock, and a consent form claims its sign-in before it makes anything, so two submissions at once make one agent or kolab. Or the client works as the person themselves. The web interface is for people, so it always works as the person. The kolab is one they can reach, or a new private kolab of their own, with D54's limits but the Write-where-you-work one, which someone new can't meet (D56). The consent page shows where the client gets its answer, since a client's name is its own say-so. The scope a client asks with may preselect the choices (D59): `kolab:<name>` and `role:<role>`, and who it works as, `agent:<id>`. Each word only preselects, and only a choice the person signing in has anyway: a kolab they can't reach, or an agent that isn't a live agent of theirs, is ignored, never shown, and the page's own default stands; the web interface's own sign-in takes no `agent:`. No client preselects the person (D60): `as:self` is ignored from every client, loopback or hosted, since it would turn the safe default (an agent, capped at Write) into the person, with all their access; the person chooses Yourself by hand, and the page says under it that doing so ends any other session they hold open. A client with no such fallback in its MCP SDK (scope from its own configuration when the resource lists none) gets no preselection, and the page's defaults stand. The person confirms on the page, and the form is checked as before, whatever the scope said. A scope that names all three, `agent:<id> kolab:<name> role:<role>`, as `konjir connect` writes it, locks the page to them instead (D97; `scopeLock`): the page shows that agent, kolab and role alone, as fixed fields, with no list of agents, no new agent and no Yourself, so nothing on it can sign in anyone else, and Kolab refuses a consent posted for it that names any other actor, kolab or role, or none, saying so on the page again (`Kolab.consent`). If the agent isn't a live agent of the person's, or the kolab isn't one they reach, the page names neither and offers only Deny. Its title and heading name the agent, and "agent N of M" when the request says which of several sign-ins it is: `step` and `steps` on `/oauth/authorize`, kept only when both are whole numbers from 1 to 99, `step` no more than `steps`, and only from a client whose registered redirect URIs are all on the person's own machine (http on `127.0.0.1` or `[::1]`, as konjir's are), and otherwise ignored: from a hosted client, "agent 2 of 2" would dress a lure up as a setup the person started. They are display only, kept apart from the scope (`oauth_request.step` and `steps`, migration 0028), so they grant nothing. A scope naming fewer of the three only preselects, as above, and the web interface's own sign-in is never locked.
- **Tokens.** An access token is a session token: it opens the same one-actor, one-kolab, one-role session (ENF4, ENF5), so every check, row-level security's included, applies to it unchanged. It lasts 15 minutes. A grant's session keeps its id, the key `whoami` and events give, while its access token rotates: `session.token_key` is the sha256 of the current one and `session.expires_at` its expiry. A refresh token (`kjr_…`) lasts 30 days past its last use, and is used once: each refresh issues the next. One presented again within 10 s is taken for a concurrent request and refused; later, for a replay, which revokes the grant. A code (`kjc_…`) lasts 60 s and is used once; used again, it revokes the grant it opened. Kolab stores the sha256 of every token, code, state and form token, never the thing itself (P1). The newest sign-in for an actor wins: opening a grant's session ends the actor's other open session (ENF4), and tells its streams (D41).
- **Expiry in the database too.** Row-level security finds the session through `kj_session_id()`, which reaches a grant's session only by its current, unexpired access token, and a hand-issued one by its id until it expires. So a rotated or expired token reaches nothing, in Kolab or under `kj_agent`. The session helpers use it (0018), each a security definer function with its search path pinned.
- **Revocation.** `/oauth/revoke` (RFC 7009) takes a refresh or access token: the grant is revoked and its session ends, so its streams close (D41). So do signing out of the web interface, `admin_end_session`, and a session losing its access. A listen stream, and a web page's event stream, live as long as the access token they opened with: once it expires or a refresh rotates it, the stream closes before anything more is signalled to it, checked before each signal and, for listen streams, every 30 s, and the client listens again with its refreshed token. `/oauth/revoke` takes only a token issued to the registered client that names itself (RFC 7009 §2.1).
- **The transition.** Hand-issued session tokens (`admin_open_session`, `deploy/konjir-ops.sh connect`) keep working beside OAuth's, until `KONJIR_HAND_ISSUED_TOKENS=off` turns them off on `/mcp` and in the web interface. Each expires (W2.22): 30 days after it is issued, or `KONJIR_HAND_ISSUED_TOKEN_DAYS` days (more than 0, at most 365). `admin_open_session` returns `expires_at` with the token, and `connect` prints it. An expired token is refused like an ended session's, by Kolab, its listen streams and row-level security alike (`session.expires_at`, which `kj_session_id()` reads), and opening a new session for the actor ends the expired one, so it holds no place (ENF4). Moving a hand-issued session to another kolab or role in the web interface keeps its expiry. A hand-issued session opened before migration 0026 had none: the migration gives each one still open an expiry 30 days after it runs, so the deploy starts their clock. The break-glass admin token works either way. `KONJIR_GITHUB_CLIENT_ID` and `KONJIR_GITHUB_CLIENT_SECRET` turn GitHub sign-in on for `konjir serve`; the OAuth app's callback URL is `<origin>/oauth/callback/github`. With it on, the web page offers only *Sign in with GitHub*, unless `KONJIR_WEB_TOKEN_SIGN_IN=on` (for development) keeps pasting a token; without it, pasting a token is how one signs in, as before.
- **Not yet.** A person can't list or revoke their grants in the web page, only sign out of it, nor remove someone's access there once an invite is accepted; and an invite is a link, not an invitation to a GitHub login or an email address. Rate limits are per process: 10 registrations an hour from one address (500 in all), and 30 authorizations a minute from one address, counted only once the client and redirect URI check out, with no total and no limit per client, whose id is public, so no few addresses can lock everyone out. An IPv6 address counts by its /64; a request with no address to count by is refused. A refused request spends nothing. Behind the TLS proxy the address is the last `X-Forwarded-For` entry, which Caddy writes.

### Onboarding with no admin

A person's first session needs no admin (W3.4; P15, D55). They sign up with GitHub and make their first kolab on the consent page, connect a harness with one command, and invite a teammate with a link.

- **A first kolab.** Someone new, with no kolab and no invite, makes a private kolab of their own on the consent page (D54, D56), its short name filled in with theirs when that is a kolab name. An empty kolab's first page says what to do first: connect a harness, invite a teammate, write the spec.
- **Connecting a harness**, the web page's *Connect a harness*, by two routes shown apart, after `konjir connect` (below), which for Claude Code sets up the Konjir channel (W3.8). Over MCP: Claude Code with `claude mcp add --transport http konjir <origin>/mcp`, or OpenCode with an `mcp.konjir` entry of `{"type":"remote","url":"<origin>/mcp"}` in `opencode.json` and `opencode mcp auth konjir` (each signs in on Kolab's page, as an agent of the person's by default), then the agent calls `konjir_instructions`. In a shell: the konjir CLI, with `konjir login --url <origin>/mcp [--kolab <name>] [--role product|engineer]`. The page shows `npx <spec> …` only when the server names the published package, pinned to an exact version, with `KONJIR_CLI_NPM_SPEC=konjir@<version>` (`GET /api/session/cli` gives it, or null; `konjir serve` refuses a spec that isn't pinned). Until then `konjir` isn't on npm, and an `npx konjir` would run whatever someone else published under that name, so the page shows a checkout's `~/kolab/bin/konjir …` instead, with the clone to make, and says npm publishing is pending. `konjir login` is an MCP client like any other (`@konjir/login`, in `libs/login`, which the channel bridge shares): it registers itself as a public client with the loopback redirect `http://127.0.0.1/callback`, listens on a port of its own on 127.0.0.1 (RFC 8252), opens the browser at Kolab's sign-in with the kolab and role preselected, and takes only the answer that carries its own state. It keeps its registration and tokens in `$XDG_CONFIG_HOME/konjir/credentials.json` (`~/.config` by default, or `KONJIR_CREDENTIALS`), keyed by the MCP URL: the file 0600, and konjir's own default folder 0700 (tightened if it already existed); a folder named through `KONJIR_CREDENTIALS` is never changed, only warned of when others may write in it. Each write is a new file of a random name made with O_EXCL, moved into place. A file konjir can't parse is never overwritten; konjir names it and stops. Every later `konjir` command with no `KONJIR_TOKEN` uses it, the MCP client refreshing the access token as it expires; `konjir watch` listens again when its stream closes at the token's expiry, backing off (1 s, doubling to 30 s) while streams keep closing at once. Several konjir at once share it safely: every write takes a lock file beside it (O_EXCL, holding its owner's random id, refused if it is a symbolic link), which its holder touches every 10 s, for at most 30 s a hold, and others break only once it is 30 s untouched, by moving it aside and checking it is still the stale one; a holder re-reads the lock before it saves or lets go, so one whose lock was broken while it stalled keeps the tokens another konjir saved rather than writing over them. Waiting for a lock that can't be read or removed ends, by its deadline, in an error naming the file. A refresh holds the lock from reading the refresh token to saving the next, a request refused while another konjir refreshed waits for the lock and is sent again with the new token, and tokens are forgotten only if they are still the ones that failed. A sign-in that ended or was revoked says to run `konjir login`. `konjir login` keeps the sign-in it replaces, working, until the new one succeeds, then revokes it. `konjir logout` reads, revokes and forgets under the lock. `konjir logout` revokes the refresh and access tokens at Kolab's own `/oauth/revoke` and then forgets them; if Kolab can't be reached or refuses, the sign-in is kept and logout fails, saying so, unless `--forget` drops it anyway, unrevoked.
- **`konjir connect opencode|claude`** (W3.7, D59; `apps/cli/src/connect.ts`): one command connects a harness to a kolab, one agent per entry: `[--kolab <k>] [--agent <label>[:<role>]]… [--global] [--force] [--force-path] [--yes] [--no-auth] [--url <origin>]`, by default `--agent product --agent engineer`. It works as the person, and keeps no sign-in as them: a `konjir login` sign-in that is already the person's is used and left as it is; otherwise (none, or one that works as an agent, which stays untouched) it signs in in memory only (`ephemeralLogin`, its scope preselecting only the kolab; the terminal tells the person to choose "Yourself" by hand under "Work as", since no client may preselect it, D60), never writing it to `credentials.json`, and revokes it as soon as the agents are made, before it writes anything or any harness signs in. If the person chooses an agent there instead, connect revokes that sign-in at once and stops, saying to run it again and choose Yourself. `KONJIR_TOKEN` or `--token` must be the person's; an agent's is refused, saying so. It makes or reuses each agent up front with the person-only verb `konjir_create_agent label=<label>`: `<person>-<label>`, within D56's limits (10 live agents a person, 3 made in 10 minutes, counted in the database under the access lock), reused if it is a live agent of theirs, and refused for an agent's session, the admin token, a bad label, or an archived agent of theirs. Any other name not free to them is refused with one message, `the name <id> isn't available`, whoever holds it, so the verb probes nothing; that includes another account's namespace: a person or organization whose name starts `<person>-` owns `<their name>-*`, so `ann` can't make `ann-x-pm` while `ann-x` exists (the mirror of sign-up's rule). `konjir_archive_agent label=<label>` archives an agent of their own, ending its sessions and freeing its place under the cap; its name stays its own. It grants nothing: the agent gets its access at consent, what its owner holds, at most Write (D30, D56). Each agent gets an MCP entry, `konjir-<label>`, whose OAuth scope, `konjir kolab:<k> role:<role> agent:<person>-<label>`, locks Kolab's page to them (see *Consent* above). Nesting past 512 levels, or a file OpenCode can't parse, is refused. Claude Code's goes into the project's `.mcp.json`, by default as the Konjir channel bridge (W3.8, D61; see *Pushing the inbox into a Claude Code session*), Claude Code's one Konjir server: a stdio server as `claude mcp add --scope project` writes one, `{"type":"stdio","command":"<checkout>/apps/channel-bridge/scripts/start.sh","args":[],"env":{"KONJIR_URL":…,"KONJIR_TOKEN":"","KONJIR_AGENT":"<person>-<label>","KONJIR_SCOPE":"konjir kolab:<k> role:<role> agent:<person>-<label>"}}`, the bridge of the checkout this `konjir` runs from, proven from the CLI module's own place: it must sit at `<root>/apps/cli/src` (or `dist`) of a git checkout whose `package.json` is the `kolab` workspace, with the `konjir` and `@konjir/channel-bridge` packages where they belong, never a path relative to wherever `konjir` was installed. One that runs from elsewhere, such as the npm package or a binary, has none, even beside a planted `channel-bridge/scripts/start.sh`, and says to run a checkout's `bin/konjir` or pass `--http`. The entry names that checkout's absolute path, so it works only on that machine: don't commit it, or use `--global`. `--http` writes Claude Code's plain HTTP entry instead, for people who don't want channels: `{"type":"http","url":…,"oauth":{"scopes":…}}`, as `claude mcp add --scope project --transport http` writes it. A new file is written whole, and an existing one edited in place the same way, keeping its formatting and numbers (one that isn't plain JSON is refused); with `--global`, Claude Code's own `claude mcp add-json --scope user` writes it, after konjir reads `~/.claude.json` to refuse an entry already there. Every merge is checked before it is written: the result must parse, read as the file before with just the entries set, and keep every comment, or nothing is written. It shows a diff (or the commands) and asks first, `--yes` skipping that in a script and needed without a terminal; refuses an existing `konjir-<label>` entry unless `--force`; refuses a config file that is a link outside the project (or, with `--global`, the config folder) unless `--force-path`, even with `--yes`, and a link to nothing always; writes atomically, to a new file beside it then moved into place, keeping its mode, and only if the file hasn't changed since it was read; refuses a `--url` with a user name, password, query or fragment; and writes no token anywhere. Then it runs `opencode mcp auth konjir-<label>` for each entry, one at a time, or prints the steps (Claude Code's `/mcp` with `--http`, or with `--no-auth`). For a Claude Code channel entry it signs the entry in itself, one at a time, in the browser, as `konjir login` does but registered as `konjir channel (Claude Code)`, with the entry's scope locking the page to its agent, kolab and role (never Yourself, D60) and, when there are several entries, the page saying "agent N of M" (`step` and `steps`), and keeps that sign-in in the agent's own credentials file, `agents/<person>-<label>.json` beside `credentials.json`, where the bridge started with `KONJIR_AGENT` finds it; the CLI's own sign-in is untouched. A sign-in that works as anyone but that agent (another chosen on the page of a Kolab from before the lock) is forgotten and revoked, and konjir asks again for the same agent at once, saying so, at most twice more, before it goes on to the next entry (D97); after three, the entry counts as not signed in. Only channel entries get "agent N of M" and asking again: an OpenCode entry, or Claude Code's `--http` one, is signed in by the harness itself (`opencode mcp auth`, `/mcp`), which sends no `step` and tells konjir only whether it finished, so its page is locked to its agent but says no "N of M", and a wrong sign-in there isn't asked again. konjir manages `agents/` itself, wherever `KONJIR_CREDENTIALS` points: it makes it 0700 (tightening a looser one), and refuses one that is a symbolic link or belongs to someone else. Then it prints how to start Claude Code with the channel: `claude --dangerously-load-development-channels server:konjir-<label> …`. Channels need Claude Code signed in with a claude.ai account, not an API key; without one the tools still work, and no channel messages arrive. - **Invites** (*People*, for those with Admin in the session's kolab): an invite is a link, `<origin>/#/invite/kji_…`, shown once. Whoever signs in with it, as a person, is granted its access in that kolab, once: Read, Triage, Write on one layer or both, or Maintain, never Admin, which the kolab's owners give. It lasts 7 days, until it is accepted, or until an admin of the kolab revokes it, and it counts only while whoever made it still holds Admin there, so an admin who loses Admin takes their open invites with them. An archived kolab's invites are no good (D52). Accepting always writes the person's own grant there: their direct grant, if any, raised to cover the invite (the higher level; at Write, the layers of either), so it never lowers a grant and never leans on what reaches them only through the kolab being public, a team or a base permission, and their agents may borrow it (D56). In an organization's kolab, someone who isn't a member becomes an outside collaborator (TEN10). An agent never accepts one: it gets its access from its owner (D30, D56). Accepting runs under the access lock, as any change of access does, and the invite row is locked, so one is accepted once however many people try at once; at consent it is the same transaction that issues the code, so a sign-in that fails uses up nothing. A kolab holds at most 50 open invites and a person makes at most 20 an hour, counted in the database under the access lock. Kolab stores only an invite's sha256 (P1), and `kji_` tokens are masked in logs like every other secret. A refused invite says only that it is unknown, used, revoked or expired, or that its maker can no longer invite.
- **Who holds access** (*People*, W3.6, for a person with Admin in the session's kolab, `Kolab.listAccess`): everyone who holds access there, people and agents, with what they hold now (`kj_access`) and every source of it: owning the kolab, being an owner of the organization that owns it, the organization's base permission, an internal kolab's members' Read, a direct grant (an outside collaborator's, in an organization's kolab, when they aren't a member), or a team's grant, nested teams included. An agent shows its own grant beside what its owner lends it (`kj_agent_cap`), and is marked capped when that takes something away (D30, D56). Someone whose direct grant gives nothing now, such as an agent whose owner lost access, is listed too, so it can be removed. Teams' grants are listed apart, with how many people each reaches. A public kolab's readers, everyone, aren't listed. Only a direct grant is changed here: *Change* (`Kolab.changeGrant`) to another level and its layers, and *Remove access* (`Kolab.removeGrant`), each confirmed in the page first. Access from owning the kolab, its organization, the base permission or a team is shown, saying where it is changed: today, by Konjir's admin (`admin_grant` to a team, `admin_add_member`, `admin_remove_team_member` and the like). Kolab's rules, not the page's: only a person with Admin, whose session and Admin are both checked again in the changing transaction; never the last person with Admin (an agent with Admin doesn't count; this path's rule only: an organization's owners, archiving and teams don't check it); Admin given, and a granted Admin lowered or removed, only by the kolab's owners (its owner, or an owner of the owning organization), though anyone may step down from their own; new people come in by invite; an agent's grant only lowered (to any level at or under it) or removed, since raising it is its owner's, at most Write (D56), which signing the agent in does again after an Admin lowered it, and the page offers an agent no higher level; an archived actor's grant only removed (D52). An unknown actor is refused exactly as a known one with no grant there, so no Admin learns who has signed up. The list is one read-only snapshot, and names no agent's owner who holds nothing there. Each change runs as every change of access does (`changeAccess`): under the access lock, held exclusively, with the kolab checked live (D52), and in the same transaction the person's and their agents' links and forks into kolabs they no longer read are marked `access_lost` (D53), and every session that can no longer reach its kolab ends, agents' included, its streams told (D41). Removing a person's grant caps their agents with it, since an agent holds no more than its owner on every use. Two admins removing each other at once are serialized by the lock: the second no longer holds Admin and is refused.
- **Opening a link.** The secret rides in the URL's fragment, which no request carries; the page takes it out of the address as soon as it reads it. The page posts it to `POST /api/session/invite`, from Kolab's own origin, 30 a minute from one address (an IPv6 /64), which says what it offers and keeps it in an `HttpOnly`, `SameSite=Lax` cookie for 30 minutes: `__Host-konjir_invite` behind the TLS proxy (`Secure`, `Path=/`), `konjir_invite` scoped to `/oauth` on loopback. Only `/oauth/authorize` reads it, and only for the web interface's own client, `konjir-web`, never a registered MCP client; the consent page then offers to join that kolab, saying who invites and with what: chosen already for someone with no kolab yet, and otherwise for the person to pick. The page's kolab choices are `kolab:<name>`, `@new` and `@invite`, so a kolab may be called `new` or `invite`. Consenting accepts it and clears the cookie, and so do Decline, *Not now* (`DELETE /api/session/invite`) and signing out. A person already signed in joins with *Join* (`POST /api/session/invite/accept`), which grants the invite's access and moves their session there in the same role.

### Addresses

An address names its kolab: `kj:<kolab>/<node>[@<version>][#<element>][~q(<selector>)]` (ADR3, D8, DAT11). Inside a kolab the short form, `kj:<node>…`, is enough. `@konjir/address` parses and prints both, and nothing else does: the kolab segment is a kolab name (lowercase letters, digits and `-`), and a node's name is anything without `/`, `@`, `#`, `~` or whitespace, so the first `/` always ends the kolab.

- **A node's name is unique within its kolab**, not across Konjir, so two kolabs may each have a `checkout` and neither learns of the other. A name taken in the session's own kolab is refused, naming only that kolab. Migration 0008 adds `node.name`, unique per kolab (`node_kolab_name_key`); each existing node's name is its id.
- **The id is Kolab's own.** A node keeps the id every version refers to. A new node's id is its name, unless another kolab's node already holds that id, and then it is `~` and a ULID, which no name can be, since a name has no `~` (`node_id_name_check`). The id says nothing of the kolab, so renaming a kolab, if that ever comes, needn't touch it. Neither id nor name changes once written (`node_name_fixed`). Every verb takes a node's name, every address and message Kolab gives names the node by its name, and no verb shows an id.
- **The short form** is the node of that name in the session's kolab. Every read names its reader: `{ session }`, or `{ system: <kolab> }` for Kolab's own reads, which check nothing and may never stand in for a session.
- **The full form resolves from anywhere** its reader can read. In the session's own kolab it is the same as the short form. In another kolab, `konjir_resolve` and `konjir_read_node` (`node=<kolab>/<node>`) need the actor to hold Read there, as `kj_access` computes it: so an agent needs a grant of its own, never more than its owner's (D30), and a person may read a public kolab. Without it, the address is refused exactly as one naming a node or kolab that isn't there. `read_node` across kolabs prints full addresses, its own kolab's short ones.
- **Across kolabs, only committed work shows.** A reader outside a node's kolab sees its committed versions only, and of their questions only those people raised: none a mark raised (a boundary finding, or a ruling that changes the intent, D51), and none naming its mark or the element that asked (0016 holds `kj_agent` to the first). The same holds in a session's own kolab for a session that holds only Read there, which doesn't belong to its work (D49). It gets no mark and no mark's cause, since a mark's note can quote a ruling or the review gate's finding. It also gets no question a mark raised. It still sees the kolab's links, its review requests with their verdict notes, and a variant's rebase status (D58): only marks, their causes and the questions marks raised are held from it. That covers:
  - `konjir_list_stale`, `konjir_list_queries` and `read_node`
  - the inbox and answers resources, and a commit's `stale_after_commit`
  - the instructions
  - the web page's queue, threads, marks, overview counts and activity

  0022 holds `kj_agent` to it on `query`, `invalidation` and `invalidation_cause`, through `kj_session_belongs()` (Write on a layer, an agent capped by `kj_agent_cap`). Each of those paths reads as the session: `Kolab.queriesFor`, `Kolab.marksFor` (which picks the marks as the session, by layer and node there too, then describes them as Kolab, since an `access_lost` mark's trigger may be a version the session can no longer read), `readNode` and `views.ts`. Kolab's own writers (the cascade, `clear_mark`, the outbox, `access_lost`) run as the owner or `kj_system`, so 0022 doesn't touch them. What triggered a mark is named only to a session that reads it; otherwise `konjir_list_stale`, the inbox and the web page all say "a version in another kolab" (`markBecause`). Answering a question, or resolving an override, checks first that the session may do it, and another kolab's question or mark reads as one that isn't there, so its state isn't told to anyone else. Version numbers are the node's own, committed or not, so where drafts or rejected versions came between, a reader outside sees a gap (`v1`, `v4`): addresses carry the real number, so this is accepted. a pinned draft or rejected version (`kj:billing/checkout@3`) resolves as an orphan, and `read_node` says there is no such version, as for one that doesn't exist. Inside its own kolab a session reads drafts as before (ADR9). This reading is put to Lee.
- **Enforced twice.** Kolab checks Read first, then runs the read as `kj_agent` in the session, so row-level security returns nothing it shouldn't, even to code that skips Kolab's check. The one exception is `read_node`'s author: `kj_agent` reads no actors, so Kolab's login looks up who wrote the version, after the version itself was read under row-level security.
- **Writing stays in the session's kolab, but a link or a fork may reach out.** A question or a draft naming another kolab is refused from the address alone, saying it isn't supported across kolabs, without looking at what is there. A link's target and a variant's parent may be another kolab's committed version, wherever the session's actor holds Read (see *Links and forks across kolabs* below); anywhere else they are refused as a node that isn't there.

### Links and forks across kolabs

A link into another kolab (LNK8) and a fork, a variant of another kolab's spec (KON9), are made as any other: `konjir_link target=kj:billing/checkout#R1`, `konjir_draft parent=kj:billing/checkout@3`, and a draft's `unlink` removes one as any other (`link_removal.target_kolab_id`). Migration 0017 relaxes four of 0006's composite keys for them, and only those: an edge's target, a version's parent, an override's base and a mark's trigger. D53 settles the model.

- **Only committed work, and only with Read.** Another kolab's reference must name a committed version, for every role (`kj_kolab_ref_check`, checked after row-level security so an agent refused there learns nothing more). Kolab checks Read on the target's kolab, and row-level security repeats it for `kj_agent` (`edge_target`, `version_parent`, and `delta_base` for an override's base), inside the writing transaction under a shared hold on the access lock, so no revoke lands between the check and the commit.
- **A holder.** A link or fork across kolabs rests on one actor's access: `edge.held_by`, the actor who linked, and `version.parent_held_by`, the author who forked. The holder vouches for it while they hold Read on the other kolab *and* Write on the dependent's layer in its own, so someone who has left the dependent's kolab is no channel into it. A rebase, or a draft of the fork by someone who can't read the parent, carries the holder; someone who reads it and drafts, clears a mark, revises the element or links again becomes the holder.
- **`access_lost`.** When the holder no longer vouches for it, the dependent (a link's source element, or a fork's live version) is marked `access_lost`: in the transaction that changes the holder's access, which looks only at the links and forks held by the actors the change can affect (the grantee, a team's members, and the agents they own), and whenever the cascade meets the link. While it is open, the other kolab's commits reach neither the link (no marks, no re-pin) nor the fork (no rebase, no fold). It settles when the holder vouches again, when someone who reads takes it over with `konjir_clear_mark`, or when the link or fork goes. A settled link is checked against its target's latest version at once; a settled fork is caught up by a rebase job (0015) written in that transaction.
- **Locks.** Every transaction that takes both takes the access lock (shared) before a node's lock, and a change of access takes the access lock alone, exclusively, so none waits on another in a cycle (W1.17 still locks at most one node).
- **Each kolab's work is its own.** A commit owes each dependent in another kolab a rebase job of its own (0015): its links there checked, its fork rebased once its holder still vouches for it. One that fails backs off and retries on its own, the committer hears nothing of it, and a pending rebase never names the upstream kolab's version or its error.
- **Each kolab's rows stay private (D49).** The edge and its marks belong to the source's kolab, which the target's kolab never reads: `konjir_lineage` downstream shows only links from the reader's own kolab, and a mark spreads only within its own kolab (a mark's causes keep 0006's composite key), so the downstream kolab hears of an upstream change when it commits, not of the upstream kolab's own marks. A binding's layer leak against a spec in another kolab asks the binding's own layer.

Questions across kolabs stay refused.

- **Claude Code, with OAuth (D55):** `claude mcp add --transport http konjir https://kolab.konjir.com/mcp`, then `/mcp` in Claude Code to sign in with GitHub in the browser and choose its agent, kolab and role.
- **OpenCode, with OAuth:** add `"mcp": { "konjir": { "type": "remote", "url": "https://kolab.konjir.com/mcp" } }` to `opencode.json`, then `opencode mcp auth konjir` to sign in.
- **Claude Code, with a hand-issued token:** `claude mcp add --transport http konjir http://127.0.0.1:7420/mcp --header "Authorization: Bearer <token>"`
- **Any MCP client:** one that speaks MCP's authorization needs only the URL; otherwise, an HTTP server entry with an `Authorization: Bearer <token>` header.
- **Anything with a shell** (Codex, a person): `konjir login --url https://kolab.konjir.com/mcp` signs in with the browser, as an agent of yours (W3.4, *Onboarding with no admin*); or `export KONJIR_URL=… KONJIR_TOKEN=<token>`. Then `bin/konjir instructions`.

That one connection is the only static setup a harness needs. The rules come down the protocol. The server instructions tell an MCP session to call the `konjir_instructions` tool before its first change, for the full operating instructions, and `konjir_instructions which=reviewer` before reviewing: an agent connected only over MCP usually has no konjir CLI, and its client shows MCP prompts to the person, as slash commands, not to the model. The tool is read-only and idempotent; agents and people may call it, and the admin token gets the rules alone. The same texts are the resources `konjir://instructions` and `konjir://instructions/reviewer`, which are read, never pushed (`ListenScope` refuses a session's listen stream that asks for them, as for anything but its own kolab's inboxes and answers); the prompts `konjir_operating_instructions` and `konjir_reviewer_instructions`, for a person to invoke; and `konjir instructions` and `konjir instructions reviewer` in a shell. See *Review*. The web page's *Connect a harness* shows the two routes apart: over MCP (Claude Code or OpenCode, then ask the agent to call `konjir_instructions`), or the CLI (`konjir login`, then `konjir instructions`). `apps/cli/test/instructions.test.ts` checks that the tool and the resources give exactly the prompts' texts, with only the session's own kolab's precedent (for one actor in two kolabs too) and, for a session that holds only Read, no precedent and no question a mark raised (D49, D51), that `konjir instructions` takes `reviewer` or `which=reviewer`, that the resources can't be listened to, and that the server instructions name the tool first; `apps/web/test/onboarding.test.tsx` renders both routes. The served text includes the answered questions and override precedent of the session's own kolab, so settled questions aren't re-asked.

### Installing the konjir CLI

Outside a checkout, `konjir` is the client alone: every verb, `instructions`, `watch` and `--version`, but no `serve`, which runs Kolab and needs a checkout. It needs only a Kolab's URL and a token.

```
# From npm (Node 22 or later; the package has no dependencies). Pin the version:
npx konjir@0.5.0 --help                 # run it without installing
npm i -g konjir@0.5.0                   # or install it, then run `konjir`
# A Kolab sets KONJIR_CLI_NPM_SPEC=konjir@<version> so its web page shows the same npx commands.

# Or from a checkout:  git clone https://github.com/konjir/kolab ~/kolab && (cd ~/kolab && npm ci)
#                      ~/kolab/bin/konjir --help

# Or a single-file binary, which needs no Node, from the GitHub release:
#   konjir-linux-x64, konjir-linux-arm64, konjir-darwin-arm64, konjir-darwin-x64, konjir-windows-x64.exe
curl -fLo konjir https://github.com/konjir/kolab/releases/download/konjir%400.5.0/konjir-darwin-arm64
chmod +x konjir                         # each release also carries SHA256SUMS
xattr -d com.apple.quarantine konjir    # macOS: the binaries aren't signed

KONJIR_URL=https://kolab.example.com/mcp KONJIR_TOKEN=<token> konjir whoami
```

`apps/cli/scripts/package.mjs` builds both from `apps/cli/src` with [Bun](https://bun.sh). `apps/cli/bun-runtimes.json` pins Bun's version and the sha256 of each Bun release zip used. Each build checks that the `bun` on your PATH is that version, and `node apps/cli/scripts/package.mjs bun <dir>` installs a checked one. `npx nx run konjir:bundle` writes the npm package to `apps/cli/dist-npm`: the CLI and the MCP client SDK bundled into one `konjir.mjs`, a `package.json` that declares nothing else, `LICENSE` (konjir's own, Apache-2.0) and `THIRD-PARTY-NOTICES.md`, the bundled packages' licences, taken from Bun's metafile. `npx nx run konjir:compile` writes the binaries, `LICENSE` and the same notices, plus the Bun runtime's, to `apps/cli/dist-bin`. It compiles each binary with `bun build --compile` on a Bun runtime downloaded from Bun's release and checked against its pinned hash (`node apps/cli/scripts/package.mjs binaries darwin-arm64` builds one). Both builds leave out `@konjir/server`, so `konjir serve` from them says to use a checkout. Neither target is part of `build`, so the release Kolab runs, which `install.sh` builds with tsc, doesn't need Bun.

### Pushing the inbox into a Claude Code session

Kolab signals inbox changes over `subscriptions/listen`, but Claude Code doesn't hand those notifications to the model. The Konjir channel does: `apps/channel-bridge` is a stdio server, run by Claude Code from the entry `konjir connect claude` writes or from the Claude Code plugin `konjir-channel`, that listens to Kolab as the session's agent and forwards each change to its inbox (`konjir://inbox/{layer}`) or its answers (`konjir://answers/{actor}`) as a [channel](https://code.claude.com/docs/en/channels-reference) message. Each message says what changed and how to read it. It serves the 2025-era protocol by default, because Claude Code doesn't register a channel server that negotiates 2026-07-28; `KONJIR_CHANNEL_PROTOCOL=auto` serves both eras, for a client that isn't using it as a channel. It speaks to Kolab over Streamable HTTP on 2026-07-28, which `subscriptions/listen` needs, and reconnects when Kolab restarts.

It is also Claude Code's one Konjir server (W3.8, D61). It serves Kolab's own tools, resources and prompts, passed through on its one connection and sign-in: what Kolab lists, unchanged (names, descriptions, input and output schemas, annotations), read at each connection and again whenever Kolab sends `notifications/tools/list_changed` (or the prompts' or resources' own), which it passes on to Claude Code. Each list's reads run one at a time, in order, and a burst of changes while one runs costs one more read, so the latest read always wins. It adds no tools of its own. So the session's tool calls and its channel are one session, and one session per actor (ENF4) needs no relaxing: Claude Code's own HTTP sign-in as the same agent, which would end the bridge's session and be ended by it in turn, isn't needed. Each call goes to Kolab as it came (its name and arguments; Claude Code's `_meta` stays behind) and Kolab's result comes back as it came, encoded by the MCP SDK for whichever era Claude Code negotiated. A call is sent once. The MCP client sends it again only after Kolab answered 401, which Kolab gives before it runs anything: a token that expired or rotated mid-call, refreshed under the credentials file's lock (or found already refreshed by another konjir). A call that got no answer in time (2 minutes), lost its connection, or was cancelled by Claude Code after it was sent is never sent again, so a non-idempotent tool is never run twice by the bridge; the session is told it may or may not have run, and to check before calling it again. A call that was never sent (no connection, or cancelled first) says nothing was sent. A call goes out only on the connection live at that moment, registered in the same tick, and a connection being replaced (at token expiry, say) is closed only once every call on it is answered. While the bridge has no connection to Kolab, a call waits up to 15 seconds for one, then is answered with why, having sent nothing; Claude Code's first list waits up to 10 seconds for the first connection, and a list that arrives later is announced with `list_changed`. Errors keep Kolab's text, with every token masked as the bridge masks its log: Kolab's JSON-RPC errors pass on with their code, and an error result's text, or a transport error, is masked the same way.

It signs in as `konjir login` does (W3.5, D55), with no hand-issued token. With `KONJIR_TOKEN` unset or empty it uses the sign-in `konjir login` keeps for `KONJIR_URL` (default `http://127.0.0.1:7420/mcp`, matched exactly) in the same credentials file, under the same lock, through the same client (`@konjir/login`): the bridge and the konjir CLI share one sign-in, one grant and one session, so the bridge hears exactly the inbox and answers of the agent the CLI works as. With nothing kept, the bridge signs in by itself on first start: it opens the browser at Kolab's sign-in, registered as `konjir channel (Claude Code)`, and tells the session so in fixed words. The link stays in its log (stderr), never in the model's context, since it carries the sign-in's state and PKCE challenge. That sign-in is kept for the CLI too. One bridge signs in at a time: a marker lock beside the credentials file (`credentials.json.signing-in`), under which it checks again, under the credentials lock, that nothing was kept meanwhile; a bridge that finds the marker taken waits for that sign-in. A bridge sign-in that finishes after a `konjir login` kept one yields: the other is kept, and the bridge revokes its own new grant. The reverse, a `konjir login` that started before the bridge's sign-in and finishes after it, keeps the CLI's and leaves the bridge's grant unrevoked, to lapse within 30 days unused: the same as two `konjir login`s at once. `konjir logout --forget` drops a sign-in kept for an http URL to another host (from before the https check) without contacting Kolab, and says so. It signs in by itself only where a browser can open: not with `CI` set, not over SSH, and on Linux only with a display; `KONJIR_CHANNEL_SIGN_IN=off` turns it off too. Then it waits for `konjir login`.

Signing in, by the bridge or the CLI, takes Kolab's URL over https only, or http on this machine (loopback) for local development: over http to another host the network could read the 30-day refresh token and answer discovery in Kolab's place. The browser opens only Kolab's own `<origin>/oauth/authorize`, over https or loopback http, through `open`, `xdg-open` or, on Windows, `rundll32 url.dll,FileProtocolHandler`, with fixed arguments and no shell. A sign-in link Kolab's metadata points anywhere else (another host or path, `file:` or a custom scheme) is refused, and nothing is opened or printed. Every URL the bridge prints has no credentials and no query.

Its access token lasts 15 minutes, and Kolab closes a listen stream once its token expires or a refresh rotates it (API4). The bridge then connects again, with its usual backoff (back to the first step only after a stream that lived a minute), and the MCP client refreshes the token under the credentials file's lock, so a `konjir` command refreshing at the same moment never uses a refresh token twice. A connection that ends while a refresh is in flight leaves the refresh its lock; only an idle hold is let go, and the lock's 30 s maximum hold covers a leak. It re-reads its inbox and answers, so nothing that changed in between is lost. When the sign-in ends (revoked, lapsed, or replaced by a newer sign-in as the same agent), the bridge tells the session once to run `konjir login`. It never opens the browser again by itself. It checks the credentials file at its slowest backoff and goes on with the new sign-in, with no restart. `KONJIR_TOKEN`, when set, overrides all of it: a hand-issued agent session token, as before. If that isn't an agent session token, the bridge tells the session so once, and waits. It never prints a token: the token it was given, the sign-in's tokens as kept, and anything shaped like a Kolab secret (`kjs_`, `kjr_`, `kjc_`) are masked in its log and its messages. A bridge that can't start says so in fixed words, with the detail, masked, in its log.

One session per actor (ENF4) shapes the setup. The bridge listens and works as the agent its sign-in names, so the session's Kolab work goes through the bridge's own tools. Don't also add Claude Code's HTTP server (`claude mcp add … /mcp`) as the same agent: the newer sign-in ends the older one's session, and the two keep signing each other out. `konjir connect claude` gives each entry its own agent and keeps each agent's sign-in in a file of its own (`KONJIR_AGENT=<agent>` names `agents/<agent>.json` beside the credentials file; `KONJIR_SCOPE` preselects the agent, kolab and role when the bridge signs in by itself, `as:self` dropped), so two entries never share a sign-in, and the konjir CLI's own sign-in is apart from them. With `KONJIR_AGENT` set, a kept sign-in (or a `KONJIR_TOKEN`; the entries `konjir connect claude` writes set it empty, so one in Claude Code's own environment isn't passed on) that works as anyone else is refused whole, and any list served from an earlier connection is dropped, with `list_changed`: the bridge serves no tools and hears nothing, and tells the session once which command signs that agent in (`KONJIR_CREDENTIALS=<its file> konjir login --url <url> --agent <agent>`: `--agent` names the agent, and `konjir login` refuses, revokes and forgets a sign-in as anyone else, then asks again for that agent, at most twice more, stopping at once if a revoke failed, and its error lists every try's outcome); `KONJIR_SCOPE`'s `agent:` word must name that agent, or is dropped. The bridge's own browser sign-in that comes back as anyone else is revoked and forgotten. A `konjir login` as one of those agents would end that entry's session, so use the CLI as another agent of yours, or with `KONJIR_CREDENTIALS` naming the agent's file. Started from the plugin, with no `KONJIR_AGENT`, the bridge shares the sign-in `konjir login` keeps, as before.

The simplest setup is `konjir connect claude` from a checkout (see *Onboarding with no admin*), then `claude --dangerously-load-development-channels server:konjir-product server:konjir-engineer`. The plugin works too. The bridge runs in place from a Kolab checkout, so run `npm install` there first, and install it only from that checkout's local path. A marketplace added from GitHub copies the plugin into Claude Code's cache, away from the workspace's packages, and the bridge won't start. Channels are a research preview and this one isn't on Anthropic's allowlist, so it loads with the development flag, in an interactive session (`-p` ignores the flag). Never give it the admin token that step 2 exports: if you set `KONJIR_TOKEN`, set it on the `claude` command itself, or start from a fresh shell.

```
# One command, straight from the checkout. On first start the bridge opens your browser to sign in to
# Kolab with GitHub, as an agent of yours; later sessions, and the konjir CLI, use that sign-in.
KONJIR_URL=https://kolab.konjir.com/mcp \
  claude --plugin-dir ~/github.com/konjir/kolab/apps/channel-bridge \
  --dangerously-load-development-channels plugin:konjir-channel@inline

# Or sign in first with the CLI (choosing the agent, kolab and role), then start Claude Code as above:
~/github.com/konjir/kolab/bin/konjir login --url https://kolab.konjir.com/mcp --kolab <name> --role product   # npx konjir only once published, pinned

# Or install it from the checkout's marketplace (local path only), then start sessions with the plugin:
claude plugin marketplace add ~/github.com/konjir/kolab
claude plugin install konjir-channel@konjir
KONJIR_URL=https://kolab.konjir.com/mcp claude --dangerously-load-development-channels plugin:konjir-channel@konjir

# With a hand-issued token instead (it overrides any sign-in):
KONJIR_URL=http://127.0.0.1:7420/mcp KONJIR_TOKEN=<the agent's session token> \
  claude --plugin-dir ~/github.com/konjir/kolab/apps/channel-bridge \
  --dangerously-load-development-channels plugin:konjir-channel@inline
```

Choose **I am using this for local development** at the warning. Work already waiting arrives first, as one `← konjir: Your functional inbox already holds …` message. Each new question, note, mark, answer, review request or case file after that arrives as `← konjir: Your functional inbox changed: …`, and a verdict on a version the session submitted as `← konjir: A version you submitted has been reviewed: …`. Items leaving the inbox, such as the agent's own answers and clears, send nothing. The plugin loads in place from a marketplace added from a local path, so it keeps using this checkout's `node_modules`. On Team and Enterprise plans an admin must enable channels first.

## The web interface

Kolab serves a web interface at its root, `https://kolab.konjir.com/` on the test server (W3.1, API8). It is a React and Vite single-page app in `apps/web`, built to `apps/web/dist` by its Nx `build` target, and served by the same NestJS process as `/mcp`. A product owner can do there what the [Konjir Kolab prototype](https://claude.ai/artifact/99doLyY9QFgZZkENDb4GNa) simulates, against the real server:

- **Read a spec** (or any node of the kolab) with its questions and notes beside each element, open and answered, from any version (Q5), the links each element relies on and is relied on by, and its versions. A version in review, or an older one, shows its changes word by word against the version before it.
- **Answer** a question, or reply to a note, that the session's layer owns; **ask** a question or **leave a note** about an element or a node (Q1, Q3). Questions route to the layer that owns the answer.
- **See what's stale:** each mark beside its element, with the text it was written against and the text now, and settle it as its owner: *Still holds* (`clear_mark`), revise the element, or for a variant's override, rule on it: keep ours, adopt the parent's, or amend (`resolve_override`, OVR8), which becomes precedent (LNK6, OVR9).
- **Edit and submit:** edits, and links dropped (*unlink*, which settles their marks when the version commits), stay in the page as a draft until *Submit for review*, which drafts the node's latest version with them and submits it. A draft that fails Kolab's structural checks is abandoned at once and the page keeps the edits to fix. A draft that came back with changes requested can be resubmitted or abandoned.
- **Review:** a version waiting for the session's actor shows *Approve* and *Request changes* (with a note), the same verdicts as `konjir_review`.
- **Case files and rulings** (W3.2; CASE1–CASE7, D49, D51): open a case file on an element (*Dispute*: the question, a claim, its evidence and the side it takes), take the other side, and, as a person with Write on the element's layer from its role who isn't a party, rule on it, sustaining exactly one position. Or rule directly (*Rule*) on an element or a whole node, which supersedes any case file still open on the element. Each ruling shows beside the element it rules on, from any version, as precedent; one that changes the intent marks the element (*ruled*), which only a version amending it settles. The **Cases** page lists the open case files, the kolab's rulings, newest first, and the settled case files. Only those who belong to the kolab's work (Write on a layer of it) see any of it, and the page offers each action only to whom Kolab would allow it (`WebCase.you`); Kolab decides.
- **Reading another kolab in place** (D49): *Read here* on another kolab's card, or an address in *Go to an address* (`kj:<kolab>/<node>[@<version>][#<element>]`), reads its committed versions, with their elements and questions, read only, without leaving the session's kolab. Only nodes with a committed version are listed; one with none is refused as one that isn't there. Its drafts, versions in review and rejected versions, links, marks, reviews, case files and rulings never show, nor questions a mark raised. A kolab the session can't read, a node that isn't there and a version that isn't committed are refused alike, saying nothing of which. Working there takes *Open* (a session there).
- **Lineage** (what depends on what, wire by wire, stale wires dashed), **Questions**, **Reviews** (waiting for you, and what you submitted) and **Activity**, and the kolabs the actor can reach. A person whose role writes the layer can create a node in the session's kolab.
- **People** and **Connect a harness** (W3.4, W3.6): an admin of the kolab sees who holds access and from where, changes or removes a direct grant, makes invite links, sees what became of them and revokes open ones; anyone sees the one command that connects Claude Code or a shell to this Kolab, with their kolab and role. An invite opened from its link shows what it offers, and *Join* (see *Onboarding with no admin*).

**Signing in.** A person signs in with GitHub (D55): *Sign in with GitHub* goes to `GET /api/session/oauth/start`, which sends the browser through Kolab's own authorization server as its first-party client `konjir-web`, with PKCE and a state of its own kept in a cookie only its callback reads, to GitHub and the consent page, where the person picks the kolab and role (or makes their first kolab), and back to `GET /api/session/oauth/callback`. There Kolab exchanges the code in the process, and keeps the access token in an `HttpOnly`, `SameSite=Strict` session cookie, and the refresh token in another, which the browser forgets when it closes, so the page's script never holds either. Behind the TLS proxy they are `__Host-konjir_session` and `__Host-konjir_refresh` (`Secure`, `Path=/`, no `Domain`), so no other host under the same domain can plant one; on loopback `konjir_session` and `konjir_refresh`, scoped to `/api`. Every call checks the session again, as `/mcp` does; when the access token has expired, the guard refreshes it, once however many of the page's calls arrive together, and sets both cookies anew. A session that ends or loses its access signs every page out. *Sign out* (`DELETE /api/session`) ends the session itself, if it is a person's, and revokes its refresh token; signing in again starts afresh. Whatever the cookies held, they are cleared. `GET /api/session/methods` tells the page which ways in this Kolab offers.

With token sign-in on (no identity provider, or `KONJIR_WEB_TOKEN_SIGN_IN=on` for development), a person may instead paste a Konjir session token of their own, which an admin opened (`konjir admin_open_session actor=lee role=product kolab=accounts`, or `deploy/konjir-ops.sh connect lee product`): the page posts it once to `POST /api/session`, into the same cookie. Either way an agent's session is refused: the web interface is for people, and an agent works through MCP or the CLI, so no person clicks as their agent and no verdict says an agent gave it. The admin token, which works in no kolab, is refused too (compared in constant time, as on `/mcp`).

**Kolab and role.** The kolab picker lists the kolabs the person can reach, with their access there, and *Working as* switches between product and engineer. Either switch (`POST /api/session/switch`, `Kolab.switchSession`) ends the person's session and opens one in the chosen kolab and role in one transaction under the access lock, checking access there, so either both happen or neither does; the old session's end is signalled only once that commits (D41). The new token goes only into the cookie (ENF4 allows one open session per actor, so a CLI using the same token stops working too). *New kolab* (`POST /api/session/kolab`, `Kolab.createOwnKolab`) makes a private kolab owned by the person (D54; TEN2, TEN3) and moves the session into it in the same role. Kolab enforces the limits, not the page: the person holds Write where they work (a reader can't), the name follows the kolab grammar in at most 40 characters, is unique across Konjir (TEN4) and isn't reserved (`kolab`, and anything starting `konjir`, such as D15's `konjir-site` and `konjir-brand`), the title is at most 100 characters, a person owns at most 10 kolabs (`KONJIR_KOLABS_PER_PERSON` for `konjir serve`), and makes at most 3 in 10 minutes, counted in the database under the access lock, so in every process together. An admin's `admin_add_kolab` keeps no such limits. An empty kolab's first page offers its first document.

**The API** (`apps/server/src/web`) is thin: each write is one of the agents' verbs, with the same engine call and the same rules, which Kolab enforces, not the API. Every read gathers what a page shows through `@konjir/engine`'s `views.ts` and `readNode`, which run as the session reads (`Kolab.readAs`: `kj_agent` under row-level security, in a read-only transaction) and name the session's kolab too. The one exception is the picker's list of kolabs, which comes from Kolab's own access check (`kj_access`, which no session may run). A submission names the version its edits were made on (`base`); if the node has moved on since, whether before the draft is written or before it is submitted, the draft is abandoned and the submission refused as stale (409), and the page keeps the edits, so edits are never laid over a version their author didn't see (CAS7). Nothing writes outside the session's kolab (TEN12): a node is named by its name in it, and another kolab's is refused as if it weren't there. Reading another kolab goes only through `/api/kolabs/:kolab/…`, in place and read only (D49, below). Every `/api` request must name a host Kolab serves (loopback, or its public host), as `/mcp`'s DNS-rebinding guard requires, and a change must come from Kolab's own origin. Errors come back as `{ error, message }` with any token masked; anything Kolab doesn't name is logged and answered with a plain 500, so no database detail reaches a page. The types are `@konjir/types`' `Web*`.

Case files and rulings are read as `kj_agent`, so a session holding only Read sees none (row-level security, 0013); `GET /api/nodes/:name` carries each element's rulings and open case files, and the node's own rulings. **Live.** Each page holds one `GET /api/events` stream. It carries signals, never content, and the page re-reads what it shows: `changed` with a layer when that layer's inbox changes (from any Kolab process on the database, API5), `changed` `answers` for the session's own answers, `changed` `versions` when a version is written or changes state in the kolab, and `ended` when the session ends (D41), after which the stream closes. A stream lives as long as its access token: when that expires but the session lives on, the stream closes without `ended`, and the browser reconnects a second later, which refreshes the token (D55). Push signals name their kolab (D50), so a page hears only its own kolab's. A commit signals no inbox, so each process checks the versions of each kolab that has a page open, once every 3 seconds however many pages are open there, one check at a time; once push signals carry commits (D50), that check becomes a fallback. A session holds at most 6 streams (429 beyond). The session is checked before each signal, and a comment every 20 seconds keeps the proxy from closing an idle stream.

**The pages** are served at `/` with a strict content security policy: everything from Kolab itself, the design system's fonts included, bundled with the page from `@fontsource-variable` packages, so no third party learns who opens a private kolab's page, `X-Frame-Options: DENY` and no referrer. Assets are named by their hash and cached for a year; `index.html` isn't cached. Any other path that asks for HTML gets `index.html`; `/api`, `/mcp` and `/healthz` are never shadowed. Without a build, `/` says how to make one. The look is the Konjir design system's: Predawn (dark) by default and Daybreak (light), Fraunces, Instrument Sans and JetBrains Mono, and the prototype's layout.

### Deploying from CI

`.github/workflows/deploy.yml` runs on every push to main, and by hand (**Actions › Deploy › Run workflow**, on main):

1. **Build release** packs the commit with `deploy/release/pack.sh` (below) and uploads the zip with its checksum. Terraform installs exactly those bytes (`release_zip`, `release_id`) and packs nothing itself.
2. **Plan production** waits in the `production` GitHub environment for Lee's first approval, then plans. The run's summary lists each change, with the names of the attributes an update changes, and the plan's digest: a sha256 of each change's address, actions and new values (sensitive ones redacted). A plan that would delete a protected resource, alone or to replace it, fails unless the run was started by hand with **allow_replacement**: the instance or its data volume's attachment, the data volume, the database, the release or site bucket, the snapshot schedule, or the instance or snapshot role (which only Lee can make again).

Kolab listens on localhost only, behind Caddy. Its database is on RDS, apart from the instance, so replacing the instance is safe. A change to the boot script replaces it automatically. The boot script still writes `KONJIR_REVIEW=structural` and `KONJIR_REVIEW_MODEL` into `/etc/konjir/env`, which Kolab ignores since W1.7: `modules/kolab` passes them as constants so that the script renders unchanged and W1.7 doesn't replace the instance. They go with the next boot-script change. Production's data volume still holds the PGlite database Kolab used before RDS.

Day to day:

- **Ship code:** merge to main, then approve the run's **Plan production**, read its summary, and approve **Deploy production**. `deploy/release/pack.sh` packs the release with `git archive` of the commit, so only tracked files ship: never an untracked or ignored one, such as `.env`, a `.claude/` worktree, a nested `.konjir` or a `*.tfvars` file. It refuses a checkout with uncommitted tracked changes, so a deploy is always exactly a commit, and refuses one that tracks a file that must never ship. The release id is the commit's tree id without `site/` (the marketing site, which isn't in the zip either), so it changes only when Kolab's tracked content does; a new one makes Terraform reinstall and wait for success.
- **Bump the CLI on the web page:** after each CLI release (see [Releasing the CLI](#releasing-the-cli)), set `cli_npm_spec`'s default in `deploy/terraform/variables.tf` to the version npm now has, `konjir@<version>`, and merge. The release workflow doesn't bump it. The deploy updates the parameter, and, since the commit is a new release, reinstalls and restarts Kolab, whose `start.sh` reads it. Until then the page keeps showing the version before.
- **Inspect:** `deploy/konjir-ops.sh status`, `logs` or `bootstrap-log`; `cloudwatch-logs [since]` follows the same lines in CloudWatch Logs, and `alarms` lists each alarm's state. `shell` opens a session; it needs the Session Manager plugin. `deploy/smoke.sh <site>` checks `/healthz` and `/mcp` from anywhere.
- **One-way migrations:** a release that applies a migration can't be rolled back by deploying the release before it, which refuses a database migrated past it. 0011 (hashed session tokens) is also irreversible in the data: the hashes can't be turned back into tokens, so there is no down migration. Before approving a production release with such a migration, take an RDS snapshot (`aws rds create-db-snapshot`). Rolling back means restoring that snapshot and deploying the earlier release; every session opened since the snapshot is lost, so reissue those tokens with `deploy/konjir-ops.sh connect`.
- **Preflight a migration that can refuse:** before approving a deploy that carries such a migration, run `deploy/konjir-ops.sh preflight <NNNN>`, today `preflight 0027`. It sends `deploy/preflight/<NNNN>.sql` and `deploy/preflight/run.cjs` to Kolab's instance over SSM, as the recovery drill sends `recovery-verify.cjs`, since only the instance reaches RDS and it has no `psql`. There, as the `konjir` user, with `/etc/konjir/env` and the database URL read from SSM into a file only that user can read, the live release's own `pg` runs the queries in a session read-only by its startup options, with a 60 s statement timeout, inside `begin read only` … `rollback`. It prints each refusal the migration would make, or that it applies cleanly, then the parents it will set, and never the database URL. It needs the database at the migration before (0026 for 0027, today's live release), and says so on one already past it. An advisory preflight, one whose first line is `-- advisory` (`preflight 0029`), gates nothing, because its migration can't fail: the command and its output say "advisory", and it lists what to look at before deploying (for 0029, the plan links PLN2 would refuse a plan's next version for) as `advise` lines, never as refusals.
- **Recover the database:** [`deploy/RECOVERY.md`](deploy/RECOVERY.md) is the runbook: restore to a point in time into a new instance, verify it, cut over, roll back. `deploy/recovery-drill.sh` is the drill (see *Recovering the database*).
- **OS refresh:** the AMI is pinned when the instance is created. Run the workflow by hand with **refresh_os**: both plans then replace the instance (`-replace=module.kolab.aws_instance.kolab`), and that one replacement, with its data volume's attachment, is allowed.
- **Tear down:** set `DEPLOY_FROM_CI` off, then, by hand: the database has deletion protection, so turn it off first, `deploy/konjir-ops.sh terraform apply -var db_deletion_protection=false`, then `deploy/konjir-ops.sh terraform destroy -var db_deletion_protection=false`. Final snapshots of the data volume and the database, and the database's automated backups, are kept by default. For a teardown that leaves nothing, add `-var final_snapshot_on_destroy=false` to both. The apply is needed because destroy reads the database's deletion protection and snapshot settings from state. Daily volume snapshots made before the teardown remain until you delete them. The state bucket stays until you remove it. So does the break-glass admin token's SSM parameter, `/konjir/<name>/admin-token`, which Terraform doesn't manage (below): delete it with `aws ssm delete-parameter --name /konjir/<name>/admin-token` once the stack is gone, or the next stack of that name starts with its value.

**The break-glass admin token** (W2.22, D69) is the SSM SecureString `/konjir/<name>/admin-token`, which Terraform names but never holds, like the GitHub app's secret. `deploy/konjir-ops.sh rotate-admin-token` writes a fresh one (`kja_` and 40 letters and digits, from a temporary file, never a command line) and restarts Kolab, so the old one stops working; `admin-token` prints it, and `rotate-admin-token --off` writes `off`, which disables the break-glass, once Kolab, asked with the token still in place, has a live admin who signs in with GitHub (`--off-without-an-admin-who-signs-in` skips that check). That check, like `connect`, uses the token, so it sets off `break-glass-used` too. Until W2.22 Terraform generated it, so it is in older state files: the root module's `removed` blocks make the next `terraform apply` forget it without deleting the parameter, and rotating once after that apply makes the value in the state worthless. A new stack's Kolab starts once `rotate-admin-token` has written the parameter. Admins don't use the token day to day: see *Konjir's admins*. The state bucket stays private, encrypted and TLS-only, since the database password is in it, and the deploy role reads only production's state. The deploy role has no SSM or KMS access to the parameter; an approved deploy can still reach it through the instance, which reads it (W2.23a, *Deploying from CI*).

### Recovering the database

The targets (P12, D75, D81): a recovery point at RDS's documented guarantee, through point-in-time recovery, and a restore in under 1 hour. The automated backups allow a restore to any second in the last 7 days, up to the latest restorable time. RDS uploads the log every 5 minutes, so a restore can lose up to about 5 to 6 minutes of writes, and the drill records the real figure (D81). A failed host with intact storage is recovered in place by RDS, with nothing lost. The database has deletion protection. Deleting it anyway keeps a final snapshot and the automated backups, so a point-in-time restore is still possible, unless `final_snapshot_on_destroy` is off.

[`deploy/RECOVERY.md`](deploy/RECOVERY.md) is the runbook. It goes step by step:
- pause deploys (`DEPLOY_FROM_CI=false`, and cancel pending runs);
- choose the point;
- restore into a new instance, from settings in Terraform's state (`database_recovery`), so it works when the instance is gone;
- verify;
- cut over through the `database-url` parameter;
- roll back;
- bring Terraform into line;
- clean up.

It has a separate path for when a release caused the damage, and says who does each step and how long each takes.

`deploy/recovery-drill.sh --env production` is the drill (production is the only environment, D83):
- It refuses unless the environment's state names that environment's database and parameter.
- It restores the latest restorable time into a scratch instance, `<db>-drill-<UTC date-time>`, and waits for it.
- It verifies the copy through Kolab's instance over SSM (`deploy/recovery-verify.cjs`), changing nothing. It checks the migrations against the live release's pins, and that the copy's tables are there. Then a second Kolab, `konjir serve --no-migrate --no-worker` on a read-only session at `127.0.0.1:7499`, must, writing nothing, answer `/healthz`, refuse a token that is no session's with 401 (once it has looked it up in the copy's sessions), and refuse `admin_list_actors` with the break-glass token, because that verb's audit row can't be written to the read-only copy (W2.22; a live release from before W2.22 runs the verb instead). Then the release's engine, opened read-only on the copy without migrating, must list every actor the copy holds. Last comes an optional comparison with the environment's database.
- It logs the timings to `deploy/drills/`, which git ignores, and deletes the scratch instance, with no final snapshot.
- It asks before creating anything and before deleting, and refuses a name that exists or a leftover drill.
- It never modifies the environment's database or any parameter.

`verify <instance> [--compare-production]` runs the same verification on a real restore, and `vars` prints the checked settings the runbook uses.

`konjir serve --no-migrate` applies no migration and refuses a database that needs one, and `--no-worker` runs no outbox jobs; both say so at warn. They don't stop a request through that Kolab from writing. What makes verify change nothing is the read-only session (`default_transaction_read_only`) its Kolab and its own checks use.

### Logs and alarms

Failures are noticed before users report them (P11, D68): alarms email the operator.

**Logs.** Kolab's own log lines are JSON, one object per line: `time`, `level` (`info`, `warn` or `error`), `message`, then fields where Kolab knows them, such as `kolab`, `actor`, `event`, `job`, `version` or `error`. `@konjir/log` writes them, NestJS's lines go through it (`JsonNestLogger`, with `context` and `stack`), and so does `konjir serve`'s startup. No token reaches a line: every string in it has Kolab's tokens masked (any `kj<letter>_`, the admin token's `kja_` among them: `kjs_***`, as `maskTokens` does) and GitHub's (`gho_`, `ghu_`, `ghs_`, `ghr_`, `ghp_`, `github_pat_`), and a URL's password (whatever it holds) or libpq's `password=`, a secret in a query string (`code`, `state`, `client_secret`, `access_token`, `refresh_token`, `code_verifier`, `token`, `password`), and a `Bearer` or `Basic` credential too (in any case, after a space, tab or colon, but only before a credential-like word, so "a basic check" stays readable); and a field whose name says it holds a secret (`token`, `secret`, `password`, `pass`, `pwd`, `authorization`, `cookie`, `privateKey`, `codeVerifier`, `sessionId`, `code`, `state`, …) is written as `***`. The journal copy on the instance masks the same way, and `libs/log/test/mask-vectors.json` holds both to it: `@konjir/log`'s tests run the copy's Python tests too. Kolab logs every 5xx answer at error level (`event: http_5xx`, with method, path and status, never the query), and a dead outbox job as one error line with `event: outbox_job_dead`, its `id`, `kolab`, `job`, `version`, `attempts` and `error`. The one line that isn't JSON is the admin token a local `konjir serve` prints when it generated one, which a deployed Kolab never does.

The release ships them: `deploy/release/install.sh` runs `deploy/release/observe.sh` as root, which installs the CloudWatch agent and logrotate from Amazon Linux's repository if they're missing, and copies the journal of `konjir.service` and `caddy.service` (`konjir-journal@<unit>`, since the agent reads files, not the journal) to `/var/log/konjir/<unit>.log`, from where the agent sends them to the log group `/konjir/<name>`, as the streams `konjir` and `caddy`, kept 30 days. The agent also puts memory and root-disk use in the namespace `Konjir/<name>`. So none of it changes the boot script or replaces the instance: the first deploy with it installs it.

The copy (`deploy/release/journal-copy.py`) runs sandboxed (`ProtectSystem=strict`, `NoNewPrivileges`, writing only `/var/log/konjir`), and:
- starts from now each time it starts (`journalctl --lines=0`), so it never ships an old line again; a restart of the copy may miss the few lines written meanwhile;
- reads lines of any length (`--all`; without it journalctl drops a line over 4 KB), and ships at most 16 KiB of each: a longer JSON line has its longest strings cut and says `"truncated":true`, keeping its `level` and `event`, so a dead job with a long error still counts;
- masks every line as `@konjir/log` does before it leaves the instance, Caddy's too, whose error lines carry the request's URI, OAuth `code` and `state` included; a line too deeply nested to walk is masked as text;
- adds the journal's own `_SYSTEMD_UNIT` to each JSON line, and writes systemd's lines about the unit (`konjir.service: Main process exited, …`) as JSON with the journal's `_PID` 1 and `UNIT`, so the alarms' filters can tell Kolab's lines from Caddy's and systemd's from either. A line can't claim those fields: they're removed from a service's JSON, and struck out of a line that isn't JSON;
- every 5 minutes writes a probe into the unit's journal (`konjir-journal@<unit>: probe`, which `deploy/konjir-ops.sh logs` shows too) and a heartbeat line (`event: heartbeat`) with `last_journal_line` and `journal_age_s`, how long ago it last read a line from journalctl. The probe comes straight back, so an age over 15 minutes means journalctl is stuck: the heartbeat no longer counts as fresh, and after 20 minutes the copy exits and systemd starts it again.

`konjir-journal-rotate.timer` rotates the copies every 10 minutes once one passes 50 MB, keeping two, and `logrotate.timer` is enabled too, so a log flood can't fill the root disk. If `observe.sh` fails, the release goes on without it: `install.sh` prints an `observe_failed` warning, and the `no-logs` alarm fires within 30 minutes. The warning is in the install's output, which is the SSM association's run (Systems Manager, State Manager, the association's execution history) or, on a first boot, `/var/log/konjir-bootstrap.log` (`deploy/konjir-ops.sh bootstrap-log`); and in the instance's journal, `journalctl -t konjir-observe` in a `shell`. It can't be in CloudWatch, since it says shipping failed. Shipping logs never stops a deploy, or a new instance's first boot.

**Alarms.** Each is named `<name>-…`, emails the topic `<name>-alarms` when it fires and again when it recovers, and says in its description what to do.

**The email.** `alarm_email` comes from the repository secret `PRODUCTION_ALARM_EMAIL`, which the deploy workflow passes as `TF_VAR_alarm_email`; set it and deploy. Terraform subscribes it to the topic, and AWS emails it a link, which must be followed once before any alarm is delivered. Until then, and with `alarm_email` empty, the alarms still change state (`deploy/konjir-ops.sh alarms`) but email no one. Changing the address subscribes the new one; destroying a subscription still pending confirmation only drops it from Terraform's state, and AWS deletes it after 3 days.

The first apply may send one ALARM email, then its OK, that is not an outage: `healthz-failing` and `no-logs` treat missing data as failing, and they have none until Route 53 publishes its first status and the agent ships its first lines.

**Checking each alarm after a deploy** (the done-when): `deploy/konjir-ops.sh inject <what>` sets off one alarm on purpose, and its email should arrive in the time the table gives, then its recovery. Each kind says what it will do and for how long, then which alarm to watch. `crash`, `down`, `log-flood`, `disk-high` and `no-logs` change the live instance, so without `--yes-production` they only say what they would do (`disk-high` also runs a read-only check on the instance, from stdin, which writes nothing, to show its sizes). What they change on the instance runs as a transient systemd unit or timer (`konjir-inject-*`) with a time limit of its own, so it ends and undoes itself even if the SSM command, the shell or the laptop goes away; the units run their script from `/run/konjir-inject-<hash>.sh`, written once per version, so a later call never rewrites a running one. `disk-high` and `no-logs` also watch their alarm, and undo the inject as soon as it fires, or on Ctrl-C or a closed terminal. Each refuses to start while its alarm is already in ALARM; and on the instance, while another `konjir-inject-*` unit or timer is active (so no two overlap: `no-logs` would blind `disk-high`, and a flood rotating the copy with the agent stopped would lose lines), while a deploy is installing a release (`konjir-update`, from the install association), or, but for `down`, while the CloudWatch agent isn't running. A routine deploy shouldn't fire any alarm; check that on the first apply with `alarms`.

**Cost**, roughly, at us-east-1 list prices: the HTTPS health check about $1.50–2.75 a month, twelve alarms about $1.20, ten custom metrics (eight from log filters, the agent's memory and disk) $3, and logs $0.50 a GB ingested and $0.03 a GB stored, well under a GB a month for a test server (the heartbeats are about 1 MB): about $5–6 a month. Each `inject log-flood` adds about 1.4 GB ingested, $0.70, and its 30 days' storage, at most $0.04. Email through SNS is free at this volume. A CloudWatch Synthetics canary would cost about $10 a month for the same check, which is why `/healthz` uses Route 53.

**Testing only.** This is one instance with no failover. With the GitHub OAuth app set up, people sign in with GitHub, and their tokens last 15 minutes and refresh (D55). Hand-issued tokens are bearer tokens that expire 30 days after they are issued (W2.22; `KONJIR_HAND_ISSUED_TOKEN_DAYS` changes that): hand them out privately, and revoke them with `admin_end_session` (by `token`, `session` key or `actor`; Kolab stores only their hashes, so it can't show a token again). Turn them off with `KONJIR_HAND_ISSUED_TOKENS=off` once nothing needs them.

### Marketing site

`https://konjir.com` is the marketing site (D81). Each deploy publishes the built site with everything else, through the `site` module:

- each file the build writes in `site/` (its README and the source in `site/src/` aside; `deploy/terraform/tests/site_files.tftest.hcl` checks it) as an object with its content type. ## Releasing the CLI

`nx release` versions `konjir` (D23), configured in `nx.json`'s `release`: the `konjir` project only, tagged `konjir@<version>`. The current version is the newest such tag, or `apps/cli/package.json`'s before the first release. Bumps are plain semver, so `minor` from 0.5.0 is 0.6.0. The commits here aren't conventional commits, so the version is given, not inferred, and nx release writes no changelog. `apps/cli/scripts/version-actions.cjs` writes the version, in place of `@nx/js`'s, so the workspace doesn't install `@nx/js`. Installing it would add Babel to every install, the instance's included, and turn on Nx's source-file analysis, which needs TypeScript 5's JavaScript API. Publishing isn't nx release's: the workflow below publishes the tarball it tested with `npm publish`.

```
npx nx release version 0.6.0 --first-release --dry-run   # preview the version the workflow would set
```

Publishing runs only in GitHub Actions, by hand: **Actions › Release CLI › Run workflow** on main, with a version (`patch`, `minor`, `major` or an exact `X.Y.Z`; no prereleases) and dry run on (the default) or off. The workflow, `.github/workflows/release-cli.yml`, has four jobs, each with only the permissions it needs:

1. **Build konjir release** (read-only) sets the version in the runner and commits nothing. It refuses a version that already has a tag or is on npm. It builds the tarball and the binaries, checks both against a Kolab it starts from the checkout, runs `npm publish --dry-run`, and uploads the files with `SHA256SUMS`. A dry run stops here.
2. **Draft GitHub release** attests the files' build provenance (`gh attestation verify <file> --repo konjir/kolab` checks a download). It creates the release `konjir@<version>` as a draft, with the files and notes generated from the merged pull requests.
3. **Publish konjir to npm** runs in the `npm-release` environment, with no checkout and no dependencies. It publishes the tested tarball, with provenance, through npm 11.
4. **Publish GitHub release** takes the draft out of draft. That creates the tag on the built commit, and the next release reads its version from that tag.

Before the first release, Lee sets up:

- **A GitHub environment** named `npm-release` (Settings › Environments), with deployment branches limited to `main`, and a required reviewer if wanted. A copy of the workflow on another branch then can't reach the npm credentials.
- **npm trusted publishing**, preferred. On npmjs.com, konjir's settings › Trusted publishing › GitHub Actions: repository `konjir/kolab`, workflow `release-cli.yml`, environment `npm-release`. No secret is needed. A package must exist before trusted publishing can be configured on npm, so the first publish may need the fallback.
- **Or the fallback:** an `NPM_TOKEN` secret in the `npm-release` environment, a granular npm token with write access to `konjir`. npm caps such tokens at 90 days, so it needs rotating.

If a run fails, what to do depends on how far it got. Before *Publish konjir to npm*, nothing is published: delete the draft release if there is one (`gh release delete konjir@<version>`), then run again. If npm has the version but *Publish GitHub release* failed, re-run that job, or run `gh release edit konjir@<version> --draft=false`. A new run for a version npm already has stops in its first job.

A release doesn't change what the test server's web page shows: bump `cli_npm_spec` and deploy (see *Deploying to AWS*).

The published CLI is licensed under the Apache License 2.0 (D63): `apps/cli/package.json` and the published `package.json` declare `Apache-2.0`, and `apps/cli/LICENSE` holds the full licence text. `package.mjs` copies `LICENSE` into the npm package, beside `THIRD-PARTY-NOTICES.md`, and beside the binaries, so the release carries both too. `package.mjs` refuses to build if `apps/cli/package.json` declares any other licence, and `apps/cli/scripts/check-licence.sh`, which both workflows run on the packed tarball and the binaries, fails if `LICENSE` or the notices are missing or the tarball declares anything else. The bundled packages are Apache-2.0 (the MCP SDK, with its MIT-licensed earlier contributions) and MIT (eventsource-parser, pkce-challenge, zod), all of which allow redistribution under Apache-2.0 with their notices. The rest of the repository is FSL-1.1-ALv2 (see *Licence*), so konjir must carry none of it: `package.mjs` fails the build if the bundle inlines any first-party source outside `apps/cli/src` and `libs/login/src`, if either package stops declaring `Apache-2.0`, or if any bundled package is FSL-licensed, and `check-licence.sh` fails if the notices name a `@konjir/*` package or an FSL licence, or if `libs/login` lacks `apps/cli`'s `LICENSE`.

## Who pays for which model calls

Kolab makes no model calls (REV5, VER7). It has no model SDK among its dependencies, holds no model credentials, and its instance role has no Bedrock access. All the work that takes judgment happens in collaborators' own harnesses.

| Work | Runs where | Paid by |
| --- | --- | --- |
| Authoring specs, bindings, plans; implementing; answering questions | Each collaborator's harness (Claude Code, Codex, opencode, …) | That collaborator's own subscription or API account |
| Reviewing a version: contradictions, layer leaks, one testable intent per element | The reviewing agent's own harness, through `konjir_review` (see *Review*) | The reviewer's own subscription or API account |
| Structural checks, cascade, addressing, rebase, roles | The Konjir server | No model at all |

The server is built so it can't drift across that line:

- **It never asks for, stores, or relays a collaborator's model credentials.** A collaborator's token identifies them to Konjir and nothing else.
- **It never borrows a client's model.** It doesn't use MCP sampling or any other way to make a collaborator's harness run inference on the server's behalf. When the server needs judgment beyond its structural checks, it asks for a review or raises a question, which an agent or a person answers from their own harness, by their own choice.
- **Each collaborator's model use stays inside their own harness and account.** Konjir doesn't pool, share or proxy anyone's access. Whether a given plan permits a given use (for example, connecting an MCP server, or how much automated work a subscription may drive) is set by that provider's terms. Each collaborator should confirm their own plan covers how they use it.

`apps/server/test/no-model.test.ts` fails if any package of the workspace declares a model SDK, or if the lockfile installs one, even as a dependency of a dependency. Until W1.7 the server could call Amazon Bedrock as a semantic review gate (`KONJIR_REVIEW=bedrock`); that reviewer, its AWS SDK packages, its settings, its Terraform variables and its IAM permissions are gone. `konjir serve` refuses to start when `KONJIR_REVIEW` or `--review` asks for anything but `structural`, so no one believes a gate runs that doesn't, and warns that it ignores a `KONJIR_REVIEW_MODEL` set on its own. What the test server's boot script writes, `structural` with a model beside it, starts it silently.

### Konstruct kinds

A node's kind is one of four, fixed when it is made (W4.1, D77, D95): `spec` and `prototype`, in the functional layer, and `binding` and `plan`, in the technical layer. The kind fixes the layer, and the existing layer checks apply. A work package is an element of a plan (KON5), and implementation is a repository, not a node (KON7). Kolab holds to the limits, and the database holds to them for every role (migration 0027):

- **A kolab holds exactly one spec (KON1).** A second is refused, saying where its variants and prototypes go: a variant of a spec lives in another kolab, as a fork (KON9), and is that kolab's spec. A kolab starts with none, so the database enforces "never a second" (`node_one_spec_per_kolab`).
- **Each binding names the spec it binds, and each plan the binding it plans (D78).** It is a node-level parent link, `node.parent_node_id`, set when the node is made, in its own kolab, of the right kind (`node_parent_kind`), and never changed. `create_node parent=<node>` names it; a binding's defaults to its kolab's one spec, and a plan's to its kolab's binding when there is only one. Kolab never picks one of several: it refuses, naming them. A spec and a prototype name none, since either a prototype or its spec may come first (KON3).
- **A binding has at most one plan (KON5, D96).** A new binding starts without one (`node_one_plan_per_binding`).
- **Element links point inside the parent (D78, KON6).** A plan's links deliver its own binding's elements, never the spec or another node, and a plan gains no new link between its own work packages: `konjir_link` and a draft's `links` refuse one, pointing to the `depends_on` work field (D99), while such links written before keep working and are carried forward; a binding's links to a spec serve its own spec, never another kolab's. A binding may still rely on another binding, or on a prototype. `konjir_link` refuses the rest, saying what to link instead, and `edge_within_parent` refuses them as each link is written, links carried forward included, or moved to another source. A re-pin, which 0017 allows only onto another version of the node a link already names, can't change the verdict, so the trigger leaves it alone.
- **A node's kind, layer and parent never change** (`node_kind_fixed`, `node_layer_of_kind`), for `kj_agent` and `kj_system` without exception. Kolab's own login can set `kj.migrating`, as the migration runner does (0014's exemption), so only a later migration should change one.
- **A variant is of its parent's kind (D95).** A version built on another node's version takes its kind's elements: a spec's variant is a spec (in another kolab, as a fork), a binding's a binding, a plan's a plan, a prototype's a prototype. The one exception is a prototype derived from the spec (KON3). So a plan or a binding never inherits a spec's elements (KON6). The engine refuses the rest as it drafts, and `version_parent_kind` refuses them for every role.
- **`konjir_draft` with `links` is all or nothing (D95).** Each link is resolved and checked before anything is written, and written in the draft's own transaction: a link refused leaves no draft behind.
- **Old kinds are refused, pointing to what replaces them:** `functional_spec` to `spec`, `technical_binding` to `binding`, `wbs` to `plan`, a work package to an element of a plan, implementation to a repository, from `konjir_create_node`, the CLI and the web API alike.
- **Prototypes (D79, KON2, KON3).** A prototype's elements are its screens or states, each a URL, linked by equivalence to the requirements it shows. A spec change marks the screens that show the changed requirement, beside the binding elements that serve it and the work packages that deliver those, through the cascade.

**Work packages (W5.1a; PLN1–PLN3, D98).** A plan's elements are its work packages. Besides its text (what to do), each may carry work fields, on `konjir_draft`'s elements and deltas as `work`: `done_when` (its definition of done, at most 4,000 characters), `depends_on` (the work packages of the same plan version it depends on, by element id, at most 50), `size` (`S`, `M` or `L`), `milestone` (true for a work package with no work of its own: it depends on its members and delivers nothing) and, for a milestone only, `target_date` (YYYY-MM-DD), and `repo` (the repository it is done in, when not its binding's own; not checked until repositories exist, W5.2a). Kolab stores them in one form (fields in that order, a done-when trimmed) and refuses, before writing anything, a field it doesn't know, a work field written beside an element's text instead of inside `work`, a malformed field, one over its limit, an empty one (a blank done-when, an empty `depends_on`, `milestone: false` or `{}`: leave the field out instead), a target date on a work package that isn't a milestone, and work fields on any other kind's elements. Nothing given is dropped quietly. An element or a delta that leaves `work` out keeps the element's own, whether the draft sends deltas or the full element list, and `konjir_admin_apply_ruling` does the same; one that gives `work` replaces them whole, and `null` clears them. `read_node`, and the web interface's plan page, show them; the page shows them read only, keeps them when it edits an element's text, and refuses an edit that carries them. What a work package delivers is not a field: each Delivers is a dependency link from it to one element of its binding, at element scope, and `konjir_link` and `konjir_draft`'s links refuse any other link from a plan into its binding (another kind, a whole version at either end, a quote) and any from a milestone: in a draft, a milestone of the draft's own elements; in `konjir_link`, a milestone of the version linked from, and for a link from a committed version (which the plan's next commit carries forward), a milestone of the plan's latest committed version too, checked under the plan's lock, which its commits take as well. Depends on is a field, not a link, because a link pins a committed version and two new work packages in one draft often depend on each other. A plan version still commits after structural checks, without review, and PLN2's checks run as it is submitted, whoever wrote it and whatever checks a test substitutes: every Depends on names a work package of the same version, and not itself; Depends on has no cycle; a milestone depends on at least one member and delivers nothing; only a milestone carries a target date; and every Delivers the version will hold once it commits (its own links, and those it carries forward from the version it was built on) is a dependency link from a work package to an element of a committed version of its binding. A version that fails goes back to its author, still drafted, with `Plan checks failed (PLN2): …` naming each problem; Kolab's own versions of a plan are rejected. The checks run again in the commit step, under the plan's lock, so a link added meanwhile to the version it was built on is seen. An element's fingerprint is the hash of its normalized text, as it always was, when it has no work fields, so every element written before them keeps its fingerprint and every link to it holds; with them, it covers the text and the fields' canonical JSON, so changing a done-when, a dependency, a size or a date is a change, as an edit of the text is. An element-scope link, and a question on an element, resolve the same way: a work package's subtree reads as its text with its canonical work fields after it, so a link to a work package is marked when its fields change, and a link to any element without work fields resolves exactly as it always did. A quote is resolved against the text alone. `deploy/preflight/0029.sql` is advisory, not a gate, since 0029 itself can't fail: run before deploying it, with `deploy/konjir-ops.sh preflight 0029`, it lists each plan link that a plan's next version would be refused for (ord, why, and each link with its edge id, to unlink), and says it is advisory. Migration 0029 adds `element.work` and `delta.work`, both nullable, checked by `kj_work_valid` (the same rules) and held to a plan's elements by the `element_work_plan_only` and `delta_work_plan_only` triggers, for every role.

**Work state, pulling and the lease (W5.1b; PLN3–PLN5, PLN12–PLN15, PLN17–PLN19, D98).** A work package's state lives outside its plan's versions, so changing it makes no version and marks nothing (PLN4): one `work_package` row per element id a plan has ever had, keyed by the plan and the id, To do, In progress, In review or Done (PLN12), and a `work_event` row for every change, with its kind, the states it moved between, who did it (`kolab` for Kolab's own), who held the package before and after, the plan version it stood in, and each binding element it delivers at the binding's latest committed version with its fingerprint (PLN5). The commit step keeps them in line with the plan, in the commit's own transaction, so a package exists when its plan's commit returns: a new element id is To do (`added`, by the version's author); one that is gone is flagged removed, never ready, and any work on it stops (`removed`); one that comes back is To do again, or Done if it was Done (`restored`). A lease that lapsed and wasn't swept yet is recorded as lapsed first, so the history says how the package got to To do. A milestone has a row too, and only Kolab moves it: it is Done once every member is (`milestone_done`), To do again once one isn't (`milestone_reopened`), a milestone of milestones included (PLN3); an element that becomes a milestone stops any work on it.

`konjir_list_work` is the board: the kolab's packages, plan by plan, in natural order by id, so W1.2 comes before W1.10 (PLN17), each with its state, its assignee and lease, whether it is a milestone, its size, and `blocked`: a work package it depends on that isn't Done, an open question, or an open case file on a binding element it delivers (PLN19 as D98 amends it; a note blocks nothing, and "open contradiction" is gone). `ready` is To do, not blocked, not a milestone, and the reading session may write the technical layer (PLN13). Any session of the kolab reads it, one that holds only Read too, which is told neither an open case file nor a question a mark raised, as row-level security holds them from it (0013, 0022; D49, D58). `konjir_read_work work=kj:<plan>#<id>` reads one package with its context and its events, paged, in the database clock's order (a ULID breaks ties); a removed package reads too. A work address in another kolab, `kj:<kolab>/<plan>#<id>`, reads as not found (D49).

`konjir_pull_work` gives an engineer session that may write the technical layer the first ready package of its kolab's plan (`plan=` when the kolab has more than one), In progress for its actor, with its context (PLN14): its done-when, size and fields, the packages it depends on with their states, and each binding element it delivers at its latest committed version, with that element's links (the spec elements it serves, with their ancestors' text; a link into another kolab is named, not inlined), its questions and notes, open and answered, and its rulings. It returns the git trailer for the package's commits, `Konjir-Work: kj:<kolab>/<plan>#<id>`. An actor pulls only while it holds no package In progress, across every kolab (PLN18 as D98 amends it: the limit is on pulling); a pull is refused, naming the one it holds, and the database's `one_pulled_per_actor` index (0031) refuses a second package pulled or given, so two pulls by one actor at once get one package. A package a request for changes returned to its assignee (`returned`) isn't counted by the index, so an assignee may hold it beside one it pulled meanwhile; see *Submitting, reviewing and delivering work*. With nothing ready, a pull says how many are blocked, and by what. A pull counts as a draft against its actor's hourly budget. One transaction takes a shared hold on the access lock and on the plan's row, so neither a change of access nor a plan commit lands between the checks and the claim, and claims each candidate in order with `for update skip locked`, so many agents pulling at once each get a different package.

In progress is held by a lease, on the database's clock (`clock_timestamp()`), never the server's or the client's (D98): 30 minutes, unless the kolab sets another with `konjir_set_work_lease minutes=<1–1440>`, which needs Maintain or Admin and is audited (`work_lease.set`). Every call the assignee makes in the package's kolab renews a lease, reads included, while it may still write the technical layer: each engine call through `Kolab.session()`, so each MCP tool call and each web API request its person makes (PLN15). Renewal is per package (W5.1c, D98): a call that names a work package (`read_work`, `add_evidence`, `submit_work`, `release_work`, `reassign_work`, `review work=`, `reopen_work`) renews that package's lease if its actor holds it, and no other; a call that names none renews only the package its actor pulled, was given or had returned most recently (`touched_at`), so of two it holds, the one it neglects lapses. It is renewed only once 30 seconds of it are spent, so a burst of calls writes once, and only while it still runs, so a lapsed lease is never revived. What a listen stream prompts doesn't renew it (D98, D100): the inbox and answers resources are read `quietly`, and so is `konjir_whoami`, the channel bridge's 30-second liveness check and `konjir watch`'s first call on each reconnect; the streams themselves call nothing. On the web, only requests a person initiates renew it (D100): the page marks each read it makes by itself after a pushed event with `X-Konjir-Refresh: push` (`REFRESH_HEADER`), and Kolab reads those quietly; the mark only withholds a renewal, and grants nothing. Opening the page's event stream (`GET /api/events`, which EventSource opens and reopens by itself and can't mark), and Kolab's poll of the kolab's versions for each open stream, are read quietly too, and so are the instructions resources and an admin's opening of a session for an actor. So an agent idle with its channel open, or a person's idle open tab, holds no work. The outbox worker's timer sweeps lapsed leases, waking for the next one to lapse: each goes back to To do (`lapsed`, by `kolab`, noting whose lease lapsed when), `for update skip locked`, so a renewal that holds the row first keeps it. A pull sweeps first, too. Until the sweep, a read shows a lapsed package as To do with no assignee, and its assignee's release is refused as lapsed. Archiving a kolab, or an organization with its kolabs, gives back the work held In progress there in the archive's own transaction (`released`, by `kolab`, noting `archived`), so its assignees can pull elsewhere. The assignee may give its package back with `konjir_release_work` (`released`). An actor with Maintain or Admin, checked again under the access lock, may give a package In progress, or To do and not blocked, to anyone who writes the technical layer and holds nothing In progress, with `konjir_reassign_work` (`reassigned`), with a fresh lease; work To do isn't given to oneself (pull it). Whoever `to` is, an unknown actor, one with no Write there and one busy in another kolab get the same refusal, so nothing is learned of who exists or of another kolab's work (D49). A lease that lapsed unswept is recorded as lapsed first, and its old assignee told. A change of grants, membership or archive that takes Write on the technical layer from an assignee gives its work back in the same transaction (`released`, by `kolab`, noting `access_lost`), locking rows in plan and element order, as a plan commit does, so the two never deadlock. The assignee's answers (`konjir://answers/{kolab}/{actor}`) carry `work`: the package it holds here with its lease (`holding`, the one pulled, given or returned last; any other in `also_holding`), and the newest changes others made to its work, a verdict on it included. A plan's page in the web interface shows each package's state, assignee, lease and what blocks it, read only, on the plan's latest committed version.

Agents read their own kolab's work and never write it: `kj_agent` is granted select alone, through `kolab_read`, and every write is Kolab's (ENF2, D98): as `kj_system` after the engine's checks, but for the lease's renewal, one statement, and the releases a change of access or an archive makes, in that change's transaction, on Kolab's own login. Events are never edited or removed, by any role, Kolab's login included (`work_event_fixed`); the one change allowed is a redaction by `kj_system`, of the actor, the note and the assignees, which the redaction verb will make (deferred, with P16). A package is never deleted. Both tables carry their kolab, set from the plan's (`kj_work_kolab`), fixed once written, and refuse writes in an archived kolab. Migration 0030 adds them and `kolab.work_lease_s`, and brings in the plans that exist: a To do package for each element of each plan's latest committed version, with an `added` event dated, and named, by the committed plan version that brought the element in.

**Submitting, reviewing and delivering work (W5.1c; PLN10, PLN16, PLN18, VER17, D98, D99).** The assignee of a package In progress, from an engineer session that may write the technical layer, records its evidence with `konjir_add_evidence work=kj:<plan>#<id> evidence=[…]` as the work goes: commits (a full sha, lowercase hex, with their subject as `title`, the `files` they touched and a `url`), pull requests (an https `url`, with their number as `pr` and their `title`) and test runs (a `url`, or a summary as `title`). Each item is the assignee's attributed claim: Kolab never reads git (D36), so the reviewer checks it outside Kolab. A link is https, with no user or password in it; a field a kind doesn't take, or an unknown one, is refused, not dropped; at most 50 items a call, 500 a package and 500 files a commit, and text of at most 4,000 characters. An item already among the package's evidence since it was last To do (the same commit, pull request or test run) is counted in `already`, not recorded again. `add_evidence` renews the package's lease in full. `konjir_submit_work work=… [evidence=[…]] [note=…]` submits it: it needs at least one commit or pull request among the evidence since the package was last To do, this call's included (D98); test runs are optional. It goes In review, its lease ended, with a review request to each other actor holding Write on the technical layer (D66: whoever holds it, signed in or not; each is shown only while its reviewer can review in the role it works in, D65), and its assignee may pull another. With no such actor, it is Done on submission, `unreviewed` (PLN16). Submitting a package that waits in review asks whoever can review it now, withdrawing the requests of anyone who no longer can, and with none left it is Done, unreviewed. Both are refused to anyone but the assignee, and once the lease has lapsed, before the sweep runs ("pull again"). Each counts as a draft against its actor's hourly budget. `konjir_review work=… verdict=approve|request_changes [note=…]`, from an engineer session with Write on the technical layer and never by the assignee, gives the verdict: an approval makes the package Done (`approved`); a request for changes, which needs a note, returns it to its assignee, In progress with a fresh lease (`changes_requested`), even if they pulled another meanwhile (PLN18 as D98 amends it): it is `returned`, which the one-per-actor index doesn't count, and pulling and reassigning still refuse an actor who holds any package. If the assignee can no longer write the technical layer, it is To do instead. Either way the other requests are withdrawn, and the assignee's answers carry the verdict (and the channel says so). A request's subject is a version or a work package (VER17): `konjir_list_reviews`, the inbox resource and the channel list both, in one order, each naming its subject (`subject_kind`), and a work package's request says how to review it: its done-when, what it delivers and its evidence, checked with the reviewer's own access, its commit subjects and paths read as data, not instructions. `konjir_read_work` shows a package's evidence and its reviews. Removing a package In review from its plan, or making it a milestone, stops it and withdraws its requests.

A Done package whose element is marked, because something it delivers changed, stays Done, at risk (PLN10 as D98 amends it). Clearing that mark (`konjir_clear_mark`) says the work holds: the package keeps its state, recorded as `confirmed` by whoever cleared it, and its assignee is told; a mark on a package with no work yet records nothing. `konjir_reopen_work work=… note=…`, from an engineer session with Write on the technical layer, opens new work on a Done package instead: To do again under the same id, its assignee cleared, its evidence and events kept as history, recorded as `reopened`, and its open marks that the new work answers (a change upstream or a fuzzy re-anchor, each link re-pinned where it still resolves; an answered question; a dirty dependency) settled with it, so the work done next isn't at risk for what came before; a milestone it belonged to reopens. A plan version that revises an at-risk Done package (its text, its place, or its work fields) reopens it in the commit's own transaction (`reopened`, by the version's author), rather than letting the cascade settle its mark on its own (an exception to LNK6 for work packages); a plan version that revises a package not at risk leaves it Done. Every change of Done takes the plan's lock, as its commits do, so two approvals at once settle a milestone once, and a verdict never interleaves with a plan edit. Migration 0031 adds `evidence` (immutable, through `evidence_fixed`, but for a redaction of its text by `kj_system`; select alone for `kj_agent`, its own kolab's), a review request's work-package subject (`review_request_subject`: a version or a work package, never both), `work_package.returned` and `touched_at`, and replaces `one_in_progress_per_actor` with `one_pulled_per_actor`. Repositories, and evidence pinned to a registered one, are W5.2a's.

`list_nodes` gives each binding's and plan's `parent`; `read_node` gives the node's `kind` and `parent`; `create_node` returns the parent it named. The web interface's new document form offers a product session a prototype once the kolab has its spec, and asks a plan for the binding it plans; a document's page says what it binds or plans.

Migration 0027 maps each existing node by its label: `functional_spec` becomes `spec`, `technical_binding` `binding` and `wbs` `plan`, and `prototype` stays. A binding's spec is its kolab's one spec. A plan's binding is the one its live versions' links reach, if they reach exactly one binding of its kolab, or else its kolab's only binding. Before it changes anything, it stops, naming every node and link at once, if a node is a `work_package` or an `implementation`, if a node's layer isn't its kind's, if a kolab holds more than one spec, if a binding's kolab holds no spec, if a plan's binding can't be told, if two plans would share a binding, if a live version is a variant of another kind, or if a link Kolab may still write again breaks the rules above. Those are the links of a draft, a version in review or a node's latest committed version, and of the committed version that a cascade still owed (an `after_commit` job, waiting or dead) will carry forward; for the last, it asks for the outbox to drain first. Each needs a person's decision first. The links of rejected and superseded versions are history: Kolab never writes them again, only re-pins them. `deploy/preflight/0027.sql` runs the same check, text for text, read-only on a database at 0026: its first query returns no rows exactly when 0027 applies, and its second lists the parent 0027 will give each binding and plan, and why. Run it on production with `deploy/konjir-ops.sh preflight 0027` (see *Deploying to AWS*). A refusal in an archived kolab is fixed like any other, but its rows can't be changed while it is archived (0014): unarchive it with `admin_unarchive kolab=<name>`, make the change, then archive it again with `admin_archive kolab=<name>`, before deploying 0027.

### Pages and limits

Every list comes a page at a time (W2.21, D71): `list_nodes`, `list_stale`, `list_queries`, `list_reviews`, `list_cases`, `list_rulings`, `lineage`, `admin_list_actors`, `admin_list_kolabs` and `admin_outbox`, and the web API's lists. Each takes `cursor` and `limit` and returns `next`. With no cursor it returns the first page; while `next` isn't null, the caller calls again with `cursor=<next>` and the same other parameters. A page holds 50 by default and at most 200 (`PAGE_DEFAULT`, `PAGE_MAX`). A cursor is opaque: the list it belongs to and the last row's sort key, base64url JSON. Each list sorts on a key that ends in a unique id and reads the rows after the cursor's (a keyset), so a row added between two pages is neither repeated nor makes another skipped. Case files page newest opened first, by id, a key that doesn't change as a case is argued or ruled on (the answers resource, which takes no cursor, still shows the most recently changed). A cursor is bound to its list and the filters it was read with, the layer included: one from another list, read under other filters, tampered with, or with a key part of the wrong shape (each part is checked: a timestamp, a whole number or a string) is refused with "invalid cursor" (`LimitError`), a 400 on the web API, before it reaches the database. Keys on a write's time (`created_at`, the transaction's start) or a ULID (made before the row commits) can miss a row whose transaction commits late, behind a cursor already handed out: a walk that started before it committed doesn't see it, and the next walk does. Every list an agent pages is one it walks again each loop, so Kolab documents the edge rather than adding a commit-ordered sequence. `list_reviews` pages its two lists with one cursor; a list that has shown its last page returns none after it. `list_nodes` now returns `{ nodes, next }` rather than a bare list.

`read_node` returns a version's elements 250 at a time (`READ_NODE_PAGE`), with `element_count` and, for a larger version, `elements_from`, `elements_to` and `next`; a version holds at most 1,000, so most reads take one page. Beside each element it shows the newest 20 questions and notes, and `more_questions` counts the rest, which `list_queries node=<node>` lists; it reads only those questions, in SQL, never all of the node's. The web interface's document page does the same: the newest 50 versions and each element's newest 20 questions, with *More …* for the rest (`GET /api/nodes/:name/versions` and `/queries?element=`), and its People page reads invites and who holds access a page at a time. The inbox and answers resources take no cursor: each shows the first page of each list (the newest for the answers), and the inbox's `more` names each list that has more and the verb that pages it.

Kolab refuses, before writing anything and naming the limit, a draft of more than 1,000 elements, an element of more than 8,000 characters, a version of more than 512 KiB of text, a question, note, answer, review note, finding, case file question, claim or ruling of more than 4,000 characters, more than 100 findings, more than 20 items of evidence or one of more than 1,000 characters, and a node title of more than 200. A quote stays at most 1,000 characters (DAT6). The server takes request bodies of up to 2 MiB on `/mcp` and the web API (`/api`), and of up to 100 KiB anywhere else, so a caller who hasn't signed in can't make it parse more: the OAuth routes, the web sign-in and invites (`/api/session`), and `/mcp` itself unless the request's bearer token verifies, which is checked before a body that may be over 100 KiB is read. A larger one is refused with a 413 that names the limit applied. A person and their agents, together, raise at most 60 questions and notes, and draft at most 120 versions, an hour, across every kolab (`MAX_ASKS_PER_HOUR`, `MAX_DRAFTS_PER_HOUR`). An agent's count against its owner, so making agents doesn't raise the limit. An organization's agents share one budget of the organization's, however many members drive them, with limits of its own: five times a person's, 300 questions and notes and 600 drafts an hour (`MAX_ORG_ASKS_PER_HOUR`, `MAX_ORG_DRAFTS_PER_HOUR`, from `ORG_RATE_MULTIPLE`), because an organization's agents work for several people at once, and a harness looping across all of them is still stopped at hundreds of writes, not thousands. A budget counts events: a question or note counts when it is raised, and a draft when it is made, whatever happens to it after. A draft submitted by someone else, approved, rejected, folded or abandoned still counts against its author until it leaves the window, so a second account submitting someone's drafts frees none of their budget. Resolving an override mark writes a version, so it is a draft and counts too. Kolab's own rebases and folds, and a ruling an admin applies, aren't drafts anyone made: they neither count nor are limited. Each budget is counted in the database over the last hour (`kj_rate_take`, migration 0025): a call first takes its place in its owner's budget, in a short transaction under a lock per owner that counts the budget's events in the window (`rate_event`), the places held for writes under way included, and holds one more. The write marks its place used in the transaction that writes the question or the version, so the limit holds exactly when calls come at once, and the lock is never held through a write, so one person's burst doesn't keep everyone else waiting for a database connection. A write that fails gives its place back; a hold its process never gave back stops counting after ten minutes, and a write that commits after its hold was dropped is counted all the same; and a wait for the lock of more than 5 seconds is refused as busy. Past the limit, the call is refused with the limit and how long to wait, and nothing is written. The values are constants, and `Kolab.rates` holds the ones a server applies (`asks`, `drafts`, `orgAsks`, `orgDrafts`, `windowMs`), which the benchmark scripts and the property tests lift. The limits are in `libs/types/src/limits.ts`, with why each is what it is.

## Questions, notes and push

An engineer writing a binding talks to the spec through two verbs:

- **`ask`** is for a decision the engineer needs before they can proceed. Pass `from=<binding element>` to name the element that waits on it. When product answers, that element gets a `query_answered` mark carrying the question and the answer. Editing the element, or `clear_mark`, settles it. The answer reaches the binding even if the spec text never changes.
- **`annotate`** leaves a note: an interpretation the engineer is going ahead with, an assumption, a risk, or something they couldn't check. It blocks nothing, but it waits in product's queue until product replies, so product can object. A reply to a note marks nothing.

Both can target an element or a quoted span (`kj:orders#R13~q({"exact":"50 meters"})`). `read_node` shows them beside the element they're about, open and answered, including ones asked on earlier versions of the spec. Either layer can use them in either direction.

**Asking about a version in review** (D65, migration 0023). The address may name a committed version or one in review, never a draft or a rejected version. An address without `@version` names the latest committed version, so a question about a new element of a version in review names that version (`kj:orders@2#R14`); when the short form doesn't resolve and a version in review has the element, the refusal says which address to use. Only sessions in the version's kolab can ask, as only they can read a version in review: a reader from another kolab sees committed versions only (D49, D58), and can't ask across kolabs at all. Nor does it ever read a question asked of a version that never committed, even once the question has moved to a committed one: row-level security (0023) shows a reader outside the kolab only questions whose `asked_version_id` committed, since the question's text may quote words that never did. The question records the version it was asked of (`query.asked_version_id`), and follows it:

- **It commits:** the question is on the committed version already, and reads like any other, outside the kolab too.
- **It is abandoned, rejected as stale, or returned to its author as a draft:** in the same transaction, the question moves to the node's latest committed version if the element it asked about is there, and `list_queries` and `read_node` show it with `asked_of`, the version it was asked of, and `element_changed` when the element's text differs there. A question that quoted words (`~q(…)`) moves only if those words are in the target word for word, exactly once, and its quote's prefix and suffix are taken again from the target's text, so no word only the version in review had is carried. `element_changed` compares the element with everything under it. If the element or the quoted words aren't there, or the node has no committed version, an open question is settled as `withdrawn`, its answer saying why, and the element that waited on it (`from`) gets a `query_answered` mark saying so (a mark's trigger is always a committed version, so with none on the node no mark is raised). `from` must name an element the asker can write: Write on its layer, in its kolab, so a Read-only member asks without it. A question already answered stays where it was asked, as the record. Nothing is left open on a version no one can ask about.
- **Kolab folds it onto a rebase:** the question goes with the edit, onto the fold.

An ask reads the version's state under a share lock, so an abandon, a request for changes or a commit either waits for the question and settles it with the rest, or comes first and the ask is refused.

**Push.** Push is per kolab (D50). Each layer has an inbox resource in each kolab, `konjir://inbox/<kolab>/functional` and `konjir://inbox/<kolab>/technical`, holding its open questions, notes and marks there, its open case files, and, for the reader, the review requests waiting for them on that layer. Each actor has `konjir://answers/<kolab>/<actor>`, which holds what they raised in that kolab, with replies, the versions they submitted there for review, with the verdicts, and the case files they opened or argued there, with their rulings. Each body names its `kolab`. `whoami` lists the two for the session, in the session's own kolab, and a client subscribes to what it lists. A change in one kolab signals only that kolab's resources, so a subscriber in another kolab hears nothing of it. A session may read and subscribe only to its own kolab's inboxes and its own answers there: another kolab's inbox reads as if it didn't exist, and a `subscriptions/listen` asking for anything else (another kolab's resources, another actor's answers, or the per-layer `konjir://inbox/<layer>` of a release before D50) is refused in-band before it opens, HTTP 200 with the JSON-RPC error `-32003` and `data.reason` `not_subscribable`, which names nothing of the other kolab. The bridge retries that, asking `whoami` afresh, and `konjir watch` says to run it again. Neither `@onivoro/server-mcp` nor its listen-stream gate shows Kolab the URIs a stream asks for, so this check is Kolab's own Nest middleware on `POST /mcp` (`ListenScope`), which reads the token exactly as the transport does and only ever refuses; the admin token may subscribe to anything. It first applies the transport's own Host/Origin guard, and leaves a request with no valid JSON-RPC id to the transport, so it answers nothing the transport would refuse first; and a session lookup that takes over 10 seconds refuses the stream as `gate_timeout`. It covers `subscriptions/listen` alone, which is enough because the transport is stateless: a 2025-era `resources/subscribe` gets "method not found", and a test fails if sessions are ever turned on. Kolab declares `resources.subscribe` and signals a resource whenever it changes, over MCP 2026-07-28 `subscriptions/listen`. A client that listens gets `notifications/resources/updated` and re-reads the resource. Only the URI is pushed, never the content, and reading `answers` is limited to its own actor. Ending a session closes its open listen streams at once, as the server closing the subscription, and nothing more is signalled to them. Each change is also checked against the session before it is signalled, so a session ended any other way closes its stream on the next change instead. Its token is then refused (401), so a client that reconnects with it learns it was revoked. A listen stream whose session ends while it is opening is refused in-band instead: HTTP 200 with the JSON-RPC error `-32003` and `data.reason` `session_ended`, which the channel bridge and `konjir watch` treat as the token revoked, as they do a 401. The session is checked as each stream opens, so if that check fails (the database is unreachable, say) the stream is refused as `gate_failed`, or `gate_timeout` after 10 seconds, rather than opened and checked at the next change; the bridge retries those with backoff, and `konjir watch` says to run it again. [`@onivoro/server-mcp`](https://www.npmjs.com/package/@onivoro/server-mcp) tracks, gates and closes the streams (`McpHttpService.closeListenStreams` and the auth strategy's `acceptListenStream`); Kolab says which to close. Other sessions' streams, including those of the same person's other agents, are untouched.

**Push across processes.** Several Kolab processes can serve one Postgres database, and an agent listening on any of them hears a change made through any other (API5). Each engine event is sent with Postgres `NOTIFY` inside the transaction that commits its change, so it is delivered only if the change commits, and never on a rollback. Each process `LISTEN`s on the `konjir_events` channel over one connection of its own, apart from its pool, through [`@onivoro/server-pg-notify`](https://www.npmjs.com/package/@onivoro/server-pg-notify)'s `NotificationListener` (its Nest-free `/listener` entry), which reconnects with backoff (1 s, doubling to 30 s, without limit) when the connection drops, and stops when the process closes. A process tells its own listeners once the transaction commits, and skips its own notification when it hears it back, so nothing is signalled twice. The payload is the event (a kolab's name with a layer or an actor, or an ended session's sessionKey), not the content, and never a token or a row's id; an event too long for `NOTIFY` is sent as a signal to re-read every inbox. An inbox event's kolab rides on the notice, `{"from", "kolab", "event": {"inbox", "layer" | "actor"}}`, so the event keeps the shape a release before D50 reads: during a rolling deploy an older process still hears a newer one's changes (it ignores the unknown field), and a newer process hears an older one's kolab-less event as a resync, since it can't tell which kolab changed. A burst of those costs one resync: resync notices heard within 250 ms fold into one. Two windows remain while old and new releases run side by side, and only draining the old processes closes them: an old process still signals the per-layer `konjir://inbox/<layer>` to its own subscribers, so they hear every kolab's changes on that layer until it stops, the leak D50 closes; and a client whose `whoami` reached a new process but whose `subscriptions/listen` reached an old one gets a stream that opens and stays quiet, since the old process never signals the per-kolab URIs. The channel bridge re-reads everything when it reconnects, so nothing is lost for good, only late. A short drain (deregistration delay) on the old processes bounds both. Anyone who can connect to the database can NOTIFY on the channel, so a process drops anything that isn't exactly an event Kolab sends, including a payload that isn't JSON at all, which costs no reconnect. It counts and logs each one it drops, never the payload. A process that can't LISTEN at boot doesn't start. The listening connection notices a silent drop too (a failover or a NAT drop, with no FIN or RST): it is checked every 10 seconds, a check unanswered in 5 seconds counts as a loss, TCP keepalive starts after 10 seconds idle, and a reconnect that hangs gives up after 10 seconds. When the connection is lost after boot, changes committed meanwhile aren't heard, so once the LISTEN is back the process resyncs: in each kolab with an open session, it signals every inbox there and the answers of each actor with an open session there, and each subscriber re-reads. The resync reads those actors before signalling anything, and if that fails it is retried with backoff (1 s, doubling to 30 s) until it succeeds or the connection is lost again. The process logs at error level as soon as the connection is lost, at error level for each failed resync, and at warn level once it is back and every inbox has been signalled. On PGlite there is one process, and events go only to its own listeners.

Claude Code doesn't yet turn these notifications into a turn for the model. Until it does, an agent waiting on answers can run `konjir watch --once` as a background command, which exits with the change as soon as the inbox has one. `konjir watch` without `--once` prints the inbox, then one JSON line per change, for a harness that tails output.

## Case files and rulings

Most of what an agent needs is an answer (*Questions, notes and push*). A genuine disagreement the two sides can't settle becomes a **case file** (CASE1): `konjir_open_case address=kj:checkout#R1 question=… claim=… seeks=keep_intent|change_intent evidence=[…]` opens one on one element of a committed version in the session's kolab, with the opener's position and the side it takes: keep the intent as written, or change it. Evidence is a list: `kj:` addresses, each of which must resolve for the session, and anything else as text (a commit, a file and line, a test run). The other side answers with `konjir_add_position case=<id> claim=… evidence=[…]`, which takes the opposite side. A case file holds one position for each side. An engineer who finds the spec can't be met as written opens one against the spec instead of patching the behavior (CASE5). An open case file blocks nothing (CASE7).

- **Who argues (D49):** only those who belong to the kolab's work, holding Write on a layer of it. A session whose actor holds only Read there (anyone reading a public kolab, say) can't open or argue a case file, and sees no case files, positions or rulings: row-level security admits them only for a session that belongs (`kj_session_belongs`, 0013), and the instructions give it no precedent.
- **The other side** is someone else's: never the opener's own person, nor one of their agents, since one person and their agents are one side. The opener sees who took it, and which side.

A **ruling** (CASE2–CASE6) is given with `konjir_rule`:

- **On a case file:** `case=<id> verdicts={"<position>":"sustained","<position>":"overruled"}`, once it holds both sides (D51). It sustains exactly one position and overrules the other, and its effect is the side the sustained position seeks (`effect`, if given, must agree). The case file is ruled, once.
- **Directly** (CASE3, D16): `address=kj:checkout#R1`, or a whole node, with no case file behind it, and an `effect` saying what it does. It is the way out for a case file whose other side never comes: any case file still open on the element is **superseded** by it (`case_file.superseded_by`), leaves the inbox, and reaches its parties' answers.
- Either way it has `text`, an `effect` (`change_intent` or `keep_intent`, CASE6), and optionally `replaces`, what it overrules in words. It records its author and its date (`ruling.ruled_at`, CASE4), and the layer's inbox is signalled, in the ruling's kolab.
- **Who rules (D51):** a person, never an agent (CASE2), from a session in the role that writes the element's layer, whose access in the kolab includes Write on that layer. On a case file, never a party: not one who holds a position on it, nor the person whose agent does. The database holds every new ruling to a person too (`kj_ruling_by_person`).
- **A ruling that changes the intent marks the element (D51):** a `ruled` mark on its node's live version, with a question to its layer. Neither can be cleared or answered by hand: the next version that amends or removes the element settles both (a ruling on a whole node, any revision). A ruling that keeps the intent marks nothing.
- **Nothing is rewritten or removed** (`kj_case_fixed`): a ruling never changes and is never deleted; a later ruling says what it replaces. A position keeps its claim, evidence and side, and gets its verdict once, only once its case file has a ruling; a case file keeps its subject and question, is ruled only with its ruling row, and takes no position once it isn't open. Deleting or truncating any of the three is refused.

Rulings are **precedent in their kolab only** (CASE4, TEN13), for those who belong to its work (D49): `konjir_operating_instructions` lists the session's kolab's newest 20, `konjir_read_node` shows each beside its element (with the element's open case files), and `konjir_list_rulings` lists them all. Open case files wait in the inbox of the element's layer (`cases`), and each actor's answers carry the case files they opened or argued, most recently changed first, with their rulings. Kolab writes case files, positions and rulings as `kj_system`, after its checks. Migration 0013 adds the date, the effect, the side each position takes, who opened a case file on what question and when, the `superseded` state and the `ruled` mark (both value lists, D40), the rules above, and the indexes the reads use. Rows written before it keep no date or side: nothing is guessed, and its checks bind new rows only. A duplicate ruling or position among those rows stops the migration, naming it.

## Removing links

A link's owner removes it in a draft of its node (D48: the owner of an orphaned link "re-points or removes it"; D50). `konjir_unlink node=<node> version=<draft> links=[…]` removes links in a draft the session wrote, and `konjir_draft`'s `unlink` does it in the draft it writes. Each link is named by its id (`edge` in `konjir_lineage`, `link` in `konjir_list_stale`) or by its source element and target address, whose version is ignored; without `kind`, links of every kind between the two go.

- **Part of the version.** A draft records each link it drops (`link_removal`, migration 0012). Nothing changes until the version commits: its reviewers see the removals in `konjir_read_node` (`removes_links`), and a draft sent back, abandoned or rejected changes nothing. Removing links is refused once the version is in review.
- **At the commit**, the links it was built on carry forward without the removed ones (CAS3). Each removed link's open mark settles, `its link was removed by <node>@<version>`, with the marks it alone caused (LNK5), so removing an orphaned link settles its mark (LNK6). A transitive (`upstream_dirty`) mark at or below the removed link's source element keeps each cause only while that cause's walk still reaches it without the link, and clears with its last (LNK5).
- **A link the draft declared itself** goes at once. Linking a removed link again in the same draft takes the removal back.
- **Re-pointing** happens only in a draft, reviewed with it: a committed version's links never change (VER1). Linking, in a draft of your own, an element to the current words of a target element replaces the link of the version the draft is built on that has an open `orphaned` or `fuzzy_reanchor` mark, from the same element, of the same kind, to the same target element, quote for quote or whole for whole. The draft drops the marked link in the same transaction that adds the new one, and the mark settles when the draft commits. A `changed` mark is never settled this way, and a second, narrower link stands beside the first. Of two such quote links, the one whose prefix and suffix the new quote keeps is replaced; if that doesn't pick one, the link is refused, and the owner names the one to drop with `konjir_unlink`. Another writer linking from someone's draft adds a link, as before.
- **A link targets its node's live version** (its latest committed one), never an older version where words since changed still stand.
- **Removing the element** drops its links, as before, and now settles their marks and every other open mark on it, `its element was removed by <node>@<version>`: no mark moves onto an element its version doesn't have.
- **Folds and the outbox.** A draft overtaken by Kolab's rebases is folded with its removals (CAS7). The removal runs in the commit's `after_commit` job, so a cascade stopped part way and run again removes the link and settles its mark once.
- **Rulings (D47).** `konjir_admin_apply_ruling … unlink=[…]` drops links of the node's live version, with targets in the node's kolab, and commits as rulings do.
- **Row-level security.** As `kj_agent`, a session records removals, and deletes links, only on a draft of its own, in its layer and kolab.

## How each decision is implemented

**1. Addressing.** An address is `kj:[<kolab>/]<node>[@<version>][#<element>][~q(<selector>)]` (see *Addresses*). Every edge stores the fingerprint of the content it addressed when it was created. On an upstream commit, Kolab re-resolves each address against the new version:

- **Same fingerprint:** the edge is re-pinned. This is a pointer bump, not a mark.
- **Different content:** the dependent gets a `changed` mark.
- **A span that changed:** a `fuzzy_reanchor` mark. That is a near match (edited wording), or the exact words without the prefix or suffix they were quoted with, such as a copy in another statement (D42). The exact words with that context still around them, anywhere in the element, re-pin cleanly.
- **Gone:** `orphaned` mark.

An element address covers that element's subtree, so addressing a section means addressing its requirements too.

For a quote under 10 characters whose prefix and suffix both still stand verbatim, each strong (two words or eight letters), with a short gap between them (at most twice the quote's length plus 16 characters, with no sentence's end in it), the gap is the quoted words, edited, if it is still at least 0.5 similar to the quote: "7 days" become "14 days" (0.71) is a `fuzzy_reanchor` mark, a change, not an orphan (ADR8). A rewrite between the context words ("7 days" to "never") stays an orphan. The exact words with their context are still exact (D42).

A span's context is its prefix and suffix. It agrees when more than half of the words on one side still sit next to the quote, and either at least two of them do, or both sides agree. One word or punctuation alone is too little. `link` accepts only a target that resolves exactly, and quotes of at most 1,000 characters. When it refuses one, it suggests the current words with several words of context either side.

**2. Overrides.** Every delta records its base: the parent version and fingerprint it was written against. When a parent commits, each live child is rebased:

- Untouched elements are inherited.
- An override whose parent text now matches the child's text is retired as converged.
- A changed override goes `dirty` but keeps applying.
- A deleted one goes `orphaned` but keeps applying.

The rebases run in the background, after the parent's commit returns: Kolab's outbox worker rebases each variant in a job of its own, level by level, built on the variant's version as it is when the job runs (P6, D43; see *Durable waits: the outbox*). The rebased child commits after Kolab's structural checks alone, without review (VER12, D19): no person wrote it, so there is no author to review against. A conflicting override is still marked and asks its question. Resolving a dirty override records precedent, and the same `(base, parent, child)` triple then resolves itself on the next rebase; a resolution that waits in review records it, and settles its mark, when it commits.

**3. Roles.** A session activates exactly one role, and an actor has at most one open session (NIST dynamic separation of duty). Each agent is an actor of its own, so the rule holds per agent, and one person's agents can each hold a session at once. Kolab rejects writes outside the session's layer. Row-level security repeats the check in the database: agents may only *draft* (never commit), only in their session's layer, and only on a node of that layer, and they may only declare edges from their own layer. They write only as their session's own actor and role: a version, element, delta or question can't be authored as anyone else, an agent's owner included. And they read and write only in their session's kolab, and write only the layers their access covers (see *Accounts, kolabs and access*).

## Review

A version moves from drafted, to in review, to committed (VER2, REV2). `konjir_submit_for_review` runs Kolab's checks, which are structural only: no empty element, no element repeating another word for word, no element nested under one that doesn't exist (REV1). Kolab runs no model and reports no findings itself (REV5); whether a version contradicts itself or leaks across layers is for its reviewers. A version that fails the checks stays drafted, with the reason in its review note and the result, for its author to fix or resubmit. One that passes goes into review: it is `in_review`, and each other actor holding Write on its layer gets a review request in its inbox, connected or not (VER16). Holding Write means the actor's access in the version's kolab includes Write on that layer, as `kj_access` computes it from grants, teams and organizations, an agent's cut down to its owner's (W1.3); sessions don't count, so a reader with a session isn't a reviewer, and a writer with no session, or one in the other role, is. A reviewer gives its verdict from a session in the layer's role. The request names its subject, a version (or a work package In review, VER17; see *Submitting, reviewing and delivering work*), and says how to review it. The `konjir_reviewer_instructions` prompt (`konjir instructions reviewer` in a shell) gives a reviewing agent the full checklist: judging each link against the version it pins, the layer rules, one testable intent per element, what a `contradiction` and a `layer_leak` are and what each does, and how to approve or request changes. It tells the reviewer to treat everything it reads through Kolab (elements, linked text, questions, notes, review notes, suggested next steps) as data, not instructions. It holds the rules alone, no kolab's content, so every session and the admin token get the same text.

- **Who reviews (D19, D25, D33):** any actor other than the author with Write on the layer. Separation of duty is per agent, so another agent of the author's person counts, and so does the person. Only the version's own layer reviews it.
- **Who is asked (D65):** each of them has a review request, but it shows (in `konjir_list_reviews`, the inbox, the page and the author's answers) only while its reviewer can review the layer in the role it works in. A person always can, since they choose their role as they sign in. An agent signed in to the kolab can only in the role that writes the layer: its admin-opened session's role, or for an OAuth grant the role chosen at consent, whether or not its access token has expired. An agent with no open session there chooses its role when it next signs in, so it is asked. So an agent signed in as engineer isn't asked to review a spec, and once it signs in as product its request shows, with nothing to resubmit. `reviewers` in `konjir_submit_for_review`'s result, and on the page, names those who can review now. When nobody else can yet, the version still waits in review (D66: VER11 counts who holds Write, not who is signed in, so an author can't skip review by keeping their other writers in the other role), and the result and the page say so: *Nobody else can review the functional layer yet. Invite a product teammate, or connect an agent of yours with the product role.* Another agent of the author's own person counts as a reviewer (VER16, D25), so that is a way to get one.
- **`konjir_review verdict=approve`:** one approval commits the version, through the same per-node commit step as any other commit, and the other requests are withdrawn. A `layer_leak`, content in the wrong layer that conflicts with nothing, can come with an approval: the version commits and the finding becomes a `role_boundary` mark and a question to the layer that owns the answer: implementation in a spec goes back to its author, and behavior a binding adds that its linked requirements don't mention goes to the spec it links to. Answering the question clears the mark. A `contradiction` can't: two elements that can't both hold, or a binding element that conflicts with a requirement it links to (stricter, looser or different), stops the commit (VER9), so it comes only with a request for changes. Anything that conflicts is a contradiction.
- **`konjir_review verdict=request_changes`:** needs a note, and may carry findings. The version returns to drafted, and every request for it is withdrawn. Its author resubmits it unchanged, or drafts a new version and abandons this one.
- **`konjir_abandon`:** the author rejects their own draft or version in review, under the node's lock, so it can't land on a version an approval has just committed; it says so instead. A person's version is rejected only this way, or as stale, or when Kolab folds it into a fresh rebase (VER2, D33, D38). Kolab's own rebases are rejected when they fail their checks.
- **Plan versions (VER3, PLN2):** a `plan` version commits after structural checks, without review, whoever else holds Write on the technical layer.
- **Reviewers gone:** resubmitting a version that waits in review asks whoever can review it now, adding requests for new reviewers and withdrawing those of actors who no longer can (their Write was revoked, say). If no one else holds Write any more, the checks alone commit it, unreviewed. An author who lost Write meanwhile can't get it committed: entering review and committing both re-check the author, under the node's lock, and reject the version instead.
- **No reviewer (VER11):** when no one else holds Write on the layer, whatever role anyone is signed in with, Kolab's checks alone commit the version, and its review note says it committed unreviewed. A solo project works as it did before review existed.
- **Kolab's own rebases (VER12):** commit after structural checks only, with no review request.
- **A ruling applied to the mirror (D47):** `konjir_admin_apply_ruling ruling=D46 actor=mirror-product node=kolab/kolab-binding elements=…` (or `deltas=…`, and `parent=` for a variant in the node's kolab) writes a version as that actor (who must hold Write on the node's layer in its kolab), in the role of that layer, and commits it after structural checks only, with no review request: the ruling is already the approval. Its review note records the ruling and who applied it: a Konjir admin's own raised session, by name, or the break-glass admin token (W2.22). An admin's verbs work in no kolab, so `node` is `<kolab>/<node>`, or a name alone only when no other kolab has a node of that name (otherwise it is refused, naming the kolabs that do), and `committed` is the full address. It goes through the same per-node commit step as any commit, so it is rejected as stale if the node moved on, and it makes anything waiting in review on the node stale. Only a Konjir admin's raised session, a person's, or the break-glass token reaches it (D47, D69). An agent session is refused, and no session is raised by anything an agent can call: only its person's browser, signed in to their GitHub account (its account picker, not a password or 2FA check) and confirming on Kolab's page, raises one (see *Konjir's admins*). So no agent can use it to skip review.
- **While a version waits in review**, the W1.17 rules hold. A commit by anyone else to the node rejects it as stale at once, and its requests leave the inboxes. A rebase of Kolab's own doesn't: at approval, the approved version is folded onto the rebase, and the fold commits on structural checks, since its edit was reviewed. In the same transaction, under the node's lock, the version it folds is settled as `folded into` the fold, and its approval is copied onto the fold, so the author's answers show the fold committed with it; if the author abandoned the version meanwhile, the fold doesn't commit. A fold carries the version's override resolution too. A draft overtaken by Kolab's rebases before it was submitted is folded at submission, and the fold goes into review itself.
- **Inboxes:** a review request in the reviewer's layer inbox signals that inbox, and each verdict signals the author's answers, with the same events as questions and marks. The Konjir channel turns a new request, or a verdict on the session's own submission, into a message.

### Durable waits: the outbox

Every wait in review and the question tier is a row: a version in review and its requests (`review_request`), each verdict, each question and its answer. What a change still owes once it commits is a row too: a job in the `outbox` table (migration 0010), written in the transaction that makes the change, so it exists if and only if the change committed. A server restart mid-review loses no request or verdict, and the work they owe is done once.

- **`after_commit`:** each version that commits owes its cascade (stale versions in review withdrawn, edges carried forward, marks raised and spread, its own catch-up) and the layer leaks its reviewers reported with `konjir_review`, as `role_boundary` marks and questions. The commit step writes the job as it commits the version.
- **`rebase`** (migration 0015, P6, D43): each variant whose live version sits on an older version of the node that committed owes a rebase. The commit step writes one job per variant, unclaimed, in the same transaction, with a `work` notice, and the commit returns once it is committed, with `rebases`, the number queued (`rebases_queued` over MCP). The worker runs them; see *Rebasing in the background* below.
- **`settle`:** a version that something committed past while it waited owes its fold onto Kolab's rebase, or its rejection as stale if someone else committed: an approved version (the transaction that records the approval writes the job), a ruling applied through the admin token (D47; its commit step writes it), and a submitted draft. Kolab's own rebases owe nothing: an overtaken one is dropped at once.
- **Answers** need no job: an answer, the boundary mark it settles and the asker's `query_answered` mark are written in one transaction. So are a resolution's version and the ruling waiting on it.

**Claims.** The process that writes a job claims it as it writes it, runs the work at once, in the caller's call, and deletes the job when the work is done, so a commit's caller still sees its cascade finish or fail with a `CascadeError`. Each claim carries a token, fresh for each claim, and the claimant renews, deletes and releases the job only by that token, so a process whose claim lapsed and was taken by another touches nothing of it. A claim lasts 30 s and is renewed every 10 s while its work runs, on PGlite too. A renewal that finds the claim gone, or that fails for a whole lease, marks it lost and logs it: the work stops at its next step (before each variant's catch-up, and before the layer leaks), and the process that took the job does it, once more. A process never takes over a job it is running itself, even if a busy event loop let its lease lapse. A job a stopped process held is free when its claim lapses; on PGlite, the first Kolab in a process to open a data directory frees every claim in it at once.

**Failures.** A job whose work fails is freed with its error (`last_error`), to be tried again after a backoff that doubles from 1 s to 5 minutes. After ten attempts it is `dead`: no worker takes it again, an error is logged (one JSON line with `event: outbox_job_dead`, which the `outbox-job-dead` alarm counts; see *Logs and alarms*), and `konjir_admin_outbox` lists it (`state=dead` for those alone) until `konjir_admin_outbox retry=<id>` makes it due again.

**Order.** A node's cascades run in the order its versions committed, each carrying the one before it forward. Before a version's cascade, an earlier one its node still owes runs first, if it is free and due. If it is held by another live process, waiting out a backoff, or dead, the later cascade waits instead: the commit returns with `cascade: 'queued'`, its job is released with a `work` notice, and it runs once the earlier one is done (the process that finishes a cascade runs the next of its node; one that releases a waiting job after the earlier one finished runs it itself), never ahead of it. A cascade run late re-checks only the links pinned to versions older than its own, so it never touches a link that a newer version, or a dependent's catch-up, has re-pinned.

**The worker.** `konjir serve` runs Kolab's outbox worker (`Kolab.startWorker`). It runs every due job as the server boots, then again whenever a job falls due or a claim lapses, and at least every 5 s. Several processes on one Postgres database share the outbox: each job is claimed by one at a time, with `for update skip locked`. A process that frees a job, because its work failed, an admin retried it, or the process is closing, says so with a `work` notice on `konjir_events` (`{"from": <origin>, "work": true}`), in the same transaction, and every other process's worker looks again. This release ignores notices of kinds it doesn't know, and fields it doesn't know on those it does; releases before it drop and log a `work` notice as not a Kolab event, so during a rolling deploy from one, its log shows a dropped notification for each job freed, and nothing else goes wrong. Closing a Kolab stops its worker, waits up to 10 s for the outbox work it is running, then frees the claims it still holds.

**Idempotent work.** A job run again after a stop part way through does each thing once. Each mark is raised with its question, and each direct mark with its transitive marks, in one transaction. A layer leak, and a variant's `rebase_failed` mark (D44: at most one open), are checked for and raised in one transaction under the node's lock, so two runs that overlap raise one. Each link is checked again, and marked, in one transaction under its dependent's lock. A fold a stopped run already made, in review or committed, is the settle job's result: the version is settled as folded into it; one it wrote and never committed is rejected before the version is folded again. The version itself commits at most once, since it commits only from the state it was in.

The outbox is Kolab's internals: no agent reads it (`kj_agent` has no grant on it). `libs/engine/test/outbox.test.ts` stops a Kolab between steps, by closing its database under it, and opens another on the same database, on PGlite and Postgres; it also covers a lost claim, a cascade waiting behind one that is held or failing, a dead job retried, an interrupted ruling and a close that waits.

**Rebasing in the background (P6, D43).** A parent's commit no longer rebases its variants in the caller's call. Its commit step writes a `rebase` job for each variant behind it, in one statement, and the commit returns. A variant has one job waiting at a time: one already waiting covers it, and a commit by the variant itself deletes it, since that version's own catch-up owes the rebase. If a worker is running the variant's job when the parent commits again, the job may have read the older parent, so the commit sets `again` on it, and the job runs once more when it is done, whether its rebase passed or failed: no parent commit is lost. A dead job blocks nothing: the parent's next commit revives it. When a job dies, its variant gets a `rebase_failed` mark and question (D44). The cascade lists the variants again once the commit is visible. That catches a variant whose first version committed at the same moment, which the commit step's list couldn't see while its own catch-up couldn't see the commit (on Postgres). A variant whose rebase onto this version already failed and marked it gets no second job. The worker takes jobs oldest first, one variant per job, and each job rebases whatever the variant has live when it runs, onto whatever its parent's latest is then, never a list taken earlier (catch-up). The rebase goes through the same per-node commit step as any commit (W1.17): it commits after structural checks only (VER12), consults precedent (OVR9), is dropped if overtaken, and leaves one `rebase_failed` mark and question if it fails for the variant's own reasons (D44). As it commits, it writes its own variants' jobs, so the worker rebases level by level. A person who edits a variant while its rebase waits commits as usual, and the variant's own catch-up rebases their version at once. A rebase a stopped process had drafted but not committed stays drafted, and the job, run again, rebases the variant afresh. What waits is visible, while the variant is behind its parent: `konjir_read_node` shows its `rebase` (pending or dead, attempts, the parent version that queued it, if it's in the reader's kolab, and the last error), `konjir_list_nodes` marks it `rebase_pending` or `rebase_dead`, and `konjir_admin_outbox` lists each `rebase` job with its subject and `after`. A check that a variant may be rebased at all goes in `mayRebase`, which every path that rebases calls first. A test or script runs queued work at once with `Kolab.drainOutbox()`. `@konjir/engine/testing`'s `openKolab` and `setup` drain after each committing write, so a scenario reads a commit's rebases at once, unless opened with `queued: true`; `libs/engine/test/async-rebases.test.ts`, the queued property test and the outbox tests leave the queue alone.

## What the prototype found

**Element addressing has to be on both ends of an edge.** The measurement, at N = 100 requirements with one edited:

| Addressing | Dirty versions |
| --- | --- |
| Version scope everywhere | 202 of 202 (lockstep) |
| Element *targets*, whole-version sources | 202 of 202 |
| Element targets **and** element sources | **4**, at every N |
| Same, but the plan derives from the whole binding | 202 of 202 |

Pointing at the changed requirement isn't enough. The edge must also say *which part of the dependent* relies on it, or the dirt spreads to the whole dependent version and everything downstream. One whole-version hop anywhere in a lineage collapses back to lockstep.

**Concurrency needs an explicit rule.** Each version records its base: the node's live version when it was drafted, which it was built on. It commits only while that is still the node's live version. Each node's commit step checks this and sets the version committed in one transaction that holds a lock on the node's row, and every write of a new version takes its number under the same lock. So two commits to one node can't both build on one version, and version numbers never collide. A draft can be overtaken while it's open, while Kolab's checks run, or while it waits in review:

- **Overtaken only by Kolab's own rebases:** the draft is folded into a fresh rebase, keeping its author and declared edges.
- **Overtaken only by Kolab's own rebases:** the fold is built on the newest of the versions just judged, so a commit that lands while it is being made overtakes the fold in turn.
- **Overtaken by another person's commit:** the draft is rejected as stale, to be redrafted. `commit` throws a `GateError`, and `konjir_submit_for_review` returns `stale: true` and says to re-read and redraft. The caller never gets a raw database error for losing a race.
- **A rebase of Kolab's own that was overtaken** is dropped, and the variant's live version is caught up onto the parent's latest version on the spot.

A parent's commit rebases each variant's live version as it is when its turn comes, never the version it listed. A rebase that fails for the variant's own reasons (its checks refuse it, or throw) marks the variant `rebase_failed`, with a question, and the parent's commit carries on to the rest (D44), so an inbox tells a failed rebase from a rejected review. A variant holds at most one such mark: a later failure re-points it at the newer parent. The mark and its question settle once the variant's live version sits on the parent's latest version, whether through a rebase that passes or the variant's own commit with `parent` set to that version. Migration 0004 renames every `review_failed` mark of earlier releases to `rebase_failed`, since all of them came from failed rebases. On each variant it keeps open only the mark naming the newest parent, which is also the mark the engine re-points, and moves it to the live version. It settles the mark if the variant already sits on its parent's latest version, and asks the question where none was written. Any other failure, such as a lost connection, or a failure in the cascade of a version that did commit, stops the cascade: the caller gets a `CascadeError` saying which version committed and what didn't finish. Its `after_commit` job stays in the outbox, and the worker runs the cascade again after a backoff (see *Durable waits: the outbox*). A later commit of the same node succeeds, but its cascade waits for that one, in commit order, and its result says so (`cascade: 'queued'`), so until the retry, a success can stand over variants left behind. The variant's own next commit still catches the variant up. A draft left open across the upgrade to migration 0003 has no recorded base, so it is rejected as stale on review if its node has any committed version, and must be redrafted. `libs/engine/test/concurrency.test.ts` drives each race that `npm run rebase-storm -- --races` reproduces, on PGlite and Postgres.

**Property tests check the cascade and rebases (W2.5).** `libs/engine/test/properties.test.ts` uses [fast-check](https://fast-check.dev) to generate a family of prototypes (a spec's own variants live in other kolabs, KON9) and a sequence of edits to it. The family has:

- a parent with a nested element
- a variant of it, and a variant of that variant, which itself depends on the binding
- a binding of the kolab's spec linked into all three, including a cycle with the nested variant
- a second binding linked into the first, and its plan, whose work packages are linked into it

The edits are parent commits that change, delete and restore elements, variant overrides, edits of marked elements, clears, override resolutions, links removed in a draft (with or without an edit of their element) and links linked again. A stand-in for review, the test's own submission checks, rejects some of them.

After each step the test compares Kolab with a reference model (`libs/engine/test/cascade-model.ts`), written from the spec rather than the engine. It checks:

- every element's text
- every override's state: clean, retired, dirty or orphaned
- exactly which marks are open, each on its node's live version, and that a mark carried forward keeps its id rather than being raised again
- one open question per dirty or orphaned override and no other, and a resolved question answered with the ruling by whoever made it
- every link: either pinned to its target's live version with a matching fingerprint, or carrying an open mark, and a removed link gone from the live version

The seed is fixed, so CI runs the same sequences every time: 25 on PGlite and 60 on Postgres, which runs them about twice as fast. Three environment variables change that: `KONJIR_PROPERTY_SEED` changes the seed and `KONJIR_PROPERTY_RUNS` the number of runs, to replay a failure or search harder; `KONJIR_PROPERTY_SHRINK=0` stops at the first failure instead of shrinking it.

The model makes three readings of the spec on purpose:

- **A link that already carries an open mark isn't re-checked by later commits.** CAS1's "each live link" is read as each link not already marked. Its owner settles the mark (LNK6), even if the target goes back to the pinned text, or is deleted after it changed.
- **A link whose target is gone can't re-pin.** Revising its element doesn't settle the mark (CAS4 says "clears that mark and re-pins its link"), and clearing it is refused: its owner re-points or removes it (D48; see *Removing links*).
- **When two rulings share a (base, parent, child) triple, the first stands.**

The tests found six bugs, now fixed, each with a regression in `libs/engine/test/property-regressions.test.ts`:

- **A mark didn't spread through a link that carried a mark of its own.** Such a link stays pinned to an older version. Clearing the link's mark then left its element clean while what it relied on was dirty. The walk now follows live links into any version of the node it reaches. Migration 0012 indexes `edge(target_version_id)` for it, with `edge(source_version_id)` and the open-mark lookups: measured on Postgres over 38,400 links, a step of the walk went from 11.7 ms to 0.4 ms, and the links a commit re-checks from 6.7 to 0.9 ms.
- **A self-settled override left its question open.** When a dirty or orphaned override came out clean on its own (its parent went back to the text it was written against, converged on it, or the variant overrode it again), its mark cleared but its question stayed open, where nothing could answer it. Kolab now answers it as `kolab`.
- **An override moving between orphaned and dirty kept its first wording.** It kept the mark and question it was first raised with. Both are now reworded.
- **A resolution's precedent was recorded after its own cascade.** So a variant of the resolved variant, rebased by that cascade with the same (base, parent, child) triple, was asked again. The ruling is now recorded in the transaction that commits the resolution, before its cascade: the precedent, and the mark closed with its question answered by the ruling and its author. Nothing is visible while the resolution is in review, however long that takes: the ruling waits on the resolution's version (`version.resolves`, W1.6), and a fold of the resolution carries it. Of two resolutions of one mark, only the one that commits records anything.
- **A variant's commit settled marks on overrides it only carried forward.** It counted every element with a delta as revised. Only elements whose text or place in the tree changed from the node's previous version count now.
- **Revising an element didn't settle its upstream_dirty marks**, though LNK6 and CAS4 say revising a marked element settles its mark. It now does, as a clear would.

**Agents can use it unaided.** Two separate agents were given only a token and the `konjir` command, with no access to the source. The product agent wrote and committed a password-reset spec. The engineer agent bound it to a Node/Postgres/Redis stack and linked each of its 11 elements to the requirements it serves. It then found two real ambiguities (which sessions survive a reset, and whether earlier reset links die) and asked them instead of deciding. The product owner ruled, and the product agent answered and amended the spec. Exactly the three binding elements tied to the amended requirements went dirty. The engineer revised them and cleared all three marks.

Their feedback drove these changes:

- per-verb help
- `key=value` on every verb
- links declared inside a draft
- partial edits by delta
- `mine=true` on questions
- a gate that says what it checked
- plain errors when Kolab is down or a token is refused
- editing a marked element counts as addressing its mark

## Deliberate simplifications

- **Semantic review is only as good as the reviewers.** Kolab's own checks are structural, and they say so; contradictions and layer leaks are caught only if a reviewing agent reports them. A version with no other writer on its layer commits on the structural checks alone, unreviewed (VER11).
- **Review waits aren't durable yet** (W1.8). A review request and its verdict are rows, so a restart keeps them, but nothing retries a commit or cascade an approval started if the process stops part way, and a version whose only reviewers lose Write waits until its author resubmits it (which commits it unreviewed) or abandons it.
- **The reviewers are those of the moment** the version is submitted or resubmitted; one who gains Write later can still review it, and its request is added on resubmission.
- **Review requests are readable by every session in their kolab**, like versions and questions there: their notes and findings included. Product review of bindings (VER13) and editorial commits (VER14) aren't built. The web interface shows no work review request yet: reviews of work packages reach a reviewer through `konjir_list_reviews`, the inbox resource and the channel (VER17), and the web board waits for M6 (D98).
- **Hand-issued session tokens are bearer tokens** that last 30 days (W2.22); Kolab stores only their hashes. They're fine on one machine or a trusted network, but not on the open internet. OAuth's access tokens, which GitHub sign-in issues, expire in 15 minutes (D55). The konjir CLI and the channel bridge sign in through OAuth (W3.4, W3.5), and take a hand-issued token only as an override.
- **The web interface** works in one kolab per session: it moves between the kolabs a person reaches by ending the session and opening another, and doesn't read other kolabs' committed work in place (D49 would allow it). A person's first session still comes from an admin. It has no case files or rulings beyond resolving overrides until their verbs exist (CASE5–CASE7), no way to declare a link (agents declare them), though a draft can drop one (*unlink*, as `konjir_draft`'s `unlink`), and its activity shows when versions were written, not committed, and not when questions were answered, since Kolab doesn't record those times.
- **A few reads aren't paged yet (W2.21).** A node's page in the web interface shows every question on the node and every version of it, and `read_node` reads all of a node's questions before it shows each element's newest 20. The access list and the invites come whole. Nothing limits how often an agent asks or drafts, so these grow with use.
- **Prototypes are kept in sync one way (W4.1).** A spec change marks the screens that show it, but a prototype's change doesn't yet ask the spec (D79's other half, W4.4 per D95), and Kolab doesn't check that a screen holds a URL or an uploaded page (uploads, FIL, aren't built). A binding serves its own kolab's spec only: a binding of another kolab's spec forks it first (KON9).
- **Identity of derivation is relaxed:** a content-identical upstream commit re-pins edges instead of minting new downstream versions.
- **Precedent applies on a child's next rebase**, not immediately to other open marks.
- **The cascade isn't durable.** A commit's cascade runs after it commits, in the calling process. If that process stops part way, or the cascade stops on a `CascadeError`, variants it hadn't reached stay on the old parent, with no mark, until the parent or the variant commits again.
- **Case files and rulings** (see *Case files and rulings*): a ruling that changes the intent marks the element but doesn't amend it: its product side amends and commits it, and the cascade does the rest. Rulings are served beside their elements, in the instructions and in a pulled work package's context (PLN14), and an open case file on a binding element a package delivers blocks pulling it (PLN19); override precedent isn't in that context yet. Lee's Decisions Log entries aren't recorded as rulings by `konjir_admin_apply_ruling`, which applies them only. `ruling.verdict` is legacy, kept for rulings stored before CASE2 gave each position its own (`position.verdict`).
- **Tenancy is partial (W1.3, W1.4).** Addresses carry the kolab and node names are unique per kolab (W1.4), but a session can only read across kolabs: it can't link to, fork from or ask about another kolab, and there is no mark for lost access (LNK8), since those wait on a binding decision. Nodes can't be renamed, so there are no aliases yet (ADR11). A session works in exactly one kolab, and an actor still holds at most one open session, so an agent works in one kolab at a time; its token is its session, scoped to that kolab and its role, and its level comes from its grant. Kolabs can't yet be transferred (TEN5), visibility and base permission are set only when a kolab is made, kolabs, organizations and actors are archived rather than removed (D52), and accounts, teams and kolabs can't be renamed; teams can't be archived. Only the admin token manages tenancy: a kolab's own Admins can't yet grant access through Kolab.
- **Push is a signal, not a message.** Kolab signals an inbox over `subscriptions/listen`, and the agent reads what changed. Under the 2025 protocol, which has no listen stream, agents still poll `list_stale` and `list_queries`. In Claude Code the Konjir channel, a local stdio bridge, pushes it into the session (channels don't work over HTTP); channels are a research preview, so it loads as a development channel. Elsewhere, `konjir watch --once` (see *Questions, notes and push*).
