Prototype of Konjir's engine and its delivery rails:

- **Kolab:** versioned specs with stable element IDs, the invalidation cascade, child-spec overrides with the three-way rule, the review gate, and role enforcement. It implements the three decisions in *Konjir — Open Design Decisions*.
- **An MCP server:** stateless Streamable HTTP, MCP spec 2026-07-28, with the SDK's fallback for 2025-era clients. It's a NestJS app; each verb is an `@McpTool` method, the inboxes are `@McpResource` methods, and the operating instructions and the reviewer's instructions are `@McpPrompt` methods.
- **An OAuth 2.1 authorization server** for the MCP endpoint and the web interface, with GitHub as the identity: a person signs up and in with GitHub, and their client gets short-lived access tokens that refresh (D55). See *Signing up and in*.
- **A `konjir` CLI:** the same verbs for a shell or any harness without MCP. It is an MCP client of Kolab, so there is one backend.
- **A web interface:** a React and Vite single-page app that Kolab serves at its root, kept live with server-sent events, for a person who never opens a terminal (W3.1, API8). See *The web interface*.

TypeScript on Postgres, through [Kysely](https://kysely.dev). Give `konjir serve` a `--database-url` (or `KONJIR_DATABASE_URL`) for a Postgres server. Without one, Kolab runs on embedded Postgres ([PGlite](https://pglite.dev), Postgres in WASM), so local development needs no server.

## Changing the schema

The schema is the SQL files in `libs/db/src/migrations`, applied in order (DAT2). `0001_schema.sql` is the core schema; each later file changes it. When Kolab opens a database, it applies the files it hasn't recorded yet, in one transaction under an advisory lock. It records each one in the `kj_migration` table, with the sha256 of the file's text. A second Kolab process opening the same database waits for the first, then finds nothing left to do. A migration that fails rolls the whole open back, and the error names its file. Kolab refuses to open a database in two cases:

- it's recorded at a migration this release doesn't have
- a recorded file's text has changed since it was applied

The error names the file.

A database made before migrations began has Kolab's tables but no `kj_migration` table. Those are PGlite data directories from release 0.5 on, and the test server's first RDS database. Kolab runs `baseline.sql` on it once, which brings it to 0001 with idempotent statements. It then records 0001 as baselined, with 0001's checksum.

To change the schema:

1. Add `libs/db/src/migrations/NNNN_what_it_does.sql`, numbered one past the last file. The name must be four digits, an underscore, then lowercase letters, digits and underscores. Any other `.sql` file in the folder stops Kolab loading, so a misnamed migration can't be skipped.
2. Never edit a file that has shipped, not even a comment, and never edit `baseline.sql`. An edited file would never reach databases that already ran it, so Kolab refuses them instead. `libs/db/src/migrations/checksums.json` pins the sha256 of every `.sql` file in the folder. Kolab refuses to load if any file differs from its pin, has no pin, or is pinned but missing. The release ships only a commit's tracked files (`deploy/release/pack.sh`), and Kolab's own checkouts and tests load whatever is in the folder, so this check is what keeps a draft migration from loading or shipping unpinned. Add the new file's checksum there (`shasum -a 256 <file>`) when it's ready to ship, and never change an existing one.
3. Write plain SQL that runs once. It doesn't need to be idempotent. Every file runs inside the runner's one transaction, so a file may not contain `begin`, `commit`, `rollback`, `end`, `abort`, `start transaction`, `savepoint`, `release` or `prepare transaction`. Kolab rejects such a file when it loads. The same words are fine inside comments, string literals (including `E'…'` strings), quoted identifiers, and dollar-quoted bodies: `do $$ … $$` blocks and `as $$ … $$` functions. Write a function's body dollar-quoted, not as a SQL-standard `begin atomic … end` body, whose `end` the check can't tell apart. Avoid statements that can't run in a transaction, such as `create index concurrently`. Statements that create roles must guard against another database on the same cluster creating them first, as `0001_schema.sql` does.
4. **A new table** gets no rights by itself. The engine writes as `kj_agent` or `kj_system` through `set local role`, so grant each what it needs explicitly. If the table holds kolab data, give it a `kolab_id` that references `kolab`, not null, set from its parent by the `kolab_of_parent` trigger (`kj_kolab_of_parent`, from 0006) or by Kolab, and enable row-level security with policies like 0006's: `kolab_read` for `kj_agent` (`kolab_id = kj_session_kolab()`), `system_all` for `kj_system`, and for anything an agent inserts, an `agent_layer` policy plus a restrictive `kolab_write`. Grants on all tables are fine: Kolab revokes everything on `kj_migration` from `kj_agent`, `kj_system` and `public` after every migration.
5. **Value lists.** `MARK_REASONS`, `QUERY_KINDS`, `ACTOR_KINDS`, `ACCOUNT_KINDS`, `ORG_ROLES`, `ACCESS_LEVELS`, `VISIBILITIES`, `VERSION_STATES`, `REVIEW_REQUEST_STATES`, `OUTBOX_KINDS`, `OUTBOX_STATES`, `CASE_FILE_STATES`, `POSITION_VERDICTS`, `RULING_EFFECTS` and `ARCHIVABLE` in `@konjir/types` are also written out in the database's `invalidation_reason_check`, `query_kind_check`, `actor_kind_check`, `account_kind_check`, `org_member_role_check`, `kolab_grant_level_check` and `kolab_base_permission_check` (both `ACCESS_LEVELS`), `kolab_visibility_check`, `version_state_check`, `review_request_state_check`, `outbox_kind_check`, `outbox_state_check`, `case_file_state_check`, `position_verdict_check` and `ruling_verdict_check` (both `POSITION_VERDICTS`), `ruling_effect_check` and `position_seeks_check` (both `RULING_EFFECTS`), and `archive_event_kind_check`. A change to any of them needs a migration that drops the check and adds it again with the whole new list. The test "the database's value lists are @konjir/types' …" fails until there is one. Before removing a value, the migration must deal with the rows that use it.
6. Run `npm test` and `npm run test:postgres`.

The files ship as they are: the release runs `libs/db/src`, and `npm run build` copies them to `libs/db/dist/migrations`, so they are found from either.

## Running it with agents

```
# 1. Start Kolab. It persists to ./.konjir and prints an admin token.
bin/konjir serve --port 7420

# 2. Register a person, a kolab they own, and the agents they own, each granted access to it.
export KONJIR_URL=http://127.0.0.1:7420/mcp KONJIR_TOKEN=<admin token>
bin/konjir admin_add_actor id=lee
bin/konjir admin_add_kolab name=checkout owner=lee              # Lee owns it: Admin
bin/konjir admin_add_actor id=lee-pm owner=lee
bin/konjir admin_add_actor id=lee-eng owner=lee
bin/konjir admin_grant kolab=checkout to=lee-pm level=write layers='["functional"]'
bin/konjir admin_grant kolab=checkout to=lee-eng level=write layers='["technical"]'

# 3. Give each agent a session in the kolab (one actor, one kolab, one active role).
bin/konjir admin_open_session actor=lee-pm role=product kolab=checkout   # prints the agent's token
bin/konjir admin_open_session actor=lee-eng role=engineer                # kolab defaults to the one it can reach
bin/konjir admin_list_actors owner=lee                                   # an account's agents
```

Then point each harness at Kolab with its own token. The token decides who the agent is, which kolab it works in and which layer it may write. Tool arguments never carry identity.

Where Kolab has an identity provider (GitHub, D55), none of this needs an admin: a harness that speaks MCP's authorization, such as Claude Code, connects with the URL alone, and the person signs in with GitHub and chooses, on Kolab's consent page, who the harness works as (an agent of theirs, by default), in which kolab and role. See *Signing up and in*. Hand-issued tokens keep working beside it during the transition.

**A token is shown once (P1, D50).** `admin_open_session` prints it, beside the session's key, and nothing prints it again: `whoami` names the session by its key. Kolab stores no token. A session's id is its key, the sha256 of its token, base64url (`sessionKey`), and Kolab hashes the bearer token on every request to find its session; a key presented as a token finds nothing. Row-level security's `kj.session` carries the key too, so the token never reaches the database at all, and a check (`session_id_is_key`) refuses any id that isn't a key. To revoke a session, `admin_end_session` takes exactly one of its `token` (`kjs_…`), its `session` key (43 base64url characters) or the `actor` whose open session it is, and returns the key it ended. A token passed as `session=`, or a key as `token=`, is refused, naming the right argument, and so is a call that matches no open session, so a mistyped revoke never reads as a successful one. The MCP client a token connects as is named by its key too, never the token, and the admin token is compared in constant time. Migration 0011 hashed every existing session's id in place, so each token handed out before it, agents' included, kept working. It can't be undone (see *Deploying to AWS for testing*).

An actor is a person, or an agent owned by an account: a person or an organization. Each agent is an actor of its own: it holds its own session, so one person's agents can each hold one at the same time, and it is the author of what it writes. `whoami` names the agent and its `owner`, its kolab and its access there, and `read_node` gives each version's `author`, with the agent, its owner and its role. An actor's kind and owner never change once it's added, so past authorship stays as it was written. An id is letters, digits, `.`, `_`, `-` and `@`, and `kolab` is reserved for Kolab's own work. Two actors with Write on one layer of a kolab review each other's versions there (see *Review*): two product agents of Lee's with Write on the functional layer each wait for the other's approval.

`deploy/demo/run-local.sh` runs all of this end to end against a throwaway Kolab: two companies, a spec and its binding, reviews, questions, a spec change, a ruling and a restart. `deploy/demo/m1-walkthrough.mjs` runs the same walkthrough against any Kolab, given its URL and admin token. [`deploy/demo/DEMO.md`](deploy/demo/DEMO.md) says what each step shows.

### Accounts, kolabs and access

Kolab follows GitHub's model (D3). An **account** is a user or an organization, in one namespace: each person is a user, by the same id. An organization has **members**, some of them **owners**, and **teams**, which can nest and hold no konstructs. A **kolab** belongs to one account. Its name is unique across the whole database (`kolab.id`, its primary key, lowercase letters, digits and `-`), so a name another account has taken is refused (D7, D12). It is `private` by default, or `public` (anyone may read it) or `internal` (the owning organization's members may), and an organization's kolab may have a **base permission** that every member holds.

Access to a kolab is one of five levels, `read`, `triage`, `write`, `maintain` and `admin`. A `write` grant names the layers it covers, `functional`, `technical` or both; `maintain` and `admin` cover both, and `read` and `triage` write neither. A person's access is the most that any of these gives them: owning the kolab or being an owner of the organization that owns it (Admin), the base permission, a grant to them (a member or an outside collaborator), or a grant to a team they are in or to a parent of one. Teams are granted access only to their own organization's kolabs, and `kj_access` counts a team's grant only on a kolab its organization owns. Kolab alone refuses a base permission on a person's kolab, where it would give nothing anyway: it counts only for members of the owning organization. A session may write its role's layer only while its access covers that layer; with less, it can still read and ask.

**An agent never holds more access than its owner (TEN11, D30).** Its access is its own grant on the kolab, cut down to what its owner holds there: the lower level, and only the layers both may write. An organization holds all of its own kolabs and nothing in anyone else's, so its agents work only in its kolabs. Kolab enforces this in several ways:

- `admin_grant` refuses an agent a grant its owner lacks: a higher level, or a layer its owner can't write.
- A session's access is computed when it opens and on every use, from the grants as they stand. So an agent's session opens with no more than its owner holds, and it narrows the moment its owner's access does. An agent whose owner holds nothing in the kolab can't open a session there at all.
- Every change to grants, memberships or teams ends, in the same transaction, each open session that can no longer reach its kolab, and tells its listen streams so they close (D41). A narrowed session stays open. Those changes and sessions opening take one advisory lock, so a session can't open on access a concurrent change is removing. A session found with no access when it is used (after a change made outside Kolab's verbs) is ended then, and its streams are told.
- A draft commits only while its author may still write its layer: one whose author lost Write since drafting is rejected, whoever submits it. And submitting needs Write on the draft's layer: Read can't decide when someone's draft becomes truth.

Every row of Konjir data carries its kolab: nodes, sessions, versions, elements, deltas, edges, marks and their causes, questions, case files, positions, rulings and precedent. A child row takes its parent's kolab when it is inserted, whatever its writer gave. A session works in one kolab, and everything an agent writes or works on (a node it drafts, a mark, a question, a link's source) must be in it; a link's target and a variant's parent may be another kolab's committed version it reads (see *Links and forks across kolabs*). Reading is wider: a full address, `kj:<kolab>/<node>…`, resolves in any kolab the session's actor holds Read on (see *Addresses* below). Anything else in another kolab is refused as if it didn't exist. Row-level security repeats this in the database. As `kj_agent`, a session reads the rows of its own kolab only while its actor can still reach it (`kj_session_kolab()`). In another kolab it reads only the nodes, the committed versions and their elements and questions, and only where its actor holds Read now (`kj_session_readable_kolabs()`, 0008). It writes only its own kolab (a link or fork it makes may name a committed version it reads elsewhere, 0017), and only its layer while its access covers it (`kj_session_layer()`). The reads Kolab does for a session's addresses run as `kj_agent`, so this binds them too; see *Addresses* for the one read across kolabs that doesn't. How access is computed lives in one place, the database's `kj_access(actor, kolab)`, which the engine calls too.

The database also keeps tenants apart for every role, not only `kj_agent`:

- **No row references another kolab's row**, except a link's target, a fork's parent, an override's base and a mark's trigger, which may name another kolab's committed version (see *Links and forks across kolabs*). Each other reference is a foreign key on the pair of the referenced id and the row's own kolab: a version's node and base, an element's or delta's version, an edge's source, a mark's version, edge and delta, a mark cause's two marks, a question's version, asker's version and mark, a case file's version, and a position's or ruling's case file or version.
- **A row's kolab never changes** once written (`kolab_fixed`), and those keys stop a row being re-parented into another kolab.
- **`kj_agent` reads no sessions**, whose ids are their tokens' hashes (0011), **and no actors**. Only Kolab can run `kj_access` (and `kj_system`, which re-checks an author as a draft commits).
- **No shadowing.** Every security definer function searches `pg_catalog, public, pg_temp`, with temporary tables last. Only the database's owner may create temporary tables (0006 revokes `TEMPORARY` from `public`), so `kj_agent` can't plant a table that a helper would read in place of `session`.
- **Precedent is per kolab**, keyed by the kolab and the fingerprint triple, and a rebase matches only its own kolab's.
- **The served instructions** (`konjir_operating_instructions`) carry only the session's kolab's precedent and answered questions; the admin token gets the rules alone.

Row-level security's session helpers sit in subqueries, so Postgres evaluates them once per statement, and the tables they filter are indexed by kolab. A 400-element draft takes about 320 ms on PGlite, down from about 450 ms before that change.

| --- | --- |
| `admin_add_organization id=<org>` | An organization account |
| `admin_add_member org=<org> user=<person> [role=owner]` | Adds a person to an organization, or changes their role |
| `admin_add_team org=<org> name=<team> [parent=<team>]` | A team, `<org>/<team>`, nested under a parent if given |
| `admin_add_team_member team=<org>/<team> user=<person>` | Adds a member of the organization to the team |
| `admin_remove_member org=<org> user=<person>`, `admin_remove_team_member team=<org>/<team> user=<person>` | Removes a membership (leaving an organization leaves its teams too). Says how many sessions it ended |

| `admin_revoke kolab=<name> to=<grantee>` | Removes a grant. Says how many sessions it ended |
| `admin_access actor=<actor> kolab=<name>` | An actor's level and writable layers there, as Kolab computes them |

**Archiving (D52).** Nothing is ever deleted: an admin archives a kolab, an organization or an actor instead, with `admin_archive`, naming exactly one. An archived one is left out of `admin_list_kolabs` and `admin_list_actors` (unless `archived=true`), and can't be used. Its data is kept for audit, and its name stays reserved: a new kolab, account or actor of that name is refused. People, agents and organizations share one namespace, and names in it must differ in more than case, so archiving `lee` also keeps anyone from becoming `Lee`. The refusal reads exactly as for a live holder ("taken"), so nobody learns an archived one exists; only the admin token's verbs add which archived one holds the name and how to unarchive it. `admin_unarchive` restores it as it was, grants and memberships included. Every archive and unarchive is logged, with who asked (`admin` for the admin token) and when, in `archive_event`, which is only ever added to.

- **A kolab:** every session in it ends, in the same transaction, and its listen streams are told so they close (D41). No session opens in it, nothing in it can change, and nobody holds any access there, so nothing reads it but the admin token. A grant on it is refused; revoking one isn't. Its outbox jobs wait, unclaimed, until it is unarchived; a job already running when it was archived is released without counting as an attempt.
- **An organization:** its kolabs and its agents are archived with it, so every member's, team's and grant's access to those kolabs stops counting. It takes no members, teams, kolabs or agents.
- **An actor:** its session ends and none opens. A person's agents go with them (an agent never holds more than its owner, D30). The kolabs a person owns directly stay live for the others who work in them; the archived person holds nothing there, and can't own a new kolab. An agent can be archived alone. Its authorship stays as written.

What goes with an account is computed, not copied: a kolab is archived if it is or the organization that owns it is, and an agent if it is or its owner is. So unarchiving the account brings back exactly what wasn't archived on its own, and unarchiving a kolab or agent whose owner is still archived is refused, naming the owner. Archiving checks, changes and logs under the access lock, in one transaction, so two admins at once can't both archive one thing. Migration 0014 stores it: `kolab.archived_at`, `account.archived_at` (an organization, or a person, whose user account has their id), `actor.archived_at` (an agent only, `actor_archived_is_agent`) and `archive_event`, with unique indexes on `lower(id)` for accounts and actors. The database enforces it as well as Kolab: `kj_access` gives an archived actor, and anyone in an archived kolab, nothing (through `kj_kolab_archived` and `kj_actor_archived`), so row-level security gives `kj_agent` nothing there either. And for every role, Kolab's own login included, statement-level triggers refuse any insert, update or delete of an archived kolab's rows, one check per statement over the kolabs it touched (`kolab_writable_insert`, `_update` and `_delete` on every table with a `kolab_id` but `session` and `outbox`; new grants on it too), and a trigger refuses any session opening, or reopening, in an archived kolab or for an archived actor (`session_openable`). The one exception is the migration runner: its transaction sets `kj.migrating`, which the triggers honour only on Kolab's own login, never under `kj_agent` or `kj_system` (`kj_migrating`), so a later migration's backfill still reaches archived rows. Each helper is a security definer function with its search path pinned.

Migration 0006 keeps what the database holds. If it has any actor or node, its data becomes the kolab `kolab`, owned by the organization `konjir`; each person becomes a user and a member of `konjir`, and each person and agent gets Write on both layers of `kolab`, which is what any actor could do before. Open sessions work in `kolab`. A fresh database gets none of this. An existing actor named `konjir`, person or agent, stops the migration, since the organization needs that id: rename the actor first.

**Take a database snapshot before deploying any release with a new migration**, such as 0006, 0007 (the review flow), 0008 (node names per kolab), 0009 (which drops `version.findings`, W1.7), 0010 (the outbox), 0011 (hashed session tokens), 0012 (link removals and the cascade's indexes), 0013 (rulings' dates and the case-file verbs) 0014 (archiving), 0015 (rebase jobs), 0016 (outside readers see no question a mark raised), 0017 (links and forks across kolabs), 0018 (identities and OAuth) or 0019 (invites). Once one is applied, an earlier release refuses the database ("recorded at a migration this release doesn't have"), so going back means restoring from that snapshot, which loses whatever was written since: after 0007, for example, versions in review and their review requests, after 0010 the outbox's jobs, the work commits and approvals still owed, and after 0012 the links drafts remove. A release before 0015 also can't run the `rebase` jobs a later one queued.

### Signing up and in

A person signs up and signs in with GitHub, so their first session needs no admin (D55). Kolab is an OAuth 2.1 authorization server for its MCP endpoint and the web interface, following the MCP authorization spec for remote servers, with GitHub as the upstream identity. Other identity providers can be added behind the same interface, `IdentityProvider` (`apps/server/src/oauth/identity.ts`); tests use `StubIdentity` in GitHub's place.

- **Discovery.** `/mcp` answers a request without a valid token with 401 and `WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource/mcp"` (RFC 9728), which @onivoro/server-mcp sends. That names Kolab itself as the authorization server, whose metadata, `/.well-known/oauth-authorization-server` (RFC 8414), lists `/oauth/authorize`, `/oauth/token`, `/oauth/register` and `/oauth/revoke`. The issuer is Kolab's origin: `https://<public host>` behind the TLS proxy, or the loopback address a request names. Without an identity provider none of it is served.
- **Clients** register themselves (RFC 7591), as public clients with no secret: `none` is the only token endpoint authentication, and PKCE stands in for a secret. A redirect URI is https, or http on a loopback address; never an app's own scheme, and never one with a fragment or credentials. One given at authorization must be such a URI and match a registered one exactly, but for a loopback URI's port (RFC 8252 §7.3). Kolab redirects nowhere before the person has seen the consent page: an unknown client, an unregistered redirect URI, a missing or plain PKCE challenge, another response type or another resource each gets a page saying so, since anyone may register a client with any https redirect URI (RFC 9700 §4.11.2). A client never used is deleted a day after it registered, and one unused for 30 days with no live grant then too. The web interface is Kolab's own client, `konjir-web`, never registered, whose only redirect is its own callback. Client ID Metadata Documents, which spec 2026-07-28 prefers to registration, aren't accepted yet.
- **Authorization code with PKCE**, S256 only. A `resource` other than Kolab's own `/mcp` is refused (`invalid_target`). Kolab signs the person in at GitHub as an OAuth client of its own, with a state and a PKCE verifier of its own, both bound to the browser by an `HttpOnly`, `SameSite=Lax` cookie (`__Host-konjir_oauth`, `Secure`, `Path=/`, behind the TLS proxy, so no other host under the domain can toss one in; `konjir_oauth`, scoped to `/oauth`, on loopback), so GitHub's answer counts only in the browser that asked, with the state it was given; both are checked before GitHub's code is redeemed. GitHub is asked for no scope: Kolab reads only the user's id, login and name, then revokes the GitHub token. Then the person consents on Kolab's page, which runs no script, loads nothing from elsewhere and can't be framed, with a form token of its own, from Kolab's own origin only. The client's `state` comes back to it, with the issuer in `iss` (RFC 9207).
- **Sign-up.** A person is their GitHub identity, by GitHub's numeric user id, never their login, which can change hands. The first sign-in makes a person and their user account, named after the login, lowercased. If a live or archived account or actor holds that name in any case (D52), the name tried next is `<login>_2`, then `_3` and so on: a GitHub login never holds `_`, so no variant is someone else's login. `kolab`, `admin`, `root`, `system`, `support` and the like, and anything starting `konjir`, are reserved, and sign up as `gh_<login>`; so does a login that reads as an existing person's agent, `<person>-<label>` (`lee-claude` while `lee` exists), so no one passes for someone's agent or takes the name their agent would have; the same goes for an organization's (`acme-bot` while the organization `acme` exists). Whoever takes a name first keeps it: a person `lee-claude` who signed up before `lee` stays a person, shown as one with no owner, and `lee` choosing the label `claude` is refused, saying so, to choose another. Nobody is matched by name: an admin links an existing person to their GitHub identity with `admin_link_identity actor=lee provider=github subject=<GitHub user id>` (`gh api users/<login> --jq .id`), so their first sign-in reaches them. An archived person doesn't sign in.
- **Consent.** The person chooses who the client works as, in which kolab and role. An MCP client works as an agent of theirs by default (D30): one they have, or a new one, `<person>-<label>`, at most 10 of them, and 3 in 10 minutes. If it has no grant in the kolab, it gets what its owner holds there, at most Write, on the layers its owner writes, in any kolab the person reaches by owning it, a grant, a team or their organization, an organization's included (D56). That grant stands, but never above its owner: an agent's access is cut down to its owner's on every use (D30), so it follows the person's access down, and ends with it. A kolab the person reads only because it is public gives their agents nothing, and no grant is stored there. The database holds to that on every use too: `kj_access` cuts an agent down to `kj_agent_cap` (0018), its owner's access without what visibility alone gives, so an agent whose owner's team or grant goes, leaving only a public kolab's Read, holds nothing there, and its session ends. A grant someone else gave the agent stands as it is. The agent cap, and the rate of 3 agents in 10 minutes (counted in the database, by `actor.created_at`, so every process counts the same), are checked and the agent made under the access lock, and a consent form claims its sign-in before it makes anything, so two submissions at once make one agent or kolab. Or the client works as the person themselves. The web interface is for people, so it always works as the person. The kolab is one they can reach, or a new private kolab of their own, with D54's limits but the Write-where-you-work one, which someone new can't meet (D56). The consent page shows where the client gets its answer, since a client's name is its own say-so.
- **Tokens.** An access token is a session token: it opens the same one-actor, one-kolab, one-role session (ENF4, ENF5), so every check, row-level security's included, applies to it unchanged. It lasts 15 minutes. A grant's session keeps its id, the key `whoami` and events give, while its access token rotates: `session.token_key` is the sha256 of the current one and `session.expires_at` its expiry. A refresh token (`kjr_…`) lasts 30 days past its last use, and is used once: each refresh issues the next. One presented again within 10 s is taken for a concurrent request and refused; later, for a replay, which revokes the grant. A code (`kjc_…`) lasts 60 s and is used once; used again, it revokes the grant it opened. Kolab stores the sha256 of every token, code, state and form token, never the thing itself (P1). The newest sign-in for an actor wins: opening a grant's session ends the actor's other open session (ENF4), and tells its streams (D41).
- **Expiry in the database too.** Row-level security finds the session through `kj_session_id()`, which reaches a grant's session only by its current, unexpired access token, and a hand-issued one by its id. So a rotated or expired token reaches nothing, in Kolab or under `kj_agent`. The session helpers use it (0018), each a security definer function with its search path pinned.
- **Revocation.** `/oauth/revoke` (RFC 7009) takes a refresh or access token: the grant is revoked and its session ends, so its streams close (D41). So do signing out of the web interface, `admin_end_session`, and a session losing its access. A listen stream, and a web page's event stream, live as long as the access token they opened with: once it expires or a refresh rotates it, the stream closes before anything more is signalled to it, checked before each signal and, for listen streams, every 30 s, and the client listens again with its refreshed token. `/oauth/revoke` takes only a token issued to the registered client that names itself (RFC 7009 §2.1).
- **The transition.** Hand-issued session tokens (`admin_open_session`) keep working beside OAuth's, until `KONJIR_HAND_ISSUED_TOKENS=off` turns them off on `/mcp` and in the web interface. The admin token works either way. `KONJIR_GITHUB_CLIENT_ID` and `KONJIR_GITHUB_CLIENT_SECRET` turn GitHub sign-in on for `konjir serve`; the OAuth app's callback URL is `<origin>/oauth/callback/github`. With it on, the web page offers only *Sign in with GitHub*, unless `KONJIR_WEB_TOKEN_SIGN_IN=on` (for development) keeps pasting a token; without it, pasting a token is how one signs in, as before.
- **Not yet.** The channel bridge can't sign in through OAuth: it takes a session token (`KONJIR_TOKEN`), so pushing an inbox into Claude Code still needs one an admin opened. A person can't list or revoke their grants in the web page, only sign out of it, nor remove someone's access there once an invite is accepted; and an invite is a link, not an invitation to a GitHub login or an email address. Rate limits are per process: 10 registrations an hour from one address (500 in all), and 30 authorizations a minute from one address, counted only once the client and redirect URI check out, with no total and no limit per client, whose id is public, so no few addresses can lock everyone out. An IPv6 address counts by its /64; a request with no address to count by is refused. A refused request spends nothing. Behind the TLS proxy the address is the last `X-Forwarded-For` entry, which Caddy writes.

### Onboarding with no admin

A person's first session needs no admin (W3.4; P15, D55). They sign up with GitHub and make their first kolab on the consent page, connect a harness with one command, and invite a teammate with a link.

- **A first kolab.** Someone new, with no kolab and no invite, makes a private kolab of their own on the consent page (D54, D56), its short name filled in with theirs when that is a kolab name. An empty kolab's first page says what to do first: connect a harness, invite a teammate, write the spec.
- **Connecting a harness**, the web page's *Connect a harness*: Claude Code with `claude mcp add --transport http konjir <origin>/mcp` (it signs in on Kolab's page, as an agent of the person's by default); any shell with `npx konjir login --url <origin>/mcp [--kolab <name>] [--role product|engineer]`. `konjir login` is an MCP client like any other (`apps/cli/src/login.ts`): it registers itself as a public client with the loopback redirect `http://127.0.0.1/callback`, listens on a port of its own on 127.0.0.1 (RFC 8252), opens the browser at Kolab's sign-in with the kolab and role preselected, and takes only the answer that carries its own state. It keeps its registration and tokens in `$XDG_CONFIG_HOME/konjir/credentials.json` (`~/.config` by default, or `KONJIR_CREDENTIALS`), keyed by the MCP URL: the file 0600, and konjir's own default folder 0700 (tightened if it already existed); a folder named through `KONJIR_CREDENTIALS` is never changed, only warned of when others may write in it. Each write is a new file of a random name made with O_EXCL, moved into place. A file konjir can't parse is never overwritten; konjir names it and stops. Every later `konjir` command with no `KONJIR_TOKEN` uses it, the MCP client refreshing the access token as it expires; `konjir watch` listens again when its stream closes at the token's expiry, backing off (1 s, doubling to 30 s) while streams keep closing at once. Several konjir at once share it safely: every write takes a lock file beside it (O_EXCL, holding its owner's random id, refused if it is a symbolic link), which its holder touches every 10 s and others break only once it is 30 s untouched, by moving it aside and checking it is still the stale one; a holder re-reads the lock before it saves or lets go, so one whose lock was broken while it stalled keeps the tokens another konjir saved rather than writing over them. Waiting for a lock that can't be read or removed ends, by its deadline, in an error naming the file. A refresh holds the lock from reading the refresh token to saving the next, a request refused while another konjir refreshed waits for the lock and is sent again with the new token, and tokens are forgotten only if they are still the ones that failed. A sign-in that ended or was revoked says to run `konjir login`. `konjir login` keeps the sign-in it replaces, working, until the new one succeeds, then revokes it. `konjir logout` reads, revokes and forgets under the lock. `konjir logout` revokes the refresh and access tokens at Kolab's own `/oauth/revoke` and then forgets them; if Kolab can't be reached or refuses, the sign-in is kept and logout fails, saying so, unless `--forget` drops it anyway, unrevoked.
- **Invites** (*People*, for those with Admin in the session's kolab): an invite is a link, `<origin>/#/invite/kji_…`, shown once. Whoever signs in with it, as a person, is granted its access in that kolab, once: Read, Triage, Write on one layer or both, or Maintain, never Admin, which the kolab's owners give. It lasts 7 days, until it is accepted, or until an admin of the kolab revokes it, and it counts only while whoever made it still holds Admin there, so an admin who loses Admin takes their open invites with them. An archived kolab's invites are no good (D52). Accepting always writes the person's own grant there: their direct grant, if any, raised to cover the invite (the higher level; at Write, the layers of either), so it never lowers a grant and never leans on what reaches them only through the kolab being public, a team or a base permission, and their agents may borrow it (D56). In an organization's kolab, someone who isn't a member becomes an outside collaborator (TEN10). An agent never accepts one: it gets its access from its owner (D30, D56). Accepting runs under the access lock, as any change of access does, and the invite row is locked, so one is accepted once however many people try at once; at consent it is the same transaction that issues the code, so a sign-in that fails uses up nothing. A kolab holds at most 50 open invites and a person makes at most 20 an hour, counted in the database under the access lock. Kolab stores only an invite's sha256 (P1), and `kji_` tokens are masked in logs like every other secret. A refused invite says only that it is unknown, used, revoked or expired, or that its maker can no longer invite.
- **Opening a link.** The secret rides in the URL's fragment, which no request carries; the page takes it out of the address as soon as it reads it. The page posts it to `POST /api/session/invite`, from Kolab's own origin, 30 a minute from one address (an IPv6 /64), which says what it offers and keeps it in an `HttpOnly`, `SameSite=Lax` cookie for 30 minutes: `__Host-konjir_invite` behind the TLS proxy (`Secure`, `Path=/`), `konjir_invite` scoped to `/oauth` on loopback. Only `/oauth/authorize` reads it, and only for the web interface's own client, `konjir-web`, never a registered MCP client; the consent page then offers to join that kolab, saying who invites and with what: chosen already for someone with no kolab yet, and otherwise for the person to pick. The page's kolab choices are `kolab:<name>`, `@new` and `@invite`, so a kolab may be called `new` or `invite`. Consenting accepts it and clears the cookie, and so do Decline, *Not now* (`DELETE /api/session/invite`) and signing out. A person already signed in joins with *Join* (`POST /api/session/invite/accept`), which grants the invite's access and moves their session there in the same role.

Migration 0019 stores invites: `kolab_invite` (its key, kolab, level and layers, maker, expiry, and who accepted it or when it was revoked), with no grant to `kj_agent` or `kj_system` and the `kolab_writable` triggers of every table with a kolab, and `oauth_request.invite_key`.

Migration 0018 stores it: `identity` (provider, subject, person, login), `oauth_client`, `oauth_request` (an authorization in progress), `oauth_code`, `oauth_grant` and `oauth_refresh_token`, all keyed by hashes where they hold a secret, and none readable by `kj_agent` or `kj_system`; `session.grant_id`, `token_key` and `expires_at`, all three or none (`session_grant_token`); a trigger that only a person has an identity; and `kj_session_id()`, with the six session helpers redefined over it.

### Addresses

An address names its kolab: `kj:<kolab>/<node>[@<version>][#<element>][~q(<selector>)]` (ADR3, D8, DAT11). Inside a kolab the short form, `kj:<node>…`, is enough. `@konjir/address` parses and prints both, and nothing else does: the kolab segment is a kolab name (lowercase letters, digits and `-`), and a node's name is anything without `/`, `@`, `#`, `~` or whitespace, so the first `/` always ends the kolab.

- **A node's name is unique within its kolab**, not across Konjir, so two kolabs may each have a `checkout` and neither learns of the other. A name taken in the session's own kolab is refused, naming only that kolab. Migration 0008 adds `node.name`, unique per kolab (`node_kolab_name_key`); each existing node's name is its id.
- **The id is Kolab's own.** A node keeps the id every version refers to. A new node's id is its name, unless another kolab's node already holds that id, and then it is `~` and a ULID, which no name can be, since a name has no `~` (`node_id_name_check`). The id says nothing of the kolab, so renaming a kolab, if that ever comes, needn't touch it. Neither id nor name changes once written (`node_name_fixed`). Every verb takes a node's name, every address and message Kolab gives names the node by its name, and no verb shows an id.
- **The short form** is the node of that name in the session's kolab. Every read names its reader: `{ session }`, or `{ system: <kolab> }` for Kolab's own reads, which check nothing and may never stand in for a session.
- **The full form resolves from anywhere** its reader can read. In the session's own kolab it is the same as the short form. In another kolab, `konjir_resolve` and `konjir_read_node` (`node=<kolab>/<node>`) need the actor to hold Read there, as `kj_access` computes it: so an agent needs a grant of its own, never more than its owner's (D30), and a person may read a public kolab. Without it, the address is refused exactly as one naming a node or kolab that isn't there. `read_node` across kolabs prints full addresses, its own kolab's short ones.
- **Across kolabs, only committed work shows.** A reader outside a node's kolab sees its committed versions only, and of their questions only those people raised: none a mark raised (a boundary finding, or a ruling that changes the intent, D51), and none naming its mark or the element that asked (0016 holds `kj_agent` to the first). Version numbers are the node's own, committed or not, so where drafts or rejected versions came between, a reader outside sees a gap (`v1`, `v4`): addresses carry the real number, so this is accepted. a pinned draft or rejected version (`kj:billing/checkout@3`) resolves as an orphan, and `read_node` says there is no such version, as for one that doesn't exist. Inside its own kolab a session reads drafts as before (ADR9). This reading is put to Lee.
- **Enforced twice.** Kolab checks Read first, then runs the read as `kj_agent` in the session, so row-level security returns nothing it shouldn't, even to code that skips Kolab's check. The one exception is `read_node`'s author: `kj_agent` reads no actors, so Kolab's login looks up who wrote the version, after the version itself was read under row-level security.
- **Writing stays in the session's kolab, but a link or a fork may reach out.** A question or a draft naming another kolab is refused from the address alone, saying it isn't supported across kolabs, without looking at what is there. A link's target and a variant's parent may be another kolab's committed version, wherever the session's actor holds Read (see *Links and forks across kolabs* below); anywhere else they are refused as a node that isn't there.

### Links and forks across kolabs

A link into another kolab (LNK8) and a fork, a variant of another kolab's spec (KON9), are made as any other: `konjir_link target=kj:billing/checkout#R1`, `konjir_draft parent=kj:billing/checkout@3`, and a draft's `unlink` removes one as any other (`link_removal.target_kolab_id`). Migration 0017 relaxes four of 0006's composite keys for them, and only those: an edge's target, a version's parent, an override's base and a mark's trigger. D53 settles the model.

- **Only committed work, and only with Read.** Another kolab's reference must name a committed version, for every role (`kj_kolab_ref_check`, checked after row-level security so an agent refused there learns nothing more). Kolab checks Read on the target's kolab, and row-level security repeats it for `kj_agent` (`edge_target`, `version_parent`, and `delta_base` for an override's base), inside the writing transaction under a shared hold on the access lock, so no revoke lands between the check and the commit.
- **A holder.** A link or fork across kolabs rests on one actor's access: `edge.held_by`, the actor who linked, and `version.parent_held_by`, the author who forked. The holder vouches for it while they hold Read on the other kolab *and* Write on the dependent's layer in its own, so someone who has left the dependent's kolab is no channel into it. A rebase, or a draft of the fork by someone who can't read the parent, carries the holder; someone who reads it and drafts, clears a mark, revises the element or links again becomes the holder.
- **`access_lost`.** When the holder no longer vouches for it, the dependent (a link's source element, or a fork's live version) is marked `access_lost`: in the transaction that changes the holder's access, which looks only at the links and forks held by the actors the change can affect (the grantee, a team's members, and the agents they own), and whenever the cascade meets the link. While it is open, the other kolab's commits reach neither the link (no marks, no re-pin) nor the fork (no rebase, no fold). It settles when the holder vouches again, when someone who reads takes it over with `konjir_clear_mark`, or when the link or fork goes. A settled link is checked against its target's latest version at once; a settled fork is caught up by a rebase job (0015) written in that transaction.
- **Locks.** Every transaction that takes both takes the access lock (shared) before a node's lock, and a change of access takes the access lock alone, exclusively, so none waits on another in a cycle (W1.17 still locks at most one node).
- **Each kolab's work is its own.** A commit owes each dependent in another kolab a rebase job of its own (0015): its links there checked, its fork rebased once its holder still vouches for it. One that fails backs off and retries on its own, the committer hears nothing of it, and a pending rebase never names the upstream kolab's version or its error.
- **Each kolab's rows stay private (D49).** The edge and its marks belong to the source's kolab, which the target's kolab never reads: `konjir_lineage` downstream shows only links from the reader's own kolab, and a mark spreads only within its own kolab (a mark's causes keep 0006's composite key), so the downstream kolab hears of an upstream change when it commits, not of the upstream kolab's own marks. A binding's layer leak against a spec in another kolab asks the binding's own layer.

Questions across kolabs stay refused.

- **Claude Code, with OAuth (D55):** `claude mcp add --transport http konjir https://kolab.konjir.com/mcp`, then `/mcp` in Claude Code to sign in with GitHub in the browser and choose its agent, kolab and role.
- **Claude Code, with a hand-issued token:** `claude mcp add --transport http konjir http://127.0.0.1:7420/mcp --header "Authorization: Bearer <token>"`
- **Any MCP client:** one that speaks MCP's authorization needs only the URL; otherwise, an HTTP server entry with an `Authorization: Bearer <token>` header.
- **Anything with a shell** (Codex, opencode, a person): `konjir login --url https://kolab.konjir.com/mcp` signs in with the browser, as an agent of yours (W3.4, *Onboarding with no admin*); or `export KONJIR_URL=… KONJIR_TOKEN=<token>`. Then `bin/konjir instructions`.

That one connection is the only static setup a harness needs. The rules come down the protocol, as server instructions and the `konjir_operating_instructions` prompt (`konjir instructions` in a shell). How to review a version comes the same way, as the `konjir_reviewer_instructions` prompt (`konjir instructions reviewer`); see *Review*. The served text includes the answered questions and override precedent of the session's own kolab, so settled questions aren't re-asked.

### Installing the konjir CLI

Outside a checkout, `konjir` is the client alone: every verb, `instructions`, `watch` and `--version`, but no `serve`, which runs Kolab and needs a checkout. It needs only a Kolab's URL and a token.

```
npx konjir --help                       # Node 22 or later; the package has no dependencies
npm install -g konjir                   # or keep it installed

# or a single-file binary, which needs no Node, from the GitHub release:
#   konjir-linux-x64, konjir-linux-arm64, konjir-darwin-arm64, konjir-darwin-x64, konjir-windows-x64.exe
curl -fLo konjir https://github.com/konjir/kolab/releases/download/konjir%40<version>/konjir-darwin-arm64
chmod +x konjir                         # each release also carries SHA256SUMS
xattr -d com.apple.quarantine konjir    # macOS: the binaries aren't signed

KONJIR_URL=https://kolab.example.com/mcp KONJIR_TOKEN=<token> konjir whoami
```

`apps/cli/scripts/package.mjs` builds both from `apps/cli/src` with [Bun](https://bun.sh). `apps/cli/bun-runtimes.json` pins Bun's version and the sha256 of each Bun release zip used. Each build checks that the `bun` on your PATH is that version, and `node apps/cli/scripts/package.mjs bun <dir>` installs a checked one. `npx nx run konjir:bundle` writes the npm package to `apps/cli/dist-npm`: the CLI and the MCP client SDK bundled into one `konjir.mjs`, a `package.json` that declares nothing else, and `THIRD-PARTY-NOTICES.md`, the bundled packages' licences, taken from Bun's metafile. `npx nx run konjir:compile` writes the binaries and the same notices, plus the Bun runtime's, to `apps/cli/dist-bin`. It compiles each binary with `bun build --compile` on a Bun runtime downloaded from Bun's release and checked against its pinned hash (`node apps/cli/scripts/package.mjs binaries darwin-arm64` builds one). Both builds leave out `@konjir/server`, so `konjir serve` from them says to use a checkout. Neither target is part of `build`, so the release Kolab runs, which `install.sh` builds with tsc, doesn't need Bun.

### Pushing the inbox into a Claude Code session

Kolab signals inbox changes over `subscriptions/listen`, but Claude Code doesn't hand those notifications to the model. The Konjir channel does: `apps/channel-bridge` is a Claude Code plugin whose stdio server listens to Kolab with the session's token and forwards each change to its inbox (`konjir://inbox/{layer}`) or its answers (`konjir://answers/{actor}`) as a [channel](https://code.claude.com/docs/en/channels-reference) message. Each message says what changed and how to read it. It serves only the 2025-era protocol, because Claude Code doesn't register a channel server that negotiates 2026-07-28, and it reconnects when Kolab restarts.

It runs in place from a Kolab checkout, so run `npm install` there first, and install it only from that checkout's local path. A marketplace added from GitHub copies the plugin into Claude Code's cache, away from the workspace's packages, and the bridge won't start. Channels are a research preview and this one isn't on Anthropic's allowlist, so it loads with the development flag, in an interactive session (`-p` ignores the flag). Start Claude Code with the agent's own session token, the one its Konjir MCP server uses. ## The web interface

Kolab serves a web interface at its root, `https://kolab.konjir.com/` on the test server (W3.1, API8). It is a React and Vite single-page app in `apps/web`, built to `apps/web/dist` by its Nx `build` target, and served by the same NestJS process as `/mcp`. A product owner can do there what the [Konjir Kolab prototype](https://claude.ai/artifact/99doLyY9QFgZZkENDb4GNa) simulates, against the real server:

- **Read a spec** (or any node of the kolab) with its questions and notes beside each element, open and answered, from any version (Q5), the links each element relies on and is relied on by, and its versions. A version in review, or an older one, shows its changes word by word against the version before it.
- **Answer** a question, or reply to a note, that the session's layer owns; **ask** a question or **leave a note** about an element or a node (Q1, Q3). Questions route to the layer that owns the answer.
- **See what's stale:** each mark beside its element, with the text it was written against and the text now, and settle it as its owner: *Still holds* (`clear_mark`), revise the element, or for a variant's override, rule on it: keep ours, adopt the parent's, or amend (`resolve_override`, OVR8), which becomes precedent (LNK6, OVR9).
- **Edit and submit:** edits, and links dropped (*unlink*, which settles their marks when the version commits), stay in the page as a draft until *Submit for review*, which drafts the node's latest version with them and submits it. A draft that fails Kolab's structural checks is abandoned at once and the page keeps the edits to fix. A draft that came back with changes requested can be resubmitted or abandoned.
- **Review:** a version waiting for the session's actor shows *Approve* and *Request changes* (with a note), the same verdicts as `konjir_review`.
- **Case files and rulings** (W3.2; CASE1–CASE7, D49, D51): open a case file on an element (*Dispute*: the question, a claim, its evidence and the side it takes), take the other side, and, as a person with Write on the element's layer from its role who isn't a party, rule on it, sustaining exactly one position. Or rule directly (*Rule*) on an element or a whole node, which supersedes any case file still open on the element. Each ruling shows beside the element it rules on, from any version, as precedent; one that changes the intent marks the element (*ruled*), which only a version amending it settles. The **Cases** page lists the open case files, the kolab's rulings, newest first, and the settled case files. Only those who belong to the kolab's work (Write on a layer of it) see any of it, and the page offers each action only to whom Kolab would allow it (`WebCase.you`); Kolab decides.
- **Reading another kolab in place** (D49): *Read here* on another kolab's card, or an address in *Go to an address* (`kj:<kolab>/<node>[@<version>][#<element>]`), reads its committed versions, with their elements and questions, read only, without leaving the session's kolab. Only nodes with a committed version are listed; one with none is refused as one that isn't there. Its drafts, versions in review and rejected versions, links, marks, reviews, case files and rulings never show, nor questions a mark raised. A kolab the session can't read, a node that isn't there and a version that isn't committed are refused alike, saying nothing of which. Working there takes *Open* (a session there).
- **Lineage** (what depends on what, wire by wire, stale wires dashed), **Questions**, **Reviews** (waiting for you, and what you submitted) and **Activity**, and the kolabs the actor can reach. A person whose role writes the layer can create a node in the session's kolab.
- **People** and **Connect a harness** (W3.4): an admin of the kolab makes invite links, sees what became of them and revokes open ones; anyone sees the one command that connects Claude Code or a shell to this Kolab, with their kolab and role. An invite opened from its link shows what it offers, and *Join* (see *Onboarding with no admin*).

**Signing in.** A person signs in with GitHub (D55): *Sign in with GitHub* goes to `GET /api/session/oauth/start`, which sends the browser through Kolab's own authorization server as its first-party client `konjir-web`, with PKCE and a state of its own kept in a cookie only its callback reads, to GitHub and the consent page, where the person picks the kolab and role (or makes their first kolab), and back to `GET /api/session/oauth/callback`. There Kolab exchanges the code in the process, and keeps the access token in an `HttpOnly`, `SameSite=Strict` session cookie, and the refresh token in another, which the browser forgets when it closes, so the page's script never holds either. Behind the TLS proxy they are `__Host-konjir_session` and `__Host-konjir_refresh` (`Secure`, `Path=/`, no `Domain`), so no other host under the same domain can plant one; on loopback `konjir_session` and `konjir_refresh`, scoped to `/api`. Every call checks the session again, as `/mcp` does; when the access token has expired, the guard refreshes it, once however many of the page's calls arrive together, and sets both cookies anew. A session that ends or loses its access signs every page out. *Sign out* (`DELETE /api/session`) ends the session itself, if it is a person's, and revokes its refresh token; signing in again starts afresh. Whatever the cookies held, they are cleared. `GET /api/session/methods` tells the page which ways in this Kolab offers.

With token sign-in on (no identity provider, or `KONJIR_WEB_TOKEN_SIGN_IN=on` for development), a person may instead paste a Konjir session token of their own, which an admin opened (`konjir admin_open_session actor=lee role=product kolab=accounts`, or `deploy/konjir-ops.sh connect lee product`): the page posts it once to `POST /api/session`, into the same cookie. Either way an agent's session is refused: the web interface is for people, and an agent works through MCP or the CLI, so no person clicks as their agent and no verdict says an agent gave it. The admin token, which works in no kolab, is refused too (compared in constant time, as on `/mcp`).

**Kolab and role.** The kolab picker lists the kolabs the person can reach, with their access there, and *Working as* switches between product and engineer. Either switch (`POST /api/session/switch`, `Kolab.switchSession`) ends the person's session and opens one in the chosen kolab and role in one transaction under the access lock, checking access there, so either both happen or neither does; the old session's end is signalled only once that commits (D41). The new token goes only into the cookie (ENF4 allows one open session per actor, so a CLI using the same token stops working too). *New kolab* (`POST /api/session/kolab`, `Kolab.createOwnKolab`) makes a private kolab owned by the person (D54; TEN2, TEN3) and moves the session into it in the same role. Kolab enforces the limits, not the page: the person holds Write where they work (a reader can't), the name follows the kolab grammar in at most 40 characters, is unique across Konjir (TEN4) and isn't reserved (`kolab`, and anything starting `konjir`, such as D15's `konjir-site` and `konjir-brand`), the title is at most 100 characters, a person owns at most 10 kolabs (`KONJIR_KOLABS_PER_PERSON` for `konjir serve`), and makes at most 3 in 10 minutes, counted in the database under the access lock, so in every process together. An admin's `admin_add_kolab` keeps no such limits. An empty kolab's first page offers its first document.

**The API** (`apps/server/src/web`) is thin: each write is one of the agents' verbs, with the same engine call and the same rules, which Kolab enforces, not the API. Every read gathers what a page shows through `@konjir/engine`'s `views.ts` and `readNode`, which run as the session reads (`Kolab.readAs`: `kj_agent` under row-level security, in a read-only transaction) and name the session's kolab too. The one exception is the picker's list of kolabs, which comes from Kolab's own access check (`kj_access`, which no session may run). A submission names the version its edits were made on (`base`); if the node has moved on since, whether before the draft is written or before it is submitted, the draft is abandoned and the submission refused as stale (409), and the page keeps the edits, so edits are never laid over a version their author didn't see (CAS7). Nothing writes outside the session's kolab (TEN12): a node is named by its name in it, and another kolab's is refused as if it weren't there. Reading another kolab goes only through `/api/kolabs/:kolab/…`, in place and read only (D49, below). Every `/api` request must name a host Kolab serves (loopback, or its public host), as `/mcp`'s DNS-rebinding guard requires, and a change must come from Kolab's own origin. Errors come back as `{ error, message }` with any token masked; anything Kolab doesn't name is logged and answered with a plain 500, so no database detail reaches a page. The types are `@konjir/types`' `Web*`.

Case files and rulings are read as `kj_agent`, so a session holding only Read sees none (row-level security, 0013); `GET /api/nodes/:name` carries each element's rulings and open case files, and the node's own rulings. Another kolab's nodes are read only after Kolab's own Read check (`kj_access`), then as `kj_agent`, whose row-level security admits only committed versions there.

**Live.** Each page holds one `GET /api/events` stream. It carries signals, never content, and the page re-reads what it shows: `changed` with a layer when that layer's inbox changes (from any Kolab process on the database, API5), `changed` `answers` for the session's own answers, `changed` `versions` when a version is written or changes state in the kolab, and `ended` when the session ends (D41), after which the stream closes. A stream lives as long as its access token: when that expires but the session lives on, the stream closes without `ended`, and the browser reconnects a second later, which refreshes the token (D55). Push signals name their kolab (D50), so a page hears only its own kolab's. A commit signals no inbox, so each process checks the versions of each kolab that has a page open, once every 3 seconds however many pages are open there, one check at a time; once push signals carry commits (D50), that check becomes a fallback. A session holds at most 6 streams (429 beyond). The session is checked before each signal, and a comment every 20 seconds keeps the proxy from closing an idle stream.

**The pages** are served at `/` with a strict content security policy: everything from Kolab itself, the design system's fonts included, bundled with the page from `@fontsource-variable` packages, so no third party learns who opens a private kolab's page, `X-Frame-Options: DENY` and no referrer. Assets are named by their hash and cached for a year; `index.html` isn't cached. Any other path that asks for HTML gets `index.html`; `/api`, `/mcp` and `/healthz` are never shadowed. Without a build, `/` says how to make one. The look is the Konjir design system's: Predawn (dark) by default and Daybreak (light), Fraunces, Instrument Sans and JetBrains Mono, and the prototype's layout.

## Deploying to AWS for testing

Everything is provisioned by Terraform, so `terraform destroy` removes all of it. The one exception is the bucket that holds Terraform's own state, which a script creates once.

You need:

- Terraform 1.15 or later
- For sign-in with GitHub (D55), the GitHub OAuth app (GitHub › Settings › Developer settings › OAuth Apps): homepage `https://kolab.konjir.com`, authorization callback URL `https://kolab.konjir.com/oauth/callback/github`. Its client id is public and committed, as `github_oauth_client_id`'s default; Terraform keeps it as the SSM parameter `/konjir/<name>/github-client-id`. Its client secret is never Terraform's, so it is in no variable, file or state: put it yourself, once, as a SecureString (below). The instance may read both, the secret by its name, and the release's `start.sh` reads them when Kolab starts, so adding them changes neither the boot script nor the instance. If the secret isn't there, Kolab says so in one line of its log and runs without GitHub sign-in.
- AWS CLI v2 with a profile named `icedlee337` for the account that owns the `konjir.com` hosted zone
- `npm install` run once in this folder (the `konjir` CLI runs locally)

```
deploy/bootstrap-state.sh          # once: creates s3://konjir-terraform (versioned, encrypted, TLS-only)
# once, for GitHub sign-in (D55): the OAuth app's client secret, read without echo, so it is never on a command line or in history
# printf is a shell builtin, so the secret never reaches a command line; aws reads it from stdin.
# A GitHub OAuth app's client secret is 40 hex characters, so it needs no JSON escaping; anything else is refused.
printf 'GitHub client secret: '; read -rs SECRET; echo      # works in bash and zsh
case "$SECRET" in (*[!0-9a-f]*|'') echo 'not a GitHub client secret (hex)';; (*)
  printf '{"Name":"/konjir/konjir-test/github-client-secret","Type":"SecureString","Overwrite":true,"Value":"%s"}' "$SECRET" \
    | aws ssm put-parameter --profile icedlee337 --region us-east-1 --cli-input-json file:///dev/stdin;; esac
unset SECRET
cd deploy/terraform
terraform init
terraform apply                    # ~5–10 min the first time; ends when the code is installed
cd ../..
deploy/konjir-ops.sh connect lee product     # prints Lee's token and the Claude Code command
deploy/konjir-ops.sh connect eng-1 engineer
deploy/konjir-ops.sh connect lee-pm product lee   # an agent of Lee's, with its own token
```

`connect` works in the kolab `kolab` unless `KONJIR_KOLAB` names another. An actor it adds is granted Write on both layers there; one that exists keeps the access it has. An agent's grant is refused if its owner holds less.

The backend (`deploy/terraform/backend.tf`) stores state at `s3://konjir-terraform/konjir/test/terraform.tfstate` in `us-east-1`, using the `icedlee337` profile. It locks with S3's native lock file, so no DynamoDB table is needed.

| Module | What it creates |
| --- | --- |
| `network` | A VPC with one public subnet, and two private subnets for the database. Inbound is 443, plus 80 for certificate issuance; there is no SSH. |
| `storage` | The release bucket (emptied on destroy), the encrypted data volume, and daily snapshots kept 7 days |
| `database` | Postgres 18 on RDS (`db.t4g.micro`, 20 GB, encrypted, 7 days of backups), reachable only from Kolab over verified TLS. Its URL is an SSM SecureString |
| `secrets` | A generated admin token, stored as an SSM SecureString, and the GitHub OAuth app's client id (D55); the app's secret is put by hand, never by Terraform |
| `iam` | The instance role: Session Manager access, read its releases, token, database URL and the GitHub OAuth app's client id and secret (the secret by name). No Bedrock or other model access (REV5) |
| `kolab` | A `t4g.small` running Amazon Linux 2023, with Caddy for automatic HTTPS, an Elastic IP and the Route 53 record for `kolab.konjir.com` |
| `release` | Packs the checkout's commit (`deploy/release/pack.sh`), uploads it, and installs it on Kolab through Systems Manager. `terraform apply` is the deploy |

Kolab listens on localhost only, behind Caddy. Its database is on RDS, apart from the instance, so replacing the instance is safe. A change to the boot script replaces it automatically. The boot script still writes `KONJIR_REVIEW=structural` and `KONJIR_REVIEW_MODEL` into `/etc/konjir/env`, which Kolab ignores since W1.7: `modules/kolab` passes them as constants so that the script renders unchanged and W1.7 doesn't replace the instance. They go with the next boot-script change. The data volume still holds the PGlite database Kolab used before RDS. The rough cost is $30–35 a month at list price.

Day to day:

- **Ship code:** commit, then `terraform apply`. `deploy/release/pack.sh` packs the release with `git archive` of `HEAD`, so only tracked files ship: never an untracked or ignored one, such as `.env`, a `.claude/` worktree, a nested `.konjir` or a `*.tfvars` file. It refuses a checkout with uncommitted tracked changes, so a deploy is always exactly a commit, and refuses one that tracks a file that must never ship. The release id is the commit's tree id, so it changes only when tracked content does; a new one makes Terraform reinstall and wait for success. Terraform needs `git` and `bash` where it runs (`hashicorp/external`).
- **Inspect:** `deploy/konjir-ops.sh status`, `logs` or `bootstrap-log`. `shell` opens a session; it needs the Session Manager plugin.
- **One-way migrations:** a release that applies a migration can't be rolled back by deploying the release before it, which refuses a database migrated past it. 0011 (hashed session tokens) is also irreversible in the data: the hashes can't be turned back into tokens, so there is no down migration. Before applying a release with 0011, take an RDS snapshot (`aws rds create-db-snapshot`). Rolling back means restoring that snapshot and deploying the earlier release; every session opened since the snapshot is lost, so reissue those tokens with `deploy/konjir-ops.sh connect`.
- **OS refresh:** `terraform apply -replace=module.kolab.aws_instance.kolab`. The AMI is pinned when the instance is created.
- **Tear down:** `terraform destroy`. Final snapshots of the data volume and the database are kept by default. For a teardown that leaves nothing, run `terraform apply -var final_snapshot_on_destroy=false` first, then `terraform destroy -var final_snapshot_on_destroy=false`. The apply is needed because destroy reads the database's snapshot setting from state. Daily volume snapshots made before the teardown remain until you delete them. The state bucket stays until you remove it.

The admin token is generated by Terraform, so it is also in the state file. That is why the state bucket is private, encrypted and TLS-only.

**Testing only.** This is one instance with no failover. With the GitHub OAuth app set up, people sign in with GitHub, and their tokens last 15 minutes and refresh (D55). Hand-issued tokens are bearer tokens with no expiry: hand them out privately, and revoke them with `admin_end_session` (by `token`, `session` key or `actor`; Kolab stores only their hashes, so it can't show a token again). Turn them off with `KONJIR_HAND_ISSUED_TOKENS=off` once nothing needs them.

## Releasing the CLI

`nx release` versions `konjir` (D23), configured in `nx.json`'s `release`: the `konjir` project only, tagged `konjir@<version>`. The current version is the newest such tag, or `apps/cli/package.json`'s before the first release. Bumps are plain semver, so `minor` from 0.5.0 is 0.6.0. The commits here aren't conventional commits, so the version is given, not inferred, and nx release writes no changelog. `apps/cli/scripts/version-actions.cjs` writes the version, in place of `@nx/js`'s, so the workspace doesn't install `@nx/js`. Installing it would add Babel to every install, the instance's included, and turn on Nx's source-file analysis, which needs TypeScript 5's JavaScript API. Publishing isn't nx release's: the workflow below publishes the tarball it tested with `npm publish`.

```
npx nx release version 0.6.0 --first-release --dry-run   # preview the version the workflow would set
```

Publishing runs only in GitHub Actions, by hand: **Actions › Release CLI › Run workflow** on main, with a version (`patch`, `minor`, `major` or an exact `X.Y.Z`; no prereleases) and dry run on (the default) or off. The workflow, `.github/workflows/release-cli.yml`, has four jobs, each with only the permissions it needs:

1. **Build konjir release** (read-only) sets the version in the runner and commits nothing. It refuses a version that already has a tag or is on npm. It builds the tarball and the binaries, checks both against a Kolab it starts from the checkout, runs `npm publish --dry-run`, and uploads the files with `SHA256SUMS`. A dry run stops here.
2. **Draft GitHub release** attests the files' build provenance (`gh attestation verify <file> --repo konjir/kolab` checks a download). It creates the release `konjir@<version>` as a draft, with the files and notes generated from the merged pull requests.
3. **Publish konjir to npm** runs in the `npm-release` environment, with no checkout and no dependencies. It publishes the tested tarball, with provenance, through npm 11.
4. **Publish GitHub release** takes the draft out of draft. That creates the tag on the built commit, and the next release reads its version from that tag.

Before the first release, Lee sets up:

- **A GitHub environment** named `npm-release` (Settings › Environments), with deployment branches limited to `main`, and a required reviewer if wanted. A copy of the workflow on another branch then can't reach the npm credentials.
- **npm trusted publishing**, preferred. On npmjs.com, konjir's settings › Trusted publishing › GitHub Actions: repository `konjir/kolab`, workflow `release-cli.yml`, environment `npm-release`. No secret is needed. A package must exist before trusted publishing can be configured on npm, so the first publish may need the fallback.
- **Or the fallback:** an `NPM_TOKEN` secret in the `npm-release` environment, a granular npm token with write access to `konjir`. npm caps such tokens at 90 days, so it needs rotating.

If a run fails, what to do depends on how far it got. Before *Publish konjir to npm*, nothing is published: delete the draft release if there is one (`gh release delete konjir@<version>`), then run again. If npm has the version but *Publish GitHub release* failed, re-run that job, or run `gh release edit konjir@<version> --draft=false`. A new run for a version npm already has stops in its first job.

The published package declares the licence `ISC`, as the root `package.json` does, but the repository has no `LICENSE` file yet.

## Who pays for which model calls

Kolab makes no model calls (REV5, VER7). It has no model SDK among its dependencies, holds no model credentials, and its instance role has no Bedrock access. All the work that takes judgment happens in collaborators' own harnesses.

| Work | Runs where | Paid by |
| --- | --- | --- |
| Authoring specs, bindings, plans; implementing; answering questions | Each collaborator's harness (Claude Code, Codex, opencode, …) | That collaborator's own subscription or API account |
| Reviewing a version: contradictions, layer leaks, one testable intent per element | The reviewing agent's own harness, through `konjir_review` (see *Review*) | The reviewer's own subscription or API account |
| Structural checks, cascade, addressing, rebase, roles | The Konjir server | No model at all |

The server is built so it can't drift across that line:

- **It never asks for, stores, or relays a collaborator's model credentials.** A collaborator's token identifies them to Konjir and nothing else.
- **It never borrows a client's model.** It doesn't use MCP sampling or any other way to make a collaborator's harness run inference on the server's behalf. When the server needs judgment beyond its structural checks, it asks for a review or raises a question, which an agent or a person answers from their own harness, by their own choice.
- **Each collaborator's model use stays inside their own harness and account.** Konjir doesn't pool, share or proxy anyone's access. Whether a given plan permits a given use (for example, connecting an MCP server, or how much automated work a subscription may drive) is set by that provider's terms. Each collaborator should confirm their own plan covers how they use it.

`apps/server/test/no-model.test.ts` fails if any package of the workspace declares a model SDK, or if the lockfile installs one, even as a dependency of a dependency. Until W1.7 the server could call Amazon Bedrock as a semantic review gate (`KONJIR_REVIEW=bedrock`); that reviewer, its AWS SDK packages, its settings, its Terraform variables and its IAM permissions are gone. `konjir serve` refuses to start when `KONJIR_REVIEW` or `--review` asks for anything but `structural`, so no one believes a gate runs that doesn't, and warns that it ignores a `KONJIR_REVIEW_MODEL` set on its own. What the test server's boot script writes, `structural` with a model beside it, starts it silently.

## Questions, notes and push

An engineer writing a binding talks to the spec through two verbs:

- **`ask`** is for a decision the engineer needs before they can proceed. Pass `from=<binding element>` to name the element that waits on it. When product answers, that element gets a `query_answered` mark carrying the question and the answer. Editing the element, or `clear_mark`, settles it. The answer reaches the binding even if the spec text never changes.
- **`annotate`** leaves a note: an interpretation the engineer is going ahead with, an assumption, a risk, or something they couldn't check. It blocks nothing, but it waits in product's queue until product replies, so product can object. A reply to a note marks nothing.

Both can target an element or a quoted span (`kj:orders#R13~q({"exact":"50 meters"})`). `read_node` shows them beside the element they're about, open and answered, including ones asked on earlier versions of the spec. Either layer can use them in either direction.

**Push.** Push is per kolab (D50). Each layer has an inbox resource in each kolab, `konjir://inbox/<kolab>/functional` and `konjir://inbox/<kolab>/technical`, holding its open questions, notes and marks there, its open case files, and, for the reader, the review requests waiting for them on that layer. Each actor has `konjir://answers/<kolab>/<actor>`, which holds what they raised in that kolab, with replies, the versions they submitted there for review, with the verdicts, and the case files they opened or argued there, with their rulings. Each body names its `kolab`. `whoami` lists the two for the session, in the session's own kolab, and a client subscribes to what it lists. A change in one kolab signals only that kolab's resources, so a subscriber in another kolab hears nothing of it. A session may read and subscribe only to its own kolab's inboxes and its own answers there: another kolab's inbox reads as if it didn't exist, and a `subscriptions/listen` asking for anything else (another kolab's resources, another actor's answers, or the per-layer `konjir://inbox/<layer>` of a release before D50) is refused in-band before it opens, HTTP 200 with the JSON-RPC error `-32003` and `data.reason` `not_subscribable`, which names nothing of the other kolab. The bridge retries that, asking `whoami` afresh, and `konjir watch` says to run it again. Neither `@onivoro/server-mcp` nor its listen-stream gate shows Kolab the URIs a stream asks for, so this check is Kolab's own Nest middleware on `POST /mcp` (`ListenScope`), which reads the token exactly as the transport does and only ever refuses; the admin token may subscribe to anything. It first applies the transport's own Host/Origin guard, and leaves a request with no valid JSON-RPC id to the transport, so it answers nothing the transport would refuse first; and a session lookup that takes over 10 seconds refuses the stream as `gate_timeout`. It covers `subscriptions/listen` alone, which is enough because the transport is stateless: a 2025-era `resources/subscribe` gets "method not found", and a test fails if sessions are ever turned on. Kolab declares `resources.subscribe` and signals a resource whenever it changes, over MCP 2026-07-28 `subscriptions/listen`. A client that listens gets `notifications/resources/updated` and re-reads the resource. Only the URI is pushed, never the content, and reading `answers` is limited to its own actor. Ending a session closes its open listen streams at once, as the server closing the subscription, and nothing more is signalled to them. Each change is also checked against the session before it is signalled, so a session ended any other way closes its stream on the next change instead. Its token is then refused (401), so a client that reconnects with it learns it was revoked. A listen stream whose session ends while it is opening is refused in-band instead: HTTP 200 with the JSON-RPC error `-32003` and `data.reason` `session_ended`, which the channel bridge and `konjir watch` treat as the token revoked, as they do a 401. The session is checked as each stream opens, so if that check fails (the database is unreachable, say) the stream is refused as `gate_failed`, or `gate_timeout` after 10 seconds, rather than opened and checked at the next change; the bridge retries those with backoff, and `konjir watch` says to run it again. [`@onivoro/server-mcp`](https://www.npmjs.com/package/@onivoro/server-mcp) tracks, gates and closes the streams (`McpHttpService.closeListenStreams` and the auth strategy's `acceptListenStream`); Kolab says which to close. Other sessions' streams, including those of the same person's other agents, are untouched.

**Push across processes.** Several Kolab processes can serve one Postgres database, and an agent listening on any of them hears a change made through any other (API5). Each engine event is sent with Postgres `NOTIFY` inside the transaction that commits its change, so it is delivered only if the change commits, and never on a rollback. Each process `LISTEN`s on the `konjir_events` channel over one connection of its own, apart from its pool, through [`@onivoro/server-pg-notify`](https://www.npmjs.com/package/@onivoro/server-pg-notify)'s `NotificationListener` (its Nest-free `/listener` entry), which reconnects with backoff (1 s, doubling to 30 s, without limit) when the connection drops, and stops when the process closes. A process tells its own listeners once the transaction commits, and skips its own notification when it hears it back, so nothing is signalled twice. The payload is the event (a kolab's name with a layer or an actor, or an ended session's sessionKey), not the content, and never a token or a row's id; an event too long for `NOTIFY` is sent as a signal to re-read every inbox. An inbox event's kolab rides on the notice, `{"from", "kolab", "event": {"inbox", "layer" | "actor"}}`, so the event keeps the shape a release before D50 reads: during a rolling deploy an older process still hears a newer one's changes (it ignores the unknown field), and a newer process hears an older one's kolab-less event as a resync, since it can't tell which kolab changed. A burst of those costs one resync: resync notices heard within 250 ms fold into one. Two windows remain while old and new releases run side by side, and only draining the old processes closes them: an old process still signals the per-layer `konjir://inbox/<layer>` to its own subscribers, so they hear every kolab's changes on that layer until it stops, the leak D50 closes; and a client whose `whoami` reached a new process but whose `subscriptions/listen` reached an old one gets a stream that opens and stays quiet, since the old process never signals the per-kolab URIs. The channel bridge re-reads everything when it reconnects, so nothing is lost for good, only late. A short drain (deregistration delay) on the old processes bounds both. Anyone who can connect to the database can NOTIFY on the channel, so a process drops anything that isn't exactly an event Kolab sends, including a payload that isn't JSON at all, which costs no reconnect. It counts and logs each one it drops, never the payload. A process that can't LISTEN at boot doesn't start. The listening connection notices a silent drop too (a failover or a NAT drop, with no FIN or RST): it is checked every 10 seconds, a check unanswered in 5 seconds counts as a loss, TCP keepalive starts after 10 seconds idle, and a reconnect that hangs gives up after 10 seconds. When the connection is lost after boot, changes committed meanwhile aren't heard, so once the LISTEN is back the process resyncs: in each kolab with an open session, it signals every inbox there and the answers of each actor with an open session there, and each subscriber re-reads. The resync reads those actors before signalling anything, and if that fails it is retried with backoff (1 s, doubling to 30 s) until it succeeds or the connection is lost again. The process logs at error level as soon as the connection is lost, at error level for each failed resync, and at warn level once it is back and every inbox has been signalled. On PGlite there is one process, and events go only to its own listeners.

Claude Code doesn't yet turn these notifications into a turn for the model. Until it does, an agent waiting on answers can run `konjir watch --once` as a background command, which exits with the change as soon as the inbox has one. `konjir watch` without `--once` prints the inbox, then one JSON line per change, for a harness that tails output.

## Case files and rulings

Most of what an agent needs is an answer (*Questions, notes and push*). A genuine disagreement the two sides can't settle becomes a **case file** (CASE1): `konjir_open_case address=kj:checkout#R1 question=… claim=… seeks=keep_intent|change_intent evidence=[…]` opens one on one element of a committed version in the session's kolab, with the opener's position and the side it takes: keep the intent as written, or change it. Evidence is a list: `kj:` addresses, each of which must resolve for the session, and anything else as text (a commit, a file and line, a test run). The other side answers with `konjir_add_position case=<id> claim=… evidence=[…]`, which takes the opposite side. A case file holds one position for each side. An engineer who finds the spec can't be met as written opens one against the spec instead of patching the behavior (CASE5). An open case file blocks nothing (CASE7).

- **Who argues (D49):** only those who belong to the kolab's work, holding Write on a layer of it. A session whose actor holds only Read there (anyone reading a public kolab, say) can't open or argue a case file, and sees no case files, positions or rulings: row-level security admits them only for a session that belongs (`kj_session_belongs`, 0013), and the instructions give it no precedent.
- **The other side** is someone else's: never the opener's own person, nor one of their agents, since one person and their agents are one side. The opener sees who took it, and which side.

A **ruling** (CASE2–CASE6) is given with `konjir_rule`:

- **On a case file:** `case=<id> verdicts={"<position>":"sustained","<position>":"overruled"}`, once it holds both sides (D51). It sustains exactly one position and overrules the other, and its effect is the side the sustained position seeks (`effect`, if given, must agree). The case file is ruled, once.
- **Directly** (CASE3, D16): `address=kj:checkout#R1`, or a whole node, with no case file behind it, and an `effect` saying what it does. It is the way out for a case file whose other side never comes: any case file still open on the element is **superseded** by it (`case_file.superseded_by`), leaves the inbox, and reaches its parties' answers.
- Either way it has `text`, an `effect` (`change_intent` or `keep_intent`, CASE6), and optionally `replaces`, what it overrules in words. It records its author and its date (`ruling.ruled_at`, CASE4), and the layer's inbox is signalled, in the ruling's kolab.
- **Who rules (D51):** a person, never an agent (CASE2), from a session in the role that writes the element's layer, whose access in the kolab includes Write on that layer. On a case file, never a party: not one who holds a position on it, nor the person whose agent does. The database holds every new ruling to a person too (`kj_ruling_by_person`).
- **A ruling that changes the intent marks the element (D51):** a `ruled` mark on its node's live version, with a question to its layer. Neither can be cleared or answered by hand: the next version that amends or removes the element settles both (a ruling on a whole node, any revision). A ruling that keeps the intent marks nothing.
- **Nothing is rewritten or removed** (`kj_case_fixed`): a ruling never changes and is never deleted; a later ruling says what it replaces. A position keeps its claim, evidence and side, and gets its verdict once, only once its case file has a ruling; a case file keeps its subject and question, is ruled only with its ruling row, and takes no position once it isn't open. Deleting or truncating any of the three is refused.

Rulings are **precedent in their kolab only** (CASE4, TEN13), for those who belong to its work (D49): `konjir_operating_instructions` lists the session's kolab's newest 20, `konjir_read_node` shows each beside its element (with the element's open case files), and `konjir_list_rulings` lists them all. Open case files wait in the inbox of the element's layer (`cases`), and each actor's answers carry the case files they opened or argued, most recently changed first, with their rulings. Kolab writes case files, positions and rulings as `kj_system`, after its checks. Migration 0013 adds the date, the effect, the side each position takes, who opened a case file on what question and when, the `superseded` state and the `ruled` mark (both value lists, D40), the rules above, and the indexes the reads use. Rows written before it keep no date or side: nothing is guessed, and its checks bind new rows only. A duplicate ruling or position among those rows stops the migration, naming it.

## Removing links

A link's owner removes it in a draft of its node (D48: the owner of an orphaned link "re-points or removes it"; D50). `konjir_unlink node=<node> version=<draft> links=[…]` removes links in a draft the session wrote, and `konjir_draft`'s `unlink` does it in the draft it writes. Each link is named by its id (`edge` in `konjir_lineage`, `link` in `konjir_list_stale`) or by its source element and target address, whose version is ignored; without `kind`, links of every kind between the two go.

- **Part of the version.** A draft records each link it drops (`link_removal`, migration 0012). Nothing changes until the version commits: its reviewers see the removals in `konjir_read_node` (`removes_links`), and a draft sent back, abandoned or rejected changes nothing. Removing links is refused once the version is in review.
- **At the commit**, the links it was built on carry forward without the removed ones (CAS3). Each removed link's open mark settles, `its link was removed by <node>@<version>`, with the marks it alone caused (LNK5), so removing an orphaned link settles its mark (LNK6). A transitive (`upstream_dirty`) mark at or below the removed link's source element keeps each cause only while that cause's walk still reaches it without the link, and clears with its last (LNK5).
- **A link the draft declared itself** goes at once. Linking a removed link again in the same draft takes the removal back.
- **Re-pointing** happens only in a draft, reviewed with it: a committed version's links never change (VER1). Linking, in a draft of your own, an element to the current words of a target element replaces the link of the version the draft is built on that has an open `orphaned` or `fuzzy_reanchor` mark, from the same element, of the same kind, to the same target element, quote for quote or whole for whole. The draft drops the marked link in the same transaction that adds the new one, and the mark settles when the draft commits. A `changed` mark is never settled this way, and a second, narrower link stands beside the first. Of two such quote links, the one whose prefix and suffix the new quote keeps is replaced; if that doesn't pick one, the link is refused, and the owner names the one to drop with `konjir_unlink`. Another writer linking from someone's draft adds a link, as before.
- **A link targets its node's live version** (its latest committed one), never an older version where words since changed still stand.
- **Removing the element** drops its links, as before, and now settles their marks and every other open mark on it, `its element was removed by <node>@<version>`: no mark moves onto an element its version doesn't have.
- **Folds and the outbox.** A draft overtaken by Kolab's rebases is folded with its removals (CAS7). The removal runs in the commit's `after_commit` job, so a cascade stopped part way and run again removes the link and settles its mark once.
- **Rulings (D47).** `konjir_admin_apply_ruling … unlink=[…]` drops links of the node's live version, with targets in the node's kolab, and commits as rulings do.
- **Row-level security.** As `kj_agent`, a session records removals, and deletes links, only on a draft of its own, in its layer and kolab.

## How each decision is implemented

**1. Addressing.** An address is `kj:[<kolab>/]<node>[@<version>][#<element>][~q(<selector>)]` (see *Addresses*). Every edge stores the fingerprint of the content it addressed when it was created. On an upstream commit, Kolab re-resolves each address against the new version:

- **Same fingerprint:** the edge is re-pinned. This is a pointer bump, not a mark.
- **Different content:** the dependent gets a `changed` mark.
- **A span that changed:** a `fuzzy_reanchor` mark. That is a near match (edited wording), or the exact words without the prefix or suffix they were quoted with, such as a copy in another statement (D42). The exact words with that context still around them, anywhere in the element, re-pin cleanly.
- **Gone:** `orphaned` mark.

An element address covers that element's subtree, so addressing a section means addressing its requirements too.

For a quote under 10 characters whose prefix and suffix both still stand verbatim, each strong (two words or eight letters), with a short gap between them (at most twice the quote's length plus 16 characters, with no sentence's end in it), the gap is the quoted words, edited, if it is still at least 0.5 similar to the quote: "7 days" become "14 days" (0.71) is a `fuzzy_reanchor` mark, a change, not an orphan (ADR8). A rewrite between the context words ("7 days" to "never") stays an orphan. The exact words with their context are still exact (D42).

A span's context is its prefix and suffix. It agrees when more than half of the words on one side still sit next to the quote, and either at least two of them do, or both sides agree. One word or punctuation alone is too little. `link` accepts only a target that resolves exactly, and quotes of at most 1,000 characters. When it refuses one, it suggests the current words with several words of context either side.

**2. Overrides.** Every delta records its base: the parent version and fingerprint it was written against. When a parent commits, each live child is rebased:

- Untouched elements are inherited.
- An override whose parent text now matches the child's text is retired as converged.
- A changed override goes `dirty` but keeps applying.
- A deleted one goes `orphaned` but keeps applying.

The rebases run in the background, after the parent's commit returns: Kolab's outbox worker rebases each variant in a job of its own, level by level, built on the variant's version as it is when the job runs (P6, D43; see *Durable waits: the outbox*). The rebased child commits after Kolab's structural checks alone, without review (VER12, D19): no person wrote it, so there is no author to review against. A conflicting override is still marked and asks its question. Resolving a dirty override records precedent, and the same `(base, parent, child)` triple then resolves itself on the next rebase; a resolution that waits in review records it, and settles its mark, when it commits.

**3. Roles.** A session activates exactly one role, and an actor has at most one open session (NIST dynamic separation of duty). Each agent is an actor of its own, so the rule holds per agent, and one person's agents can each hold a session at once. Kolab rejects writes outside the session's layer. Row-level security repeats the check in the database: agents may only *draft* (never commit), only in their session's layer, and only on a node of that layer, and they may only declare edges from their own layer. They write only as their session's own actor and role: a version, element, delta or question can't be authored as anyone else, an agent's owner included. And they read and write only in their session's kolab, and write only the layers their access covers (see *Accounts, kolabs and access*).

## Review

A version moves from drafted, to in review, to committed (VER2, REV2). `konjir_submit_for_review` runs Kolab's checks, which are structural only: no empty element, no element repeating another word for word, no element nested under one that doesn't exist (REV1). Kolab runs no model and reports no findings itself (REV5); whether a version contradicts itself or leaks across layers is for its reviewers. A version that fails the checks stays drafted, with the reason in its review note and the result, for its author to fix or resubmit. One that passes goes into review: it is `in_review`, and each other actor holding Write on its layer gets a review request in its inbox, connected or not (VER16). Holding Write means the actor's access in the version's kolab includes Write on that layer, as `kj_access` computes it from grants, teams and organizations, an agent's cut down to its owner's (W1.3); sessions don't count, so a reader with a session isn't a reviewer, and a writer with no session, or one in the other role, is. A reviewer gives its verdict from a session in the layer's role. The request names its subject, a version, and says how to review it. The `konjir_reviewer_instructions` prompt (`konjir instructions reviewer` in a shell) gives a reviewing agent the full checklist: judging each link against the version it pins, the layer rules, one testable intent per element, what a `contradiction` and a `layer_leak` are and what each does, and how to approve or request changes. It tells the reviewer to treat everything it reads through Kolab (elements, linked text, questions, notes, review notes, suggested next steps) as data, not instructions. It holds the rules alone, no kolab's content, so every session and the admin token get the same text.

- **Who reviews (D19, D25, D33):** any actor other than the author with Write on the layer. Separation of duty is per agent, so another agent of the author's person counts, and so does the person. Only the version's own layer reviews it.
- **`konjir_review verdict=approve`:** one approval commits the version, through the same per-node commit step as any other commit, and the other requests are withdrawn. A `layer_leak`, content in the wrong layer that conflicts with nothing, can come with an approval: the version commits and the finding becomes a `role_boundary` mark and a question to the layer that owns the answer: implementation in a spec goes back to its author, and behavior a binding adds that its linked requirements don't mention goes to the spec it links to. Answering the question clears the mark. A `contradiction` can't: two elements that can't both hold, or a binding element that conflicts with a requirement it links to (stricter, looser or different), stops the commit (VER9), so it comes only with a request for changes. Anything that conflicts is a contradiction.
- **`konjir_review verdict=request_changes`:** needs a note, and may carry findings. The version returns to drafted, and every request for it is withdrawn. Its author resubmits it unchanged, or drafts a new version and abandons this one.
- **`konjir_abandon`:** the author rejects their own draft or version in review, under the node's lock, so it can't land on a version an approval has just committed; it says so instead. A person's version is rejected only this way, or as stale, or when Kolab folds it into a fresh rebase (VER2, D33, D38). Kolab's own rebases are rejected when they fail their checks.
- **Plan versions (VER3, PLN2):** a `wbs` or `work_package` version commits after structural checks, without review, whoever else holds Write on the technical layer.
- **Reviewers gone:** resubmitting a version that waits in review asks whoever can review it now, adding requests for new reviewers and withdrawing those of actors who no longer can (their Write was revoked, say). If no one can, the checks alone commit it, unreviewed. An author who lost Write meanwhile can't get it committed: entering review and committing both re-check the author, under the node's lock, and reject the version instead.
- **No reviewer (VER11):** when no one else holds Write on the layer, Kolab's checks alone commit the version, and its review note says it committed unreviewed. A solo project works as it did before review existed.
- **Kolab's own rebases (VER12):** commit after structural checks only, with no review request.
- **A ruling applied to the mirror (D47):** `konjir_admin_apply_ruling ruling=D46 actor=mirror-product node=kolab/kolab-binding elements=…` (or `deltas=…`, and `parent=` for a variant in the node's kolab) writes a version as that actor (who must hold Write on the node's layer in its kolab), in the role of that layer, and commits it after structural checks only, with no review request: the ruling is already the approval. Its review note records the ruling and that it came through the admin token. The admin token works in no kolab, so `node` is `<kolab>/<node>`, or a name alone only when no other kolab has a node of that name (otherwise it is refused, naming the kolabs that do), and `committed` is the full address. It goes through the same per-node commit step as any commit, so it is rejected as stale if the node moved on, and it makes anything waiting in review on the node stale. Only the admin token reaches it; an agent session is refused, so no agent can use it to skip review.
- **While a version waits in review**, the W1.17 rules hold. A commit by anyone else to the node rejects it as stale at once, and its requests leave the inboxes. A rebase of Kolab's own doesn't: at approval, the approved version is folded onto the rebase, and the fold commits on structural checks, since its edit was reviewed. In the same transaction, under the node's lock, the version it folds is settled as `folded into` the fold, and its approval is copied onto the fold, so the author's answers show the fold committed with it; if the author abandoned the version meanwhile, the fold doesn't commit. A fold carries the version's override resolution too. A draft overtaken by Kolab's rebases before it was submitted is folded at submission, and the fold goes into review itself.
- **Inboxes:** a review request in the reviewer's layer inbox signals that inbox, and each verdict signals the author's answers, with the same events as questions and marks. The Konjir channel turns a new request, or a verdict on the session's own submission, into a message.

### Durable waits: the outbox

Every wait in review and the question tier is a row: a version in review and its requests (`review_request`), each verdict, each question and its answer. What a change still owes once it commits is a row too: a job in the `outbox` table (migration 0010), written in the transaction that makes the change, so it exists if and only if the change committed. A server restart mid-review loses no request or verdict, and the work they owe is done once.

- **`after_commit`:** each version that commits owes its cascade (stale versions in review withdrawn, edges carried forward, marks raised and spread, its own catch-up) and the layer leaks its reviewers reported with `konjir_review`, as `role_boundary` marks and questions. The commit step writes the job as it commits the version.
- **`rebase`** (migration 0015, P6, D43): each variant whose live version sits on an older version of the node that committed owes a rebase. The commit step writes one job per variant, unclaimed, in the same transaction, with a `work` notice, and the commit returns once it is committed, with `rebases`, the number queued (`rebases_queued` over MCP). The worker runs them; see *Rebasing in the background* below.
- **`settle`:** a version that something committed past while it waited owes its fold onto Kolab's rebase, or its rejection as stale if someone else committed: an approved version (the transaction that records the approval writes the job), a ruling applied through the admin token (D47; its commit step writes it), and a submitted draft. Kolab's own rebases owe nothing: an overtaken one is dropped at once.
- **Answers** need no job: an answer, the boundary mark it settles and the asker's `query_answered` mark are written in one transaction. So are a resolution's version and the ruling waiting on it.

**Claims.** The process that writes a job claims it as it writes it, runs the work at once, in the caller's call, and deletes the job when the work is done, so a commit's caller still sees its cascade finish or fail with a `CascadeError`. Each claim carries a token, fresh for each claim, and the claimant renews, deletes and releases the job only by that token, so a process whose claim lapsed and was taken by another touches nothing of it. A claim lasts 30 s and is renewed every 10 s while its work runs, on PGlite too. A renewal that finds the claim gone, or that fails for a whole lease, marks it lost and logs it: the work stops at its next step (before each variant's catch-up, and before the layer leaks), and the process that took the job does it, once more. A process never takes over a job it is running itself, even if a busy event loop let its lease lapse. A job a stopped process held is free when its claim lapses; on PGlite, the first Kolab in a process to open a data directory frees every claim in it at once.

**Failures.** A job whose work fails is freed with its error (`last_error`), to be tried again after a backoff that doubles from 1 s to 5 minutes. After ten attempts it is `dead`: no worker takes it again, an error is logged, and `konjir_admin_outbox` lists it (`state=dead` for those alone) until `konjir_admin_outbox retry=<id>` makes it due again.

**Order.** A node's cascades run in the order its versions committed, each carrying the one before it forward. Before a version's cascade, an earlier one its node still owes runs first, if it is free and due. If it is held by another live process, waiting out a backoff, or dead, the later cascade waits instead: the commit returns with `cascade: 'queued'`, its job is released with a `work` notice, and it runs once the earlier one is done (the process that finishes a cascade runs the next of its node; one that releases a waiting job after the earlier one finished runs it itself), never ahead of it. A cascade run late re-checks only the links pinned to versions older than its own, so it never touches a link that a newer version, or a dependent's catch-up, has re-pinned.

**The worker.** `konjir serve` runs Kolab's outbox worker (`Kolab.startWorker`). It runs every due job as the server boots, then again whenever a job falls due or a claim lapses, and at least every 5 s. Several processes on one Postgres database share the outbox: each job is claimed by one at a time, with `for update skip locked`. A process that frees a job, because its work failed, an admin retried it, or the process is closing, says so with a `work` notice on `konjir_events` (`{"from": <origin>, "work": true}`), in the same transaction, and every other process's worker looks again. This release ignores notices of kinds it doesn't know, and fields it doesn't know on those it does; releases before it drop and log a `work` notice as not a Kolab event, so during a rolling deploy from one, its log shows a dropped notification for each job freed, and nothing else goes wrong. Closing a Kolab stops its worker, waits up to 10 s for the outbox work it is running, then frees the claims it still holds.

**Idempotent work.** A job run again after a stop part way through does each thing once. Each mark is raised with its question, and each direct mark with its transitive marks, in one transaction. A layer leak, and a variant's `rebase_failed` mark (D44: at most one open), are checked for and raised in one transaction under the node's lock, so two runs that overlap raise one. Each link is checked again, and marked, in one transaction under its dependent's lock. A fold a stopped run already made, in review or committed, is the settle job's result: the version is settled as folded into it; one it wrote and never committed is rejected before the version is folded again. The version itself commits at most once, since it commits only from the state it was in.

The outbox is Kolab's internals: no agent reads it (`kj_agent` has no grant on it). `libs/engine/test/outbox.test.ts` stops a Kolab between steps, by closing its database under it, and opens another on the same database, on PGlite and Postgres; it also covers a lost claim, a cascade waiting behind one that is held or failing, a dead job retried, an interrupted ruling and a close that waits.

**Rebasing in the background (P6, D43).** A parent's commit no longer rebases its variants in the caller's call. Its commit step writes a `rebase` job for each variant behind it, in one statement, and the commit returns. A variant has one job waiting at a time: one already waiting covers it, and a commit by the variant itself deletes it, since that version's own catch-up owes the rebase. If a worker is running the variant's job when the parent commits again, the job may have read the older parent, so the commit sets `again` on it, and the job runs once more when it is done, whether its rebase passed or failed: no parent commit is lost. A dead job blocks nothing: the parent's next commit revives it. When a job dies, its variant gets a `rebase_failed` mark and question (D44). The cascade lists the variants again once the commit is visible. That catches a variant whose first version committed at the same moment, which the commit step's list couldn't see while its own catch-up couldn't see the commit (on Postgres). A variant whose rebase onto this version already failed and marked it gets no second job. The worker takes jobs oldest first, one variant per job, and each job rebases whatever the variant has live when it runs, onto whatever its parent's latest is then, never a list taken earlier (catch-up). The rebase goes through the same per-node commit step as any commit (W1.17): it commits after structural checks only (VER12), consults precedent (OVR9), is dropped if overtaken, and leaves one `rebase_failed` mark and question if it fails for the variant's own reasons (D44). As it commits, it writes its own variants' jobs, so the worker rebases level by level. A person who edits a variant while its rebase waits commits as usual, and the variant's own catch-up rebases their version at once. A rebase a stopped process had drafted but not committed stays drafted, and the job, run again, rebases the variant afresh. What waits is visible, while the variant is behind its parent: `konjir_read_node` shows its `rebase` (pending or dead, attempts, the parent version that queued it, if it's in the reader's kolab, and the last error), `konjir_list_nodes` marks it `rebase_pending` or `rebase_dead`, and `konjir_admin_outbox` lists each `rebase` job with its subject and `after`. A check that a variant may be rebased at all goes in `mayRebase`, which every path that rebases calls first. A test or script runs queued work at once with `Kolab.drainOutbox()`. `@konjir/engine/testing`'s `openKolab` and `setup` drain after each committing write, so a scenario reads a commit's rebases at once, unless opened with `queued: true`; `libs/engine/test/async-rebases.test.ts`, the queued property test and the outbox tests leave the queue alone.

## What the prototype found

**Element addressing has to be on both ends of an edge.** The measurement, at N = 100 requirements with one edited:

| Addressing | Dirty versions |
| --- | --- |
| Version scope everywhere | 202 of 202 (lockstep) |
| Element *targets*, whole-version sources | 202 of 202 |
| Element targets **and** element sources | **4**, at every N |
| Same, but the WBS derives from the whole binding | 202 of 202 |

Pointing at the changed requirement isn't enough. The edge must also say *which part of the dependent* relies on it, or the dirt spreads to the whole dependent version and everything downstream. One whole-version hop anywhere in a lineage collapses back to lockstep.

**Concurrency needs an explicit rule.** Each version records its base: the node's live version when it was drafted, which it was built on. It commits only while that is still the node's live version. Each node's commit step checks this and sets the version committed in one transaction that holds a lock on the node's row, and every write of a new version takes its number under the same lock. So two commits to one node can't both build on one version, and version numbers never collide. A draft can be overtaken while it's open, while Kolab's checks run, or while it waits in review:

- **Overtaken only by Kolab's own rebases:** the draft is folded into a fresh rebase, keeping its author and declared edges.
- **Overtaken only by Kolab's own rebases:** the fold is built on the newest of the versions just judged, so a commit that lands while it is being made overtakes the fold in turn.
- **Overtaken by another person's commit:** the draft is rejected as stale, to be redrafted. `commit` throws a `GateError`, and `konjir_submit_for_review` returns `stale: true` and says to re-read and redraft. The caller never gets a raw database error for losing a race.
- **A rebase of Kolab's own that was overtaken** is dropped, and the variant's live version is caught up onto the parent's latest version on the spot.

A parent's commit rebases each variant's live version as it is when its turn comes, never the version it listed. A rebase that fails for the variant's own reasons (its checks refuse it, or throw) marks the variant `rebase_failed`, with a question, and the parent's commit carries on to the rest (D44), so an inbox tells a failed rebase from a rejected review. A variant holds at most one such mark: a later failure re-points it at the newer parent. The mark and its question settle once the variant's live version sits on the parent's latest version, whether through a rebase that passes or the variant's own commit with `parent` set to that version. Migration 0004 renames every `review_failed` mark of earlier releases to `rebase_failed`, since all of them came from failed rebases. On each variant it keeps open only the mark naming the newest parent, which is also the mark the engine re-points, and moves it to the live version. It settles the mark if the variant already sits on its parent's latest version, and asks the question where none was written. Any other failure, such as a lost connection, or a failure in the cascade of a version that did commit, stops the cascade: the caller gets a `CascadeError` saying which version committed and what didn't finish. Its `after_commit` job stays in the outbox, and the worker runs the cascade again after a backoff (see *Durable waits: the outbox*). A later commit of the same node succeeds, but its cascade waits for that one, in commit order, and its result says so (`cascade: 'queued'`), so until the retry, a success can stand over variants left behind. The variant's own next commit still catches the variant up. A draft left open across the upgrade to migration 0003 has no recorded base, so it is rejected as stale on review if its node has any committed version, and must be redrafted. `libs/engine/test/concurrency.test.ts` drives each race that `npm run rebase-storm -- --races` reproduces, on PGlite and Postgres.

**Property tests check the cascade and rebases (W2.5).** `libs/engine/test/properties.test.ts` uses [fast-check](https://fast-check.dev) to generate a spec family and a sequence of edits to it. The family has:

- a parent with a nested element
- a variant of it, and a variant of that variant, which itself depends on the binding
- a binding linked into all three, including a cycle with the nested variant
- a WBS linked into the binding, and a work package linked into the WBS

The edits are parent commits that change, delete and restore elements, variant overrides, edits of marked elements, clears, override resolutions, links removed in a draft (with or without an edit of their element) and links linked again. A stand-in for review, the test's own submission checks, rejects some of them.

After each step the test compares Kolab with a reference model (`libs/engine/test/cascade-model.ts`), written from the spec rather than the engine. It checks:

- every element's text
- every override's state: clean, retired, dirty or orphaned
- exactly which marks are open, each on its node's live version, and that a mark carried forward keeps its id rather than being raised again
- one open question per dirty or orphaned override and no other, and a resolved question answered with the ruling by whoever made it
- every link: either pinned to its target's live version with a matching fingerprint, or carrying an open mark, and a removed link gone from the live version

The seed is fixed, so CI runs the same sequences every time: 25 on PGlite and 60 on Postgres, which runs them about twice as fast. Three environment variables change that: `KONJIR_PROPERTY_SEED` changes the seed and `KONJIR_PROPERTY_RUNS` the number of runs, to replay a failure or search harder; `KONJIR_PROPERTY_SHRINK=0` stops at the first failure instead of shrinking it.

The model makes three readings of the spec on purpose:

- **A link that already carries an open mark isn't re-checked by later commits.** CAS1's "each live link" is read as each link not already marked. Its owner settles the mark (LNK6), even if the target goes back to the pinned text, or is deleted after it changed.
- **A link whose target is gone can't re-pin.** Revising its element doesn't settle the mark (CAS4 says "clears that mark and re-pins its link"), and clearing it is refused: its owner re-points or removes it (D48; see *Removing links*).
- **When two rulings share a (base, parent, child) triple, the first stands.**

The tests found six bugs, now fixed, each with a regression in `libs/engine/test/property-regressions.test.ts`:

- **A mark didn't spread through a link that carried a mark of its own.** Such a link stays pinned to an older version. Clearing the link's mark then left its element clean while what it relied on was dirty. The walk now follows live links into any version of the node it reaches. Migration 0012 indexes `edge(target_version_id)` for it, with `edge(source_version_id)` and the open-mark lookups: measured on Postgres over 38,400 links, a step of the walk went from 11.7 ms to 0.4 ms, and the links a commit re-checks from 6.7 to 0.9 ms.
- **A self-settled override left its question open.** When a dirty or orphaned override came out clean on its own (its parent went back to the text it was written against, converged on it, or the variant overrode it again), its mark cleared but its question stayed open, where nothing could answer it. Kolab now answers it as `kolab`.
- **An override moving between orphaned and dirty kept its first wording.** It kept the mark and question it was first raised with. Both are now reworded.
- **A resolution's precedent was recorded after its own cascade.** So a variant of the resolved variant, rebased by that cascade with the same (base, parent, child) triple, was asked again. The ruling is now recorded in the transaction that commits the resolution, before its cascade: the precedent, and the mark closed with its question answered by the ruling and its author. Nothing is visible while the resolution is in review, however long that takes: the ruling waits on the resolution's version (`version.resolves`, W1.6), and a fold of the resolution carries it. Of two resolutions of one mark, only the one that commits records anything.
- **A variant's commit settled marks on overrides it only carried forward.** It counted every element with a delta as revised. Only elements whose text or place in the tree changed from the node's previous version count now.
- **Revising an element didn't settle its upstream_dirty marks**, though LNK6 and CAS4 say revising a marked element settles its mark. It now does, as a clear would.

**Agents can use it unaided.** Two separate agents were given only a token and the `konjir` command, with no access to the source. The product agent wrote and committed a password-reset spec. The engineer agent bound it to a Node/Postgres/Redis stack and linked each of its 11 elements to the requirements it serves. It then found two real ambiguities (which sessions survive a reset, and whether earlier reset links die) and asked them instead of deciding. The product owner ruled, and the product agent answered and amended the spec. Exactly the three binding elements tied to the amended requirements went dirty. The engineer revised them and cleared all three marks.

Their feedback drove these changes:

- per-verb help
- `key=value` on every verb
- links declared inside a draft
- partial edits by delta
- `mine=true` on questions
- a gate that says what it checked
- plain errors when Kolab is down or a token is refused
- editing a marked element counts as addressing its mark

## Deliberate simplifications

- **Semantic review is only as good as the reviewers.** Kolab's own checks are structural, and they say so; contradictions and layer leaks are caught only if a reviewing agent reports them. A version with no other writer on its layer commits on the structural checks alone, unreviewed (VER11).
- **Review waits aren't durable yet** (W1.8). A review request and its verdict are rows, so a restart keeps them, but nothing retries a commit or cascade an approval started if the process stops part way, and a version whose only reviewers lose Write waits until its author resubmits it (which commits it unreviewed) or abandons it.
- **The reviewers are those of the moment** the version is submitted or resubmitted; one who gains Write later can still review it, and its request is added on resubmission.
- **Review requests are readable by every session in their kolab**, like versions and questions there: their notes and findings included. Product review of bindings (VER13), editorial commits (VER14) and reviews of work packages (VER17, PLN16) aren't built.
- **Hand-issued session tokens are bearer tokens** with no expiry; Kolab stores only their hashes. They're fine on one machine or a trusted network, but not on the open internet. OAuth's access tokens, which GitHub sign-in issues, expire in 15 minutes (D55). The konjir CLI and the channel bridge still take a hand-issued token.
- **The web interface** works in one kolab per session: it moves between the kolabs a person reaches by ending the session and opening another, and doesn't read other kolabs' committed work in place (D49 would allow it). A person's first session still comes from an admin. It has no case files or rulings beyond resolving overrides until their verbs exist (CASE5–CASE7), no way to declare a link (agents declare them), though a draft can drop one (*unlink*, as `konjir_draft`'s `unlink`), and its activity shows when versions were written, not committed, and not when questions were answered, since Kolab doesn't record those times.
- **Identity of derivation is relaxed:** a content-identical upstream commit re-pins edges instead of minting new downstream versions.
- **Precedent applies on a child's next rebase**, not immediately to other open marks.
- **The cascade isn't durable.** A commit's cascade runs after it commits, in the calling process. If that process stops part way, or the cascade stops on a `CascadeError`, variants it hadn't reached stay on the old parent, with no mark, until the parent or the variant commits again.
- **Case files and rulings** (see *Case files and rulings*): a ruling that changes the intent marks the element but doesn't amend it: its product side amends and commits it, and the cascade does the rest. Rulings are served beside their elements and in the instructions, not yet in a pulled work package's context (PLN14), and an open case file doesn't yet block pulling work (PLN19), since pulling isn't built. Lee's Decisions Log entries aren't recorded as rulings by `konjir_admin_apply_ruling`, which applies them only. `ruling.verdict` is legacy, kept for rulings stored before CASE2 gave each position its own (`position.verdict`).
- **Tenancy is partial (W1.3, W1.4).** Addresses carry the kolab and node names are unique per kolab (W1.4), but a session can only read across kolabs: it can't link to, fork from or ask about another kolab, and there is no mark for lost access (LNK8), since those wait on a binding decision. Nodes can't be renamed, so there are no aliases yet (ADR11). A session works in exactly one kolab, and an actor still holds at most one open session, so an agent works in one kolab at a time; its token is its session, scoped to that kolab and its role, and its level comes from its grant. Kolabs can't yet be transferred (TEN5), visibility and base permission are set only when a kolab is made, kolabs, organizations and actors are archived rather than removed (D52), and accounts, teams and kolabs can't be renamed; teams can't be archived. Only the admin token manages tenancy: a kolab's own Admins can't yet grant access through Kolab.
- **Push is a signal, not a message.** Kolab signals an inbox over `subscriptions/listen`, and the agent reads what changed. Under the 2025 protocol, which has no listen stream, agents still poll `list_stale` and `list_queries`. Claude Code needs `konjir watch --once` (see *Questions, notes and push*). A Claude Code channel would need a local stdio bridge, because channels don't work over HTTP.
