Kolab keeps the spec and the code in step.

Your team writes down what the software should do (the spec) and how it is built (the binding), in one place that people and their agents share. When a requirement changes, Kolab marks exactly what relied on it.

The fog

Most specs are out of date by the time anyone builds from them.

Intent lives in too many places

A wiki page says one thing, a ticket another, the code a third. Nobody can say which one is true.

Changes don’t reach what depends on them

A requirement changes in a document. The code written against it never hears.

Agents fill gaps with guesses

Hand an agent an ambiguous ticket and it picks an answer and keeps going. You find out in review, or in production.

How it works

Say it once. Everything that depends on it hears.

Kolab is the server. A kolab, lowercase, is one project in it: its spec, the bindings built on it, and the questions between them. People and their agents work in it as product, who write the spec, or as engineer, who write the binding.

  1. 01

    Write the spec

    What the software does, in plain words, one requirement to an element. Each element has an address that keeps pointing at it through every edit. The one below is requirement R1 in version 3 of the checkout spec.

    kj:checkout@3#R1
  2. 02

    Bind it

    The binding says how it is built: the technical decisions, and the work packages still to do. Each element links to the requirements it serves, pinned to the exact text it was checked against.

    kj:checkout-stripe@1#C2
  3. 03

    Change it

    Every change is a new version, and it commits only once someone other than its author approves it. Then Kolab marks exactly what relied on the old text, with a word-by-word diff.

  4. 04

    Settle it

    Whoever owns a marked element checks it against the new text. It still holds, or it gets revised. Nothing stays quietly out of date.

Roles

Every agent stays in its role, and asks across it.

Product writes the spec. Engineering writes the binding. An agent in one role can’t edit what the other writes, so when it needs something across that line, it asks.

If a requirement starts to read like implementation, its review asks for a change instead of letting it slide. Answers are kept as precedent, so a settled question isn’t asked twice.

asks sam-engineer-2 asked about kj:password-reset@3#PR3
PR3 says the response is the same whether or not the email belongs to an account. Should the response time be indistinguishable too? Today the 202 returns faster for unknown emails, which can still reveal whether an account exists.

Waiting on Maya, as product. Work that relies on PR3 waits for the answer; every other job goes on.

Bring your own harness

Your agents connect with the subscriptions you already have.

Kolab is an MCP server. Connect Claude Code, or any client that speaks MCP, and your agents read specs, resolve addresses, submit drafts and ask questions: agents of yours, with no more access than you hold.

Kolab is the queue too. Run konjir work in your repository and it takes each item as a job: a review, a ready work package, a mark to settle. One agent does that one item and exits. No agent sits connected waiting for work.

Kolab never runs a model. Review and the heavy thinking happen in your harness, on your plan, under its terms. The rules come down the connection, so there is nothing to configure per agent.

Terminal
# make a kolab and connect two agents to it,
# product and engineer: one page in the browser
konjir connect claude --kolab my-checkout

# in its repository, sign in as yourself
# and set this machine to work
konjir login --role engineer
konjir repo register
konjir work
